Three names for one idea

Riya's canteen app adds up a bill. She has written totalOfTwo(a, b), totalOfThree(a, b, c) and totalWithDiscount(a, b, percent). Her friend Kabir keeps calling the wrong one, and every new case needs a new name.

Sir, I keep inventing names: totalOfTwo, totalOfThree… Is there a better way? Give them all the same name, total. Java allows several methods with one name as long as their parameter lists differ. The compiler looks at the arguments in each call and picks the matching version. So when I write total(40, 25, 15), Java decides at run time which one to use? No, earlier! The compiler decides, while compiling. By the time the program runs, each call already points to one exact method. You use this every day: println has ten versions.

What is method overloading?

Formal definition (write this in exams)

Method overloading means defining two or more methods in the same class with the same name but different parameter lists: a different number of parameters, different parameter types, or a different order of types. The method's signature (its name plus its parameter types) must be unique; the return type and parameter names are not part of it. The compiler chooses which overloaded method to call from the static types of the arguments, so overloading is a form of compile-time (static) polymorphism.

In simple words

Same name, different inputs. You call total(…); Java looks at what you passed in and runs the version written for exactly those inputs.

Three ways to overload, and where you've already seen them

By number of parameters

total(a, b) and total(a, b, c). The most common kind, often used for optional extras.

String.format, ArrayList(…)

By type of parameters

print(int), print(double), print(String). Same idea, different kinds of data.

The JDK is full of overloads

public class Main {
    public static void main(String[] args) {
        System.out.println(42);            // println(int)
        System.out.println(4.5);           // println(double)
        System.out.println('A');           // println(char)
        System.out.println("Chai");        // println(String)
        System.out.println(Math.abs(-7));    // abs(int)    returns int
        System.out.println(Math.abs(-7.5));  // abs(double) returns double
        System.out.println(String.valueOf(true) + String.valueOf(99));
    }
}
42 4.5 A Chai 7 7.5 true99

Each line calls a different method that happens to share a name. Notice that the two Math.abs methods also return different types. That's allowed, because their parameters differ too.

Constructors can be overloaded too

import java.util.ArrayList;

public class Main {
    public static void main(String[] args) {
        ArrayList<String> a = new ArrayList<>();      // ArrayList()
        ArrayList<String> b = new ArrayList<>(500);   // ArrayList(int initialCapacity)
        StringBuilder s1 = new StringBuilder();          // StringBuilder()
        StringBuilder s2 = new StringBuilder("Bill: ");  // StringBuilder(String)
        System.out.println(a.size() + " " + b.size() + " [" + s1 + "] [" + s2 + "]");
    }
}
0 0 [] [Bill: ]
Good practice: overloads should all do the same job. A common pattern is for the short versions to call the full one: total(a, b) just returns total(a, b, 0). Then the real logic lives in one place.

How javac chooses one method for a call

  1. Collect every method with that name

    static void show(long x)    { System.out.println("long"); }
static void show(Integer x) { System.out.println("Integer"); }
static void show(int... x)  { System.out.println("varargs"); }

show(5);   // which one?
    javac finds the three show methods in the class. Methods with a different name are never considered.

  2. Phase 1: exact match or widening only

    The argument 5 is an int. No show(int) exists, but int can widen to long. So show(long) is applicable in phase 1, and javac stops here: it prints long. Boxing and varargs are not even tried.

  3. Phase 2: allow boxing and unboxing

    Only if phase 1 finds nothing. Remove show(long) and the call boxes 5 into an Integer: it prints Integer.

  4. Phase 3: allow varargs

    Last resort. Remove the first two and show(int...) is used: the JVM receives a new int[]{5}. Varargs come in Lesson 5.6.

  5. Several fit in the same phase? Pick the most specific, or fail

    Main.java:6: error: reference to add is ambiguous
    add(1, 1);
    ^
  both method add(int,long) in Main and method add(long,int) in Main match
    If one candidate's parameters are all “narrower” than another's, it wins (String beats Object; int beats long). Here each method is better for one argument and worse for the other, so neither is more specific: compile error.

  6. The choice is written into the bytecode

    invokestatic  #33   // Method area:(I)I
invokestatic  #42   // Method area:(II)I
invokestatic  #47   // Method area:(D)D
    Each call instruction names the method and its descriptor: (I)I means “takes an int, returns an int”, (D)D double to double. The JVM never has to choose; javac already did.

Three calls, three different methods

Left: the call you write and what it prints. Right: how javac matches the arguments to a signature and what it writes into the class file.

Overload resolution for area(…) 6 steps
What you see
  1. area(5) matches area(int) exactly and prints 25.
  2. With two int arguments only area(int, int) has the right number of parameters: 4 × 6 = 24.
  3. 2.5 is a double, so area(double) runs: 3.14 × 2.5 × 2.5 = 19.625.
  4. Surprise: a char is a number (its Unicode value). 'A' is 65, which widens to int, so area(int) prints 4225.
  5. A long cannot go into an int parameter without a cast, but it can widen to double, so area(double) is chosen: 3.14 × 5.0 × 5.0 = 78.5.
  6. Two methods that differ only by return type have the same signature, calc(int). That's a compile error.
Behind the screen
  1. javac lists the argument types, here just (int), and checks every area. Two are applicable; area(int) is more specific than area(double), so it wins. The call is compiled as invokestatic area:(I)I.
  2. The number of arguments rules out the one-parameter versions immediately.
  3. A double can't be passed to an int parameter (that would lose the fraction), so only area(double) applies. Descriptor (D)D.
  4. char can widen to int (and to double). The int version is more specific. In the bytecode a char is already held as an int, so no conversion instruction is needed.
  5. long → int is narrowing (not automatic); long → double is widening. javac picks area(double) and widens the argument. For the literal 5L it simply stores 5.0; for a long variable it would insert an l2d (long to double) instruction.
  6. The rule check happens before any bytecode exists. Because both methods would have the signature calc(int), the class can't be compiled.

Where overloading shows up in real code

Overloading is how good APIs stay easy to use: one name to remember, and sensible defaults for the details you don't care about.

{{ANIM2}}

1. Printing and converting: println, valueOf

PrintStream.println has versions for every primitive, char[], String and Object. String.valueOf works the same way. You write one name; the right conversion happens.

Any value→println(…) overloads→Text on screen

2. Optional details with defaults

Logging libraries offer log(message) and log(message, exception). HTTP clients offer get(url) and get(url, headers). The short versions call the long one with default values.

log("Saved")→log(msg, null)→One real implementation

3. Different ways to build an object

Constructors are overloaded constantly: new ArrayList<>(), new ArrayList<>(500), new ArrayList<>(otherList). A booking class might accept a seat number or a seat code.

Different inputs→overloaded constructors→Same kind of object

4. Same operation, different data types

Math.max, Math.abs and Arrays.sort each have versions for int, long, float, double (and more), so each type gets fast code without boxing.

int[] or double[]→Arrays.sort overloads→Type-specific sorting

Examples are simplified. Library designers keep overload sets small and consistent; when two overloads would behave differently, they choose different method names instead.

Riya's bill calculator with overloads

public class Main {
    static int total(int a, int b) {
        return total(a, b, 0);
    }

    static int total(int a, int b, int c) {
        return a + b + c;
    }

    static double total(int a, int b, double discount) {
        return (a + b) * (1 - discount);
    }

    public static void main(String[] args) {
        System.out.println("Tea + Vada: " + total(10, 25));
        System.out.println("Tea + Vada + Samosa: " + total(10, 25, 15));
        System.out.println("With 10% off: " + total(40, 60, 0.10));
    }
}
Tea + Vada: 35 Tea + Vada + Samosa: 50 With 10% off: 90.0
  • total(int a, int b)The short version doesn't repeat the logic: it calls the three-int version with 0.
  • total(int, int, int) vs total(int, int, double)Same count, different type of the third parameter: a valid overload.
  • total(10, 25, 15)15 is an int, so the exact match (int, int, int) wins over widening to double.
  • total(40, 60, 0.10)0.10 is a double, so only the discount version applies. It returns a double: 90.0.

Quick revision

Lesson 5.4 in one screen

  • Overloading = same method name, different parameter lists (number, type or order of types) in one class.
  • Signature = name + parameter types. Return type, parameter names, static and access modifiers don't count.
  • javac chooses at compile time: phase 1 exact/widening → phase 2 boxing → phase 3 varargs; then the most specific method.
  • No single most specific method → reference to … is ambiguous. Same signature twice → already defined.
  • The choice is stored in the bytecode as a descriptor like area:(I)I.
  • Good overloads all do the same job; short versions delegate to the full one.
  • Constructors and main can be overloaded too.

Interview and viva questions

What is method overloading? Give an example from the JDK.

Defining several methods with the same name but different parameter lists in one class. The compiler picks one based on the argument types. System.out.println is the classic example: there are versions for int, long, double, char, boolean, char[], String and Object.

Why can't we overload by return type alone?

Because a call doesn't always use its result (calc(5); is a valid statement), the compiler would have no way to choose. Java therefore defines the signature as name plus parameter types only, and two methods with the same signature are a compile error.

What is the difference between overloading and overriding?

Overloading: same name, different parameters, usually in the same class, chosen by the compiler (static polymorphism). Overriding: a subclass gives a new body for a method with the same signature as in the parent, chosen at run time from the object's actual class (dynamic polymorphism).

In what order does Java try widening, boxing and varargs?

First only exact matches and widening, then boxing/unboxing, and varargs only as the last resort. Within a phase, the most specific method wins. This order keeps old code (written before boxing and varargs existed in Java 5) behaving the same way.

Can static methods be overloaded? Can main be overloaded?

Yes to both. Overloading works for static and instance methods alike. You can write main(int x), but the JVM only starts a program from public static void main(String[] args).

Real-world scenario questions (asked in company interviews)

Interviewers like overloading because it tests whether you know what the compiler does, not just the syntax. Think of your answer first, then open the model answer.

Payments · API designFresher

“Can I add a version that returns a receipt?”

A PaymentService has void pay(int amount, String upiId). A teammate wants a version that returns a Receipt and writes Receipt pay(int amount, String upiId) next to it. It won't compile. Explain and suggest a fix.

The interviewer is checking: do you know that the return type is not part of the signature?

Show a strong answer
  • Both methods have the signature pay(int, String). Return type doesn't count, so javac reports method pay(int,String) is already defined.
  • Either change the existing method to return the Receipt (callers can ignore it), or give the new one a clear name like payAndGetReceipt.
  • Don't “fix” it by swapping parameter order; pay(String, int) compiles but invites mistakes.

Avoid: saying the JVM will choose based on how the result is used.

E-commerce · bug hunt1–3 years

The discount that became an extra item

A cart has total(int a, int b, int extraItem) and total(int a, int b, double discount). A developer meant to give 10% off and wrote total(400, 600, 10). Customers were charged Rs 1010 instead of Rs 900. Why, and how would you prevent it?

The interviewer is checking: do you understand overload resolution and API design risks?

Show a strong answer
  • 10 is an int, so the exact match total(int, int, int) is chosen at compile time: 400 + 600 + 10 = 1010.
  • The overloads do different jobs under one name. Rename them: totalWithExtra and totalWithDiscount, or use a Discount type so the compiler catches mistakes.
  • Add a unit test for the discount path; this bug passes compilation silently.

Avoid: overloads whose meaning changes with the parameter type.

Library · compatibility1–3 years

Adding an overload broke someone's build

Your shared library had send(String userId, Object payload). You added send(String userId, String message). Another team's code send(id, null) still compiles, but now behaves differently. What happened?

The interviewer is checking: do you know that overload choice is fixed at compile time and depends on “most specific”?

Show a strong answer
  • When they recompiled, null fits both, and String is more specific than Object, so javac now picks the new method.
  • Code compiled against the old version keeps calling the old method until it is recompiled, because the descriptor is stored in their class files.
  • Adding overloads to a public API is a compatibility risk; document it, or use a new method name.

Avoid: assuming that adding a method can never change existing behaviour.

Analytics · performance3+ years

Why does Math.max have four versions?

A junior asks why the JDK has max(int,int), max(long,long), max(float,float) and max(double,double) instead of one max(Number, Number). What do you say?

The interviewer is checking: can you connect overloading to boxing costs and type safety?

Show a strong answer
  • Primitive overloads avoid boxing: no Integer objects are created in hot loops, and the result keeps its exact type.
  • Each version uses the right comparison for its type (for doubles, special handling of NaN and −0.0).
  • Callers still write just Math.max(a, b); the compiler picks the fastest matching version.

Avoid: “it's just old code”. It is a deliberate performance and correctness choice.
