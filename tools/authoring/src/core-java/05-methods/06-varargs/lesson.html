How many overloads is enough?

After Lesson 5.4, Riya's bill calculator has total for 2, 3 and 4 items. Then a group orders 7 snacks at once. Writing total with 5, 6 and 7 parameters feels wrong.

Sir, do I really need a new overload for every number of items? No. Write static int total(int... prices). Those three dots mean “zero or more ints”. Call it with 2 prices, 7 prices, or none at all. But how do I loop over them if I don't know how many there are? Inside the method, prices is simply an array. The compiler collects whatever you passed into a new int[]. So you use prices.length and a for-each loop, as in Lesson 4.1.

What are varargs?

Formal definition (write this in exams)

Varargs (variable-arity parameters), introduced in Java 5, let a method accept zero or more arguments of the same type. A varargs parameter is declared as Type... name; it must be the last parameter, and a method can have only one. Inside the method the parameter is an array of that type (Type[]). At each call site the compiler creates an array containing the trailing arguments; an existing array can also be passed directly.

In simple words

“Pass as many values as you like.” Java quietly puts them in an array and hands the method that array.

Words you'll meet in this lesson

VarargsA parameter written Type... name that accepts any number of values.
ArityThe number of arguments a method takes. Varargs methods have “variable arity”.
Fixed parametersThe normal parameters before the varargs one, e.g. String customer in bill(String customer, int... prices).
Implicit arrayThe array javac creates at the call site to hold the arguments.
Empty arrayWhat the method receives when called with no varargs values: length 0, not null.
Phase 3Varargs methods are tried last during overload resolution (Lesson 5.4).

Three ways to call the same method

public class Main {
    static int total(int... prices) {
        int sum = 0;
        for (int p : prices) {
            sum += p;
        }
        System.out.println(prices.length + " item(s): Rs " + sum);
        return sum;
    }

    public static void main(String[] args) {
        total();                          // no arguments → empty array
        total(40);                        // one
        total(10, 25, 15, 30);            // four
        int[] saved = {120, 80};
        total(saved);                     // an array you already have
    }
}

Pitfall with null: total((int[]) null) passes a null array, and the for-each loop throws NullPointerException. A call with no arguments gives an empty array, never null, but a caller can still pass null explicitly. Public APIs often check for it.

What javac does with a varargs call

  1. You declare the parameter with three dots

    static String bill(String customer, int... prices)
    In the class file this is just bill(String, int[]). The descriptor is (Ljava/lang/String;[I)Ljava/lang/String;, plus a flag that marks the method as varargs.

  2. You call it with loose values

    bill("Kabir", 10, 25, 15);
    The first argument fills the fixed parameter customer. All the remaining ones belong to the varargs parameter.

  3. javac rewrites the call to build an array

    bill("Kabir", new int[]{10, 25, 15});
    A new int[3] object is created on the heap at every call. For a call with no extra values, javac creates new int[0].

  4. The method works with the array

    for (int p : prices) sum += p;      // prices.length is 3
    Nothing special happens at run time: the JVM sees an ordinary method receiving an ordinary array reference.

  5. Overloads: varargs comes last

    static void log(String msg)            { … }   // chosen for log("x")
static void log(String msg, Object... d) { … }   // only when extra values are passed
    During overload resolution, varargs methods are considered only in phase 3, after exact matches, widening and boxing. That's why libraries can add fast fixed-arity versions next to a varargs one.

From loose values to an array

Left: the calls you write. Right: the array javac creates for each call and what the method sees.

bill(String customer, int... prices) 6 steps
What you see
  1. The call has four arguments. The first one, a String, matches the fixed parameter customer; the other three belong to prices.
  2. The method loops over the prices and prints a total of 50.
  3. With a single price, the loop runs once.
  4. With no prices, prices.length is 0 and the loop doesn't run: total 0. No special code is needed.
  5. If you already have an int[], pass it directly. javac doesn't wrap it in another array.
  6. Arguments are matched left to right, so the String must come first, exactly as declared. This doesn't compile.
Behind the screen
  1. javac sees that bill is a varargs method and rewrites the call: the three loose ints become new int[]{10, 25, 15}.
  2. At run time, the JVM creates array #1 on the heap. In the bill frame, prices holds a reference to it.
  3. Every call builds its own array, here a one-element array #2. (In very hot loops that small allocation is why some APIs add fixed-arity overloads.)
  4. With no values, javac writes new int[0]. The parameter is never null for such a call.
  5. An existing int[] matches the parameter type directly. No copy is made: changes to prices[0] inside the method would change saved too.
  6. Arguments are matched to parameters in order. An int can't fill the String parameter, so no method fits and compilation fails.

Where varargs make APIs pleasant

Most programmers use varargs every day without noticing, through formatting, logging and collection helpers.

{{ANIM2}}

1. Formatting text: String.format and printf

String.format(String format, Object... args) takes any number of values to fill the placeholders: receipts, SMS templates, report lines.

Template + values→format(fmt, Object... args)→Finished message

2. Logging with placeholders

Logging libraries such as SLF4J offer log.info("Order {} paid by {}", id, user), with a varargs version for any number of values, and fixed one- and two-value versions for speed.

Message + details→info(String, Object...)→Log line

3. Building small collections quickly

List.of("Tea", "Vada"), Set.of(...), Arrays.asList(...) and EnumSet.of(...) accept a few values directly. List.of has fixed versions for up to 10 elements and a varargs version for more.

A few values→List.of(E... elements)→Unmodifiable list

4. Utility methods in your own code

Helpers like maxOf(int first, int... rest), joinPath(String... parts) or hasAnyRole(String... roles) read naturally at the call site.

hasAnyRole("ADMIN", "OPS")→String... roles→true / false

Examples are simplified. Varargs create a small array on every call, so performance-critical libraries often add fixed-arity overloads for the common cases.

Interview and viva questions

What are varargs and how do they work internally?

A varargs parameter (Type... name) lets callers pass any number of arguments of that type. The compiler collects them into a new array at the call site and passes the array; inside the method the parameter is an ordinary array. In the class file the parameter type is Type[] and the method carries a varargs flag.

Why must varargs be the last parameter?

So the compiler can tell where the fixed arguments end: every argument after the fixed ones belongs to the varargs array. With a parameter after it, the boundary would be unclear, and allowing two varargs parameters would make it impossible.

What is the difference between f(int... a) and f(int[] a)?

Inside the method there is no difference. At the call site, f(int... a) also accepts loose values like f(1, 2, 3) and no values at all, while f(int[] a) requires an actual array argument.

Why does List.of have overloads for 0 to 10 elements as well as a varargs version?

Performance. Each varargs call allocates an array; fixed-arity overloads avoid that allocation for the common small cases, and the varargs version handles the rest.

What is @SafeVarargs?

An annotation for methods with a generic varargs parameter such as T... items. Generic arrays can cause “heap pollution” warnings; the annotation tells the compiler the method doesn't misuse the array. You'll meet it again with generics (Lesson 11.2).

Real-world scenario questions (asked in company interviews)

Varargs questions check whether you know what the three dots really compile to. Think of your answer first.

Platform · logging1–3 years

Why does the logger have info(String, Object) and info(String, Object...)?

You notice a logging API offers info(String msg, Object arg), info(String msg, Object a, Object b) and info(String msg, Object... args). Isn't the varargs one enough?

The interviewer is checking: do you know that each varargs call allocates an array?

Show a strong answer
  • Functionally yes, but every varargs call creates a new Object[], even when the log level is turned off and nothing is printed.
  • Logging is called millions of times; the fixed one- and two-argument versions avoid that garbage for the most common cases.
  • Overload resolution prefers fixed arity (phase 1) over varargs (phase 3), so callers get the fast version automatically.

Avoid: “varargs are free”. They are convenient, not free.

Fintech · API designFresher

max() of nothing

A teammate wrote static int max(int... values). Someone called max() and got ArrayIndexOutOfBoundsException from values[0]. How would you design it so the mistake can't happen?

The interviewer is checking: can you use the type system instead of run-time checks?

Show a strong answer
  • Change the signature to max(int first, int... rest). Now max() doesn't compile.
  • Start with first and loop over rest; the empty-array case needs no special code.
  • If the signature must stay, check values.length == 0 and throw IllegalArgumentException with a clear message.

Avoid: returning 0 for an empty list; it hides the bug.

E-commerce · bug hunt1–3 years

The discount that changed the saved cart

A method applyCoupon(int... prices) lowers prices[0] and returns the total. It was called with a cart's saved int[], and afterwards the cart itself showed the discounted price even though the order was cancelled. Explain.

The interviewer is checking: do you know that passing an array to varargs passes the same object?

Show a strong answer
  • An existing array is passed directly, not copied, so the method changed the cart's own array.
  • Fix: don't modify the parameter; work on a copy (prices.clone()) or compute the total without writing to the array.
  • Called with loose values, the bug would never show, because javac creates a fresh array each time. That's why it slipped through testing.

Avoid: assuming varargs always give the method its own private array.

Code reviewFresher

Varargs or a List parameter?

A method notifyUsers(String... userIds) is called from one place, with a list of 50,000 IDs loaded from the database: notifyUsers(ids.toArray(new String[0])). Is varargs the right choice here?

The interviewer is checking: do you know when varargs help and when they don't?

Show a strong answer
  • Varargs shine when callers type a few values by hand. Here the data is already a collection, so the conversion to an array is extra work and noise.
  • A List<String> (or Collection<String>) parameter states the intent better and avoids copying 50,000 references.
  • If both styles are needed, offer both, with the varargs version calling the List version via List.of(ids).

Avoid: using varargs everywhere just because it looks flexible.
