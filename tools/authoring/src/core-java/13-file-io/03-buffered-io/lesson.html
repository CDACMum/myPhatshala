The export that took four minutes

The canteen now has a year of orders: about 2 lakh lines. Riya's export writes them straight to a FileOutputStream, a few bytes at a time. It takes minutes. Worse, one night the last few hundred orders are simply missing from the file.

Sir, why is writing a file so slow? My laptop has an SSD! The disk isn't the slow part. Every little write is a request to the operating system, and you're making two lakh of them. Put a buffer in between: collect 8 KB in memory, then send it in one go. And the missing orders at the end? Those were still sitting in a buffer when your program stopped. A buffer must be flushed, and close() does that. Let's see both.

What is buffered I/O?

Formal definition (write this in exams)

Buffered I/O places an in-memory array (a buffer) between a program and an underlying stream, so that many small read or write operations are served from or collected in memory and transferred to the underlying stream in large blocks, reducing costly system calls. In Java, BufferedReader and BufferedWriter wrap any Reader or Writer (default buffer 8,192 characters), and BufferedInputStream and BufferedOutputStream wrap byte streams. BufferedReader.readLine() returns the next line without its terminator, or null at end of stream. Output buffers are written when full, on flush(), or on close().

In simple words

Don't run to the post office with every letter. Fill a bag, then go once. But remember to actually take the bag before you leave.

The data that wasn't there

{{CODE_LOST}} Unclosed buffered writers lose data. Nothing is wrong with the code until the very end: the text sits in memory and the file stays empty. If the program crashes or exits first, it's gone. Use try-with-resources every time, and call flush() if another program must see the data before you close.

Inside the readLine() loop

  1. Wrap the reader

    try (BufferedReader br = Files.newBufferedReader(Path.of("orders.txt"))) {
    A decoder reader on the file, wrapped by a BufferedReader with an empty char[8192].

  2. First readLine(): fill

        String line;
    while ((line = br.readLine()) != null) {
    The buffer is empty, so the reader asks the file for up to 8,192 characters in one call.

  3. Cut out one line

    It scans forward from pos to the next \n (or \r\n), creates a String from those characters, and moves pos past the line break.

  4. Next calls: from memory

    Following lines come straight from the array until it runs out; then one more big read refills it.

  5. End

    When the file has no more data, readLine() returns null, the loop ends, and try-with-resources closes the reader and the file.

Quick revision

Lesson 13.3 in one screen

  • A buffer collects data in memory so the OS is called once per block, not once per character.
  • Wrap: new BufferedReader(reader), new BufferedWriter(writer), or use Files.newBufferedReader/Writer.
  • Loop: while ((line = br.readLine()) != null); lines come without the line break.
  • newLine() writes the platform separator.
  • Buffered output is only on disk after flush() or close(); use try-with-resources.
  • Closing the outer wrapper closes the inner streams too.
  • Process big files line by line: memory stays constant.

Interview and viva questions

Why is BufferedReader faster than FileReader?

Every FileReader.read() call goes through the charset decoder and its locking for a single character. BufferedReader pulls 8,192 characters at once into its own array and serves later reads with plain array access. With raw byte streams such as FileInputStream, where each read() is a system call, the difference is even larger. BufferedReader also adds readLine().

What is the difference between flush() and close()?

flush() writes out buffered data but keeps the stream open for more writes. close() flushes and then releases the stream and its underlying resources; the stream can't be used afterwards.

BufferedReader vs Scanner?

BufferedReader reads lines of text quickly with a large buffer and does no parsing. Scanner parses tokens (ints, words) with regular expressions, which is convenient but slower, and has a smaller buffer. For large inputs, read lines with BufferedReader and parse them yourself.

What design pattern do Java I/O wrappers use?

The decorator pattern: a BufferedReader is a Reader and wraps a Reader, adding buffering without changing the interface. You can stack decorators, e.g. a BufferedReader over an InputStreamReader over a FileInputStream.

When must you call flush() explicitly?

When someone else must see the data before you close: e.g. sending a message over a socket and waiting for a reply, or writing a progress file that another program monitors. Otherwise, closing (via try-with-resources) is enough.

Real-world scenario questions (asked in company interviews)

These come up whenever a role involves batch jobs, reports or integrations.

Batch · data lossFresher

The last 300 rows are missing

An export writes 50,000 rows with a BufferedWriter. The file always ends a few hundred rows short, and the last row is cut in half. The code calls System.exit(0) right after the loop. Explain.

The interviewer is checking: buffers and flushing.

Show a strong answer
  • The writer is never closed, so the final partly-filled buffer (up to 8 KB) never reaches the file; System.exit doesn't flush it.
  • Wrap the writer in try-with-resources (or close it in finally) before exiting.

Avoid: adding flush() after every row; that removes the benefit of buffering.

Performance · I/OJunior

A 10-minute report that should take seconds

Profiling shows a report spends 95% of its time inside FileOutputStream.write, called once per character. How do you fix it with minimal code change?

The interviewer is checking: recognising unbuffered I/O.

Show a strong answer
  • Each call is a system call. Wrap the stream: new BufferedOutputStream(new FileOutputStream(f)), or use Files.newBufferedWriter for text.
  • Optionally use a larger buffer (64 KB) for very large outputs, and write whole strings rather than single characters.

Avoid: rewriting the report in multiple threads first; the bottleneck is the call pattern.

Integration · socketsJunior

The partner server never answers

A client sends a request line to a payment partner over a socket with a BufferedWriter, then waits for the reply with readLine(). It hangs forever, though the partner says it never received anything. Why?

The interviewer is checking: when explicit flush is needed.

Show a strong answer
  • The request is still in the client's buffer; it's never sent because the writer wasn't flushed. Both sides wait for each other.
  • Call writer.flush() after writing a complete request, before reading the reply.
  • Also set read timeouts so a missing reply can't hang the client forever.

Avoid: closing the writer to force sending; closing the socket stream closes the connection.

Data · line endingsMid

Files from Windows have an extra character

A Linux job reads a CSV uploaded from a Windows machine with Files.readString, splits the text on "\n", then parses the last column of each row. It fails with NumberFormatException: For input string: "450\r". Why, and how should it read the file?

The interviewer is checking: line terminators and defensive parsing.

Show a strong answer
  • Windows ends lines with \r\n. Splitting on "\n" leaves the \r at the end of every row.
  • readLine() (and lines()) treat \n, \r and \r\n all as line ends and strip them, so use those instead of splitting by hand.
  • Read with readLine (or lines()), trim() fields before parsing, and watch for a UTF-8 BOM at the start of files from Excel.

Avoid: assuming every file uses your OS's line endings.
