The cart that vanished

Riya's canteen app lets students build a cart before paying. If the app closes, the cart disappears and students have to add everything again. She could write each item as text, but the cart has items, quantities, a coupon and the student's details, all objects pointing to objects.

Sir, can't I just save the whole cart object as it is? You can. Mark the class Serializable and an ObjectOutputStream will flatten the cart and everything it points to into bytes. And the student's UPI PIN that's stored in there? That must never reach a file. Mark it transient. Let's see exactly what gets written.

What are serialization and deserialization?

Formal definition (write this in exams)

Serialization is the process of converting an object's state, together with the objects it references (its object graph), into a sequence of bytes that can be stored or transmitted. Deserialization reconstructs new objects with the same state from those bytes. In Java, a class opts in by implementing the marker interface java.io.Serializable; objects are written with ObjectOutputStream.writeObject() and read with ObjectInputStream.readObject(). Fields declared transient and static fields are not serialized. A serialVersionUID identifies the version of the class and is checked during deserialization; a mismatch causes InvalidClassException.

In simple words

Serialization packs an object flat into a box of bytes. Deserialization unpacks the box and builds an identical object, a twin, not the original.

What writeObject and readObject do

  1. Open an object stream

    ObjectOutputStream out = new ObjectOutputStream(new FileOutputStream("cart.ser"));
    It wraps a byte stream and immediately writes the header AC ED 00 05.

  2. writeObject(cart)

    It checks the class implements Serializable, writes a class description (name, serialVersionUID, field names and types), then the values of each non-transient, non-static field.

  3. Follow references

    For each reference field it serializes the referenced object the same way, recursively. Objects already written in this stream are stored as a short back-reference, so cycles and shared objects work.

  4. readObject()

    Cart cart = (Cart) in.readObject();
    It reads the class description, checks the UID, allocates a new object without calling its constructor, and sets the fields from the stream. Transient fields keep default values.

  5. Cast and use

    readObject returns Object; you cast it. It throws ClassNotFoundException if the class isn't available, and InvalidClassException if the versions don't match.

Where serialization is used

Java serialization still appears in caches, sessions and older systems, and the same idea, turning objects into bytes, is everywhere in modern formats such as JSON and Protocol Buffers.

{{ANIM2}}

1. Web sessions across servers

Some servers serialize HTTP session objects (logged-in user, cart) to share them across machines or survive restarts.

session→serialize→other server

2. Caches

Distributed caches store objects as bytes; Java serialization or a faster format turns them into bytes and back.

product object→bytes→cache server

3. Saving app state

Games, desktop tools and mobile apps save progress and drafts so users can continue later.

quit game→writeObject(progress)→save.dat

4. APIs (with JSON)

REST APIs serialize Java objects to JSON text and deserialize requests back into objects: the same idea in a portable, safer format.

Order object→Jackson→JSON response

Simplified. New systems usually prefer JSON or Protocol Buffers over Java's built-in serialization, mainly for safety and compatibility with other languages.

Interview and viva questions

What is serialization, and why is Serializable a marker interface?

Serialization converts an object's state into bytes for storage or transfer. Serializable has no methods: it only marks a class as permitted, so classes don't get serialized (and their internals exposed) by accident.

What is the use of the transient keyword?

It excludes a field from serialization. Use it for secrets (passwords, PINs), derived or cached values that can be recomputed, and fields whose types aren't serializable (threads, streams, connections). After deserialization the field has its default value.

What is serialVersionUID and what happens if you don't declare it?

It's a version number stored in the stream and checked when reading. If you don't declare one, Java computes it from the class's structure, so small changes (adding a method or field) change it and old files can no longer be read (InvalidClassException). Declaring it explicitly keeps compatible changes working.

Is the constructor called during deserialization?

Not for the serializable class or its serializable superclasses. The JVM calls only the no-arg constructor of the first non-serializable superclass (often Object), then restores fields from the stream. Validation in constructors is therefore bypassed.

What are the risks of Java serialization?

Deserializing untrusted data can instantiate unexpected classes and trigger “gadget chains” leading to remote code execution. It's also Java-only, fragile across class changes, and exposes private fields in the bytes. Mitigate with ObjectInputFilter allow-lists, or use JSON/Protocol Buffers with validation.

Real-world scenario questions (asked in company interviews)

Serialization questions test both mechanics and judgement: when to use it, and when not to.

Release · compatibilityJunior

After the update, saved carts won't load

A desktop billing app saves open bills with Java serialization. After a release that added one field to Bill, every saved bill fails with InvalidClassException: local class incompatible. What happened, and how do you prevent it?

The interviewer is checking: serialVersionUID.

Show a strong answer
  • Bill had no declared serialVersionUID, so Java computed one; adding a field changed it and old streams no longer match.
  • Declare private static final long serialVersionUID from the first release. Adding a field is then a compatible change: old data loads with the new field at its default.
  • For this release, re-add the old computed UID (find it with the serialver tool) to recover existing files.

Avoid: telling users to delete their saved bills.

Security · data leakFresher

Card numbers found in session files

A security audit finds full card numbers inside the server's serialized session files on disk. The session object holds a PaymentInfo field. What would you change?

The interviewer is checking: transient and handling sensitive data.

Show a strong answer
  • Serialization writes every non-transient field in plain bytes; there's no encryption.
  • Don't keep card data in the session at all: store a token from the payment gateway. If a field must exist, mark it transient.
  • Encrypt session storage and restrict file permissions.

Avoid: making the field private and assuming that hides it; private fields are serialized too.

Security · attackMid

An endpoint that accepts serialized objects

An internal API receives orders as Java-serialized objects in the HTTP body and calls readObject(). The team wants to expose it to partners. What's your advice?

The interviewer is checking: deserialization vulnerabilities.

Show a strong answer
  • Deserializing attacker-controlled bytes can instantiate arbitrary classes from the classpath and lead to remote code execution.
  • Switch the API to JSON with a strict schema and validation; it's also language-neutral for partners.
  • If Java serialization must stay, apply an ObjectInputFilter allow-list of expected classes, size limits, and authentication.

Avoid: “we only accept our Order class”. The cast happens after readObject has already built the objects.

Design · graphsMid

Serialized files are huge and slow

A Customer object is cached by serializing it, but each file is several MB. Investigation shows Customer has a reference to a shared CatalogService that holds the entire product catalogue. Explain and fix.

The interviewer is checking: object graphs and transient.

Show a strong answer
  • Serialization follows every reference, so the whole catalogue is written with each customer.
  • Mark service references transient and re-inject them after loading, or serialize a small DTO with only the customer's data.

Avoid: compressing the files and ignoring the design problem.
