Sixteen pigeonholes in the staff room

Arjun Sir's staff room has a wall of 16 pigeonholes for letters. A clerk doesn't search all 16: she takes the teacher's name, does a quick calculation that always gives the same answer for the same name, and drops the letter straight into that hole. When two teachers' names give the same hole, both letters sit there, and she checks the names when someone collects.

Sir, that's exactly what the canteen app needs. Prices by dish name, instantly. And it's exactly what a HashMap does. The “quick calculation” is the key's hashCode(). The pigeonholes are an array of buckets. When two keys share a bucket, the entries are chained and equals() picks the right one. What if the canteen grows to 500 dishes? Sixteen holes would be stuffed. Then the map does what the clerk would: when it's 75% full, it builds a wall with twice as many holes and re-sorts the letters. Let's watch every step happen in a real JVM.

What is a HashMap?

Formal definition (write this in exams)

java.util.HashMap<K,V> is a hash-table based implementation of the Map interface that stores key–value pairs with unique keys. It permits one null key and any number of null values, makes no guarantee about iteration order, and is not synchronised. Internally it keeps an array of buckets (table); a key's bucket index is computed from its hashCode() (spread by hash()) as (n − 1) & hash. Entries in the same bucket form a linked list, converted to a balanced tree when a bucket grows large. When the number of entries exceeds capacity × load factor (default 16 × 0.75 = 12), the table doubles and entries are redistributed. Average time for get and put is O(1).

In simple words

A dictionary: give it a key, get the value. Speed comes from computing where the key lives instead of searching for it.

Exam tip: the steps of put(k, v): (1) hash(k), (2) index = (n − 1) & hash, (3) empty bucket → new node; otherwise walk the chain comparing hash and equals: same key → replace the value (and return the old one), else append a node, (4) if ++size > threshold → resize to double capacity. Everyday operations

import java.util.HashMap;
import java.util.Map;

public class Main {
    public static void main(String[] args) {
        Map<String, Integer> price = new HashMap<>();
        System.out.println(price.put("chai", 15));      // null: no old value
        System.out.println(price.put("chai", 20));      // 15: old value replaced
        price.put("dosa", 60);
        price.putIfAbsent("dosa", 99);                   // ignored: key exists

        System.out.println(price.get("chai") + " " + price.get("tea"));
        System.out.println(price.getOrDefault("tea", 0) + " " + price.containsKey("dosa"));

        Map<String, Integer> sold = new HashMap<>();
        for (String d : new String[]{"chai", "dosa", "chai"}) {
            sold.merge(d, 1, Integer::sum);              // count: start at 1 or add 1
        }
        for (Map.Entry<String, Integer> e : sold.entrySet()) {
            System.out.println(e.getKey() + " sold " + e.getValue());
        }
    }
}
null 15 20 null 0 true chai sold 2 dosa sold 1

merge and Integer::sum use a method reference (Lesson 14.1); read it as “if the key is new, store 1, otherwise add 1 to the old value”.

Collisions are normal

public class Main {
    public static void main(String[] args) {
        // different keys, same hash code: a true collision
        System.out.println("Aa".hashCode() + " " + "BB".hashCode());
        // different hash codes, same bucket in a 16-bucket table
        System.out.println(index("idli", 16) + " " + index("samosa", 16));
        System.out.println(index("idli", 32) + " " + index("samosa", 32));   // after doubling
    }

    static int index(String key, int buckets) {
        int h = key.hashCode();
        int hash = h ^ (h >>> 16);           // HashMap.hash(): mix high bits into low bits
        return (buckets - 1) & hash;          // same as hash % buckets for powers of two
    }
}
2112 2112 9 9 9 25

With 16 buckets, “idli” and “samosa” share bucket 9. When the table grows to 32, one more bit of the hash is used and they separate: idli stays at 9, samosa moves to 9 + 16 = 25.

The mutable-key bug

import java.util.*;

public class Main {
    public static void main(String[] args) {
        List<Integer> seat = new ArrayList<>(List.of(4, 32));   // coach 4, seat 32
        Map<List<Integer>, String> booked = new HashMap<>();
        booked.put(seat, "Riya");

        seat.set(1, 33);                     // key changed after being stored!
        System.out.println(booked.get(seat) + " " + booked.get(List.of(4, 32)) + " " + booked.size());
    }
}
null null 1
Keys must not change while in a map. The entry sits in the bucket chosen by the old hash. After the change, the new hash points to another bucket, and the old key no longer equals anything you can build. The entry is stuck: size 1, but unreachable. Use immutable keys: String, Integer, enums, records. Rule of thumb: HashMap for lookups; LinkedHashMap when output should follow insertion order; TreeMap when keys must be sorted or you need floorKey/ceilingKey; ConcurrentHashMap when several threads write. If you know the size, pre-size it: new HashMap<>(expected * 4 / 3 + 1), or HashMap.newHashMap(expected) on Java 19+.

Inside put("samosa", 20)

  1. Compute the hash

    int h = key.hashCode();          // "samosa" → -909675842
int hash = h ^ (h >>> 16);       // spread the high bits down
    Only the low bits pick the bucket, so hash() mixes the top 16 bits into the bottom 16. That way keys that differ only in high bits don't all collide.

  2. Find the bucket

    index = (n − 1) & hash. With n = 16, n − 1 is binary 1111, so this keeps the last 4 bits: a number from 0 to 15. Faster than %, and the reason capacity is always a power of two.

  3. Bucket occupied? Walk the chain

    Bucket 9 already holds “idli”. For each node, the map compares the stored hash first (cheap) and then equals. “idli” ≠ “samosa”, so it keeps walking. If an equal key were found, its value would be replaced and the old value returned.

  4. Append a new node

    A Node{hash, "samosa", 20, next=null} is linked after “idli”. If this chain reached 8 nodes, the bucket would be converted to a red-black tree (or the table resized, if it has fewer than 64 buckets).

  5. Check the threshold

    ++size > threshold? With capacity 16 the threshold is 12, so the 13th entry triggers resize(): a new table of 32, and every node moves either to the same index or to index + 16, depending on one extra hash bit. No full rehash of keys is needed.

HashMap in real systems

Hash maps are the workhorse of backend code: caches, indexes, counters and lookups.

{{ANIM2}}

1. Sessions and caches

Web servers map session IDs to logged-in users; services cache exchange rates, product details and config by key to avoid slow database calls.

request cookie→sessions.get(id)→user, in O(1)

2. Counting and grouping

Orders per city, errors per type, votes per candidate: merge(key, 1, Integer::sum) or computeIfAbsent(key, k -> new ArrayList<>()).add(item) for grouping.

event→counts.merge(type, 1, Integer::sum)→dashboard

3. Joining data in memory

To combine orders with customers, load customers into a map by ID once, then look each order's customer up in O(1), instead of a nested loop.

10k customers → map→byId.get(order.custId)→enriched orders

4. Hash flooding and bad hash codes

Attackers once sent web servers thousands of parameters with colliding hash codes to slow them down. Java 8's treeified buckets cap the damage at O(log n). A home-made hashCode() that returns a constant causes the same slowdown by accident.

bad hashCode→every key in one bucket→O(1) becomes slow

Examples are simplified. Shared caches across servers use stores like Redis; inside one JVM with many threads, ConcurrentHashMap.

Canteen billing with a price map and a sales counter

import java.util.*;

public class Main {
    public static void main(String[] args) {
        Map<String, Integer> price = new HashMap<>();
        price.put("chai", 15);
        price.put("idli", 30);
        price.put("samosa", 20);
        price.put("dosa", 60);

        String[] orders = {"chai", "idli", "chai", "pav", "samosa", "chai"};
        Map<String, Integer> sold = new TreeMap<>();     // sorted report
        int bill = 0;
        List<String> unknown = new ArrayList<>();

        for (String item : orders) {
            Integer p = price.get(item);
            if (p == null) {
                unknown.add(item);
                continue;
            }
            bill += p;
            sold.merge(item, 1, Integer::sum);
        }

        System.out.println("Sold: " + sold);
        System.out.println("Bill: ₹" + bill + ", not on menu: " + unknown);
        for (Map.Entry<String, Integer> e : sold.entrySet()) {
            System.out.println(e.getKey() + " → ₹" + e.getValue() * price.get(e.getKey()));
        }
    }
}
Sold: {chai=3, idli=1, samosa=1} Bill: ₹95, not on menu: [pav] chai → ₹45 idli → ₹30 samosa → ₹20
  • price.get(item)O(1) lookup; returns null for an unknown dish, so the result is kept as Integer.
  • sold.merge(item, 1, Integer::sum)First time: puts 1. Later: adds 1.
  • new TreeMap<>()The report prints dishes alphabetically.
  • entrySet()The efficient way to walk keys and values together.

Lesson 11.6 in one screen

  • HashMap: key → value, unique keys, one null key, unordered, O(1) average.
  • Inside: Node[] table; node = hash, key, value, next.

Interview and viva questions

Explain how HashMap works internally.

It's an array of buckets. put computes the key's hash (hashCode with high bits spread), finds the bucket with (n − 1) & hash, and either inserts a new node, or walks the bucket's chain comparing hash and equals to replace an existing key's value or append a node. When size exceeds capacity × 0.75, the table doubles and nodes are split between index and index + old capacity. Long chains (8+) become red-black trees when the table has at least 64 buckets. get follows the same hash → bucket → equals path.

What happens if hashCode is good but equals is not overridden?

Equal-looking keys may land in the same bucket, but equals (identity) says they differ, so you get duplicates and failed lookups with a new key object. Both methods must be overridden consistently (Lesson 10.3).

Why is the capacity always a power of two?

So the index can be computed with a fast bit mask, (n − 1) & hash, instead of the slower %, and so that on resize each bucket splits cleanly into two (same index or index + old capacity) by checking a single bit.

HashMap vs Hashtable vs ConcurrentHashMap?

HashMap: not thread-safe, allows one null key and null values. Hashtable: legacy, every method synchronised, no nulls. ConcurrentHashMap: thread-safe with fine-grained locking/CAS, high concurrency, no null keys or values. Use ConcurrentHashMap for shared maps.

Why did Java 8 add treeification?

If many keys collide (poor hashCode or a deliberate attack), a chain could grow to thousands of nodes and make get/put O(n). Converting large buckets to red-black trees keeps the worst case at O(log n).

{{PRACTICE}}

Real-world scenario questions (asked in company interviews)

HashMap is the single most asked Java collections topic. Interviewers love scenarios where the internals explain a production bug.

Backend · performanceJunior

A cache that got slower as it grew

A product cache uses HashMap<ProductKey, Product>. Lookups were fast with 1,000 entries but take milliseconds with 100,000. Profiling shows time spent in ProductKey.equals. What's your hypothesis?

The interviewer is checking: the effect of a poor hashCode.

Show a strong answer
  • Most keys probably share a few hash codes (e.g. hashCode uses only a category field, or returns a constant), so buckets hold long chains and each lookup calls equals many times.
  • Check bucket distribution in a test; fix hashCode to use all fields that equals uses (Objects.hash(...)) or make the key a record.
  • Treeification softens it to O(log n) only if keys are Comparable; a good hash is the real fix.

Avoid: increasing the initial capacity. More buckets don't help if every key hashes to the same value.

Railways · bugJunior

A booking that can't be found or removed

Bookings are stored in a HashMap<Seat, Booking>. After a passenger changes coach (the code updates seat.coach), map.get(seat) returns null and map.remove(seat) does nothing, but size() still counts it. Explain.

The interviewer is checking: mutable keys and bucket placement.

Show a strong answer
  • The entry was placed by the old hash. Changing a field used in hashCode changes the hash, so lookups go to a different bucket.
  • Make Seat immutable (final fields, or a record). To change seat: remove(oldSeat), then put(newSeat, booking).
  • Add a test that mutating keys is impossible (no setters).

Avoid: “just iterate the map to find it”. That turns O(1) into O(n) and hides the design flaw.

Platform · concurrencyMid

Lost counts under load

A shared HashMap<String, Integer> counts API calls per client from many request threads with map.put(k, map.getOrDefault(k, 0) + 1). Under load the totals are too low, and once a thread got stuck at 100% CPU. What's happening?

The interviewer is checking: HashMap isn't thread-safe.

Show a strong answer
  • Read-modify-write races lose increments; concurrent resizes can corrupt the table (older JDKs could even form a cycle in a chain, causing infinite loops).
  • Use ConcurrentHashMap with merge(k, 1, Integer::sum), or ConcurrentHashMap<String, LongAdder> for very hot counters.
  • Module 12 covers why races happen.

Avoid: Collections.synchronizedMap with the same get-then-put code; the compound action is still not atomic.

Batch · memoryJunior

Loading 10 lakh customers into a map

A job builds a HashMap of 1,000,000 customers by ID. It's slower than expected and memory spikes during loading. What would you change?

The interviewer is checking: resizing cost and pre-sizing.

Show a strong answer
  • Starting at 16 buckets, the map resizes about 17 times, each time allocating a doubled table and moving every node.
  • Pre-size: capacity ≥ expected / 0.75 (e.g. HashMap.newHashMap(1_000_000) on Java 19+, or new HashMap<>(1_333_334)).
  • Consider primitive-keyed maps from a library if memory is critical, or stream the data instead of holding it all.

Avoid: new HashMap<>(1_000_000) thinking it holds a million without resizing; with load factor 0.75 it still resizes once.
