The ticket checker's finger

On the Panvel local, the ticket checker walks the compartment keeping one finger on the passenger he's checking. When a ticketless passenger is taken off at Kharghar, he removes them and his finger stays in the right place. Kabir, coding the same thing, removed passengers inside a for-each loop. His program crashed.

Sir, Kabir's loop is just a for-each. Where's the iterator? Hidden. javac turns every for-each over a collection into Iterator it = list.iterator(); while (it.hasNext()) { p = it.next(); … }. When Kabir calls list.remove, the list changes without telling that iterator. And the iterator notices? Every list keeps a change counter. The iterator remembers the value it started with and checks it on every next(). If someone else changed the list, it stops immediately rather than return wrong data. Remove through the iterator itself, like the checker's finger, and everything stays consistent.

What are Iterator and ListIterator?

Formal definition (write this in exams)

An Iterator<E> (java.util) is an object that traverses the elements of a collection one at a time, obtained from collection.iterator(). It defines hasNext(), next() and the optional remove(), which removes the last element returned and is the only safe way to modify a collection during iteration. The enhanced for loop uses an iterator for any Iterable. Iterators of most java.util collections are fail-fast: if the collection is structurally modified other than through the iterator, the next operation throws ConcurrentModificationException. A ListIterator<E>, obtained from list.listIterator(), extends Iterator for lists with bidirectional movement (hasPrevious, previous), index queries (nextIndex, previousIndex) and modification at the cursor (set, add).

In simple words

An iterator is a finger moving through a collection. A ListIterator is a finger that can also go backwards and edit the list where it points.

Removing while iterating, the right way

import java.util.*;

public class Main {
    public static void main(String[] args) {
        List<Integer> marks = new ArrayList<>(List.of(78, 32, 91, 28, 64));
        Iterator<Integer> it = marks.iterator();
        while (it.hasNext()) {
            if (it.next() < 35) {
                it.remove();                       // removes the element just returned
            }
        }
        System.out.println(marks);

        List<Integer> copy = new ArrayList<>(List.of(78, 32, 91, 28, 64));
        copy.removeIf(m -> m < 35);               // the same in one line (Lesson 14.1)
        System.out.println(copy);
    }
}
[78, 91, 64] [78, 91, 64]

ListIterator: backwards, set and add

import java.util.*;

public class Main {
    public static void main(String[] args) {
        List<String> route = new ArrayList<>(List.of("Panvel", "Kharghar", "Vashi"));
        ListIterator<String> li = route.listIterator();

        while (li.hasNext()) {
            int i = li.nextIndex();
            String stop = li.next();
            if (stop.equals("Kharghar")) {
                li.set("Kharghar (Fest)");          // replace the element just returned
                li.add("Belapur");                  // insert right after it, at the cursor
            }
            System.out.println(i + ": " + stop);
        }
        System.out.print("Back: ");
        while (li.hasPrevious()) System.out.print(li.previous() + "|");
        System.out.println();
    }
}
0: Panvel 1: Kharghar 3: Vashi Back: Vashi|Belapur|Kharghar (Fest)|Panvel|

Notice two things: “Belapur” wasn't printed in the forward loop, because add inserts before the cursor and the next next() continues with Vashi; and Vashi's index is now 3, because Belapur took index 2.

Making your own class iterable

import java.util.Iterator;

class Countdown implements Iterable<Integer> {
    private final int from;
    Countdown(int from) { this.from = from; }

    public Iterator<Integer> iterator() {
        return new Iterator<>() {                // anonymous class (Lesson 10.5)
            int current = from;
            public boolean hasNext() { return current > 0; }
            public Integer next() { return current--; }
        };
    }
}

public class Main {
    public static void main(String[] args) {
        for (int n : new Countdown(3)) System.out.print(n + " ");
        System.out.println("Launch!");
    }
}

Don't change a collection behind its iterator. list.add or list.remove inside a for-each over the same list throws ConcurrentModificationException (except by luck when removing the second-to-last element, as Lesson 11.3 showed). Use it.remove(), ListIterator.add, removeIf, or collect changes and apply them after the loop. Rule of thumb: for-each for reading; an explicit Iterator when you need to remove; ListIterator when you need to replace, insert or go backwards in a list. For collections shared between threads, use concurrent collections whose iterators don't throw (Module 12).

How fail-fast checking works

  1. The list counts its changes

    ArrayList inherits a field modCount from AbstractList. Every add/remove/clear increments it; set doesn't (no structural change).

  2. The iterator takes a note

    int cursor;                       // index of the next element
int lastRet = -1;                 // index of the last element returned
int expectedModCount = modCount;  // the count when iteration started
    list.iterator() creates an ArrayList.Itr, an inner class (Lesson 10.5) that reads the list's private array through its outer link.

  3. Every next() checks

    next() first calls checkForComodification(): if modCount != expectedModCount, throw ConcurrentModificationException. Otherwise return elementData[cursor], set lastRet = cursor and advance.

  4. it.remove() keeps them in sync

    It removes index lastRet from the list (which bumps modCount), moves cursor back to lastRet, sets lastRet = -1 (so a second remove fails) and updates expectedModCount. No exception.

  5. Best effort, not a guarantee

    Fail-fast checks catch most bugs, but the Java docs warn they're not guaranteed, especially across threads. Treat the exception as a bug detector, never as program logic.

Iterators in real systems

Iterators matter whenever code walks large or changing data, and when you build your own data types.

{{ANIM2}}

1. Cleaning up in place

Background jobs remove expired sessions, cancelled orders or stale cache entries while scanning, using iterator.remove() or removeIf on the collection or a map's entrySet().

scan entries→it.remove()→no CME, no copy

2. Streaming large data

Database result sets, file readers and paged API clients follow the same “has next / get next” idea, so millions of rows can be processed without loading them all.

while (rs.next())→one row at a time→constant memory

3. Custom collections

A Playlist, Route or Portfolio class that implements Iterable works in for-each and hides how it stores its items.

for (Song s : playlist)→playlist.iterator()→internals hidden

4. Listener lists

Event systems keep listeners in a CopyOnWriteArrayList: iterating (firing events) is frequent, changes are rare, and its iterator walks a snapshot, so a listener can unregister itself mid-event without an exception.

fire event→snapshot iteration→safe removal

Examples are simplified. JDBC's ResultSet isn't a java.util.Iterator, but follows the same pattern.

import java.util.*;

public class Main {
    public static void main(String[] args) {
        List<String> coach = new ArrayList<>(List.of("Riya:T", "Kabir:-", "Om:T", "Zoya:-", "Meera:T"));
        List<String> fined = new ArrayList<>();

        Iterator<String> it = coach.iterator();
        while (it.hasNext()) {
            String[] p = it.next().split(":");
            if (p[1].equals("-")) {               // no ticket
                fined.add(p[0]);
                it.remove();                      // safe removal at the cursor

        while (li.hasNext()) {
            String name = li.next().split(":")[0];
            li.set(name + " ✓");                  // mark as checked
        }

        System.out.println("Fined: " + fined);
        System.out.println("Checked: " + coach);
    }
}

Quick revision

Lesson 11.7 in one screen

  • Iterator: hasNext(), next(), remove(). for-each = hidden iterator.
  • Remove while looping: it.remove() (once per next) or removeIf. Never list.remove inside for-each.

  • Implement Iterable to use your class in for-each. Concurrent collections have fail-safe iterators.

Interview and viva questions

What is ConcurrentModificationException and how do you avoid it?

It's thrown by fail-fast iterators when a collection is structurally modified during iteration by anything other than the iterator itself. Avoid it by removing through Iterator.remove(), using removeIf, collecting changes and applying them after the loop, iterating over a copy, or using a concurrent collection. It can happen in a single thread; it's not only a threading issue.

Fail-fast vs fail-safe iterators?

Fail-fast iterators (ArrayList, HashMap…) throw on concurrent modification. Fail-safe (more precisely weakly consistent or snapshot) iterators, as in CopyOnWriteArrayList and ConcurrentHashMap, don't throw: they iterate over a snapshot or tolerate concurrent changes, possibly not reflecting the latest updates.

Iterator vs ListIterator?

Iterator works on any Collection and moves forward only, with remove. ListIterator works on Lists, moves both ways, knows indexes, and can set and add at the cursor.

Iterator vs Enumeration?

Enumeration (hasMoreElements, nextElement) is the legacy interface of Vector and Hashtable. Iterator replaced it with shorter names and a remove method.

How do you remove entries from a HashMap while iterating?

Iterate over map.entrySet().iterator() and call it.remove(), or use map.entrySet().removeIf(e -> …) / map.values().removeIf(…). Calling map.remove(key) inside a for-each over the map throws ConcurrentModificationException.

Real-world scenario questions (asked in company interviews)

Iterator questions are usually ConcurrentModificationException stories. Explain the mechanism, then the fix.

Backend · bugFresher

CME in a single-threaded job

A colleague says “ConcurrentModificationException means two threads are fighting”. But the failing job runs on one thread: it loops over orders and calls orders.remove(o) for cancelled ones. Explain.

The interviewer is checking: what “concurrent” means here.

Show a strong answer
  • “Concurrent” means “during iteration”, not “multi-threaded”. The for-each's hidden iterator saw modCount change because the list was modified directly.
  • Fix: orders.removeIf(Order::isCancelled), or an explicit iterator with it.remove().
  • Add a test with two adjacent cancelled orders to make sure none is skipped.

Avoid: switching to CopyOnWriteArrayList just to silence it in single-threaded code; it copies the whole array on every write.

Caching · mapsJunior

Evicting expired cache entries

A cache is a HashMap<String, Entry>. A cleanup task does for (String k : cache.keySet()) if (expired(k)) cache.remove(k); and crashes. How do you write it correctly?

The interviewer is checking: removing from maps during iteration.

Show a strong answer
  • cache.entrySet().removeIf(e -> e.getValue().isExpired());, or an explicit Iterator<Map.Entry<…>> with it.remove().
  • If other threads read/write the cache, make it a ConcurrentHashMap, whose iterators don't throw and whose removeIf is safe.
  • Consider a cache library with built-in expiry.

Avoid: catching the exception and restarting the loop. It's O(n²) and hides the bug.

Library · API designJunior

Exposing a class's items without exposing the list

A Playlist class stores songs in a private ArrayList. Callers want to loop over songs with for-each, but must not add or remove songs directly. How?

The interviewer is checking: Iterable and encapsulation.

Show a strong answer
  • Make Playlist implements Iterable<Song> and return Collections.unmodifiableList(songs).iterator(), whose remove() throws UnsupportedOperationException.
  • Offer explicit methods (addSong, removeSong) that apply business rules.
  • The internal list can later change type without affecting callers.

Avoid: a getter returning the internal ArrayList. Any caller could clear() it.

Events · concurrencyMid

A listener that unsubscribes itself

An event bus loops over its listeners and calls each one. One listener unsubscribes itself when called, and the bus crashes with ConcurrentModificationException. What are your options?

The interviewer is checking: snapshot iteration and its trade-offs.

Show a strong answer
  • Store listeners in a CopyOnWriteArrayList: iteration walks a snapshot, so unsubscribing during an event is safe. Ideal when events are frequent and subscriptions rare.
  • Alternatively iterate over a copy (new ArrayList<>(listeners)) per event, or queue unsubscriptions and apply them after the loop.
  • Note the semantics: the removed listener may still receive the current event.

Avoid: synchronising the whole loop if listeners can call back into the bus; it risks deadlocks.
