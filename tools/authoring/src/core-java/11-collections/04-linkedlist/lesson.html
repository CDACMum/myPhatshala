Coaches of a train

At the railway yard near Panvel, Riya watches workers add an extra coach to the front of a train. They don't move all 20 coaches; they uncouple the engine, couple the new coach, and couple the engine back. Two links change. That's it.

Sir, an ArrayList would have shifted all 20 coaches to make room at the front. This is just two couplings! That's exactly how a LinkedList works. Each element sits in a node that knows its previous and next node. Adding at either end, or next to a node you're already standing on, is a couple of pointer changes. So LinkedList is always faster? Not at all. To find coach number 15, you have to walk from the engine. An ArrayList jumps there in one step. And every node costs extra memory. Let's see both sides honestly.

What is a LinkedList?

Formal definition (write this in exams)

java.util.LinkedList<E> is a doubly linked list implementation of both the List and Deque interfaces. Each element is stored in a private Node object holding the element and references to the previous and next nodes; the list keeps references to its first and last nodes and its size. Insertion and removal at either end take constant time; access by index takes linear time, traversing from whichever end is closer. It permits duplicates and null, is not synchronised, and its iterators are fail-fast.

In simple words

A chain of small boxes, each pointing both ways. Cheap to add or remove at the ends; slow to jump to the middle.

The Deque methods

import java.util.LinkedList;

public class Main {
    public static void main(String[] args) {
        LinkedList<String> train = new LinkedList<>();
        train.add("S1");
        train.add("S2");
        train.addFirst("ENGINE");             // O(1): new first node
        train.addLast("GUARD");               // O(1): new last node
        System.out.println(train);

        System.out.println(train.getFirst() + " … " + train.getLast());
        train.removeFirst();                  // O(1)
        train.add(1, "PANTRY");               // walks to index 1, then relinks
        System.out.println(train + " size " + train.size());
        System.out.println(train.get(2));     // walks from the nearer end
    }
}

Queue and stack in one class

import java.util.Deque;
import java.util.LinkedList;
import java.util.Queue;

public class Main {
    public static void main(String[] args) {
        Queue<String> tokens = new LinkedList<>();
        tokens.offer("T1");
        tokens.offer("T2");
        System.out.println("Serve " + tokens.poll() + ", next " + tokens.peek());

        Deque<String> undo = new LinkedList<>();
        undo.push("typed A");
        undo.push("typed B");
        System.out.println("Undo " + undo.pop());
    }
}

The trap: index loops over a LinkedList

for (int i = 0; i < list.size(); i++) {
    total += list.get(i);      // each get walks from an end: O(n) → the loop is O(n²)
}
for (int x : list) {
    total += x;                // the iterator just follows next links: O(n) total
}
Never loop over a LinkedList with get(i). With 100,000 elements that's billions of node hops. Use for-each or an iterator, which simply follows the next links. When to choose LinkedList: rarely. For a queue or stack, ArrayDeque is usually faster and uses less memory (the Java docs say so). For a general list, ArrayList. LinkedList shines when you hold an iterator in the middle of a long list and insert or remove there repeatedly, or when you need a List and a Deque in one object.

What addFirst and get do inside

  1. An empty list

    first and last are both null; size is 0. No array, no nodes.

  2. add("S1"): the first node

    A Node{prev=null, item="S1", next=null} is created. Both first and last point to it.

  3. addFirst("ENGINE"): relink, don't shift

    A new node is created with next = the old first node. The old first node's prev is set to the new node, and first moves to it. Three reference writes, whatever the list's length.

  4. get(2): walk

    node(2) checks whether 2 < size/2. If so, it starts at first and follows next twice; otherwise it starts at last and follows prev. Each hop is a memory read, often a cache miss, because nodes are scattered around the heap.

  5. remove a node: unlink

    The neighbours are joined: prev.next = next and next.prev = prev. The removed node is no longer reachable and the garbage collector frees it.

{{ANIM}}

LinkedList and linked structures in real systems

The linked-node idea is everywhere, even when the class used isn't java.util.LinkedList.

{{ANIM2}}

1. Browser and app history

Back and forward navigation is a doubly linked idea: each page knows the previous and next one. Undo/redo stacks in editors work the same way.

Back button→node.prev→previous page

2. LRU caches

LinkedHashMap links its entries in a doubly linked list. In access-order mode it moves a used entry to the end in O(1), so the least-recently-used entry is always first: the basis of many caches.

cache.get(k)→unlink + relink at tail→evict from head

3. Editing a long sequence in place

Text editors, playlist editors and route planners that insert and delete at a cursor position repeatedly benefit from linked structures and a ListIterator parked at the cursor.

cursor here→it.add(x)→O(1) insert

4. A frequent code-review finding

Reviewers often replace LinkedList with ArrayList or ArrayDeque after spotting index loops or measuring memory, a quick win in many services.

LinkedList + get(i)→ArrayList→O(n²) → O(n)

Examples are simplified; real browsers and editors use their own data structures.

A playlist editor with a cursor

import java.util.LinkedList;
import java.util.ListIterator;

public class Main {
    public static void main(String[] args) {
        LinkedList<String> playlist = new LinkedList<>();
        playlist.add("Intro");
        playlist.add("Song A");
        playlist.add("Song B");
        playlist.add("Outro");

        // put an ad after every song, using a cursor (ListIterator)
        ListIterator<String> it = playlist.listIterator();
        while (it.hasNext()) {
            String track = it.next();
            if (track.startsWith("Song")) {
                it.add("Ad");                     // O(1): links a node right here
            }
        }
        playlist.removeLast();                    // O(1)
        playlist.addFirst("Welcome");             // O(1)
        System.out.println(playlist);
        System.out.println("Now playing: " + playlist.getFirst());
    }
}
[Welcome, Intro, Song A, Ad, Song B, Ad] Now playing: Welcome
  • listIterator()A cursor that can move both ways and insert or remove at its position (Lesson 11.7).
  • it.add("Ad")Inserts after the current song by relinking two nodes: no shifting.
  • removeLast() / addFirst()The ends are always O(1) thanks to first and last.
  • No get(i) anywhereThat's how LinkedList should be used.

Check yourself

Quick revision

Lesson 11.4 in one screen

  • LinkedList = doubly linked list of Node{prev, item, next} with first, last, size.
  • Implements List and Deque: get(i), addFirst/addLast, offer/poll, push/pop.
  • O(1): add/remove at either end, and at an iterator's position. O(n): get(i), set(i), contains.
  • Never loop with get(i) (O(n²)); use for-each or an iterator.
  • More memory per element than ArrayList; scattered nodes are slower to walk.
  • Usually prefer ArrayList (lists) and ArrayDeque (queues/stacks).

Interview and viva questions

ArrayList vs LinkedList: when would you use each?

ArrayList for most lists: O(1) random access, compact memory, fast iteration. LinkedList when you insert/remove at the ends or at an iterator's position very often and rarely access by index, or when you need List and Deque behaviour in one object. In practice ArrayList (or ArrayDeque) wins most benchmarks because arrays are cache-friendly.

How does LinkedList.get(index) work?

It calls node(index): if the index is in the first half, it starts at first and follows next; otherwise it starts at last and follows prev. So at most n/2 hops, which is still O(n).

Is inserting in the middle of a LinkedList O(1)?

Only if you already have a reference to the position (an iterator there). add(i, x) by index first walks to position i (O(n)), then relinks (O(1)).

Can LinkedList hold null? Is it thread-safe?

It allows nulls (though using null in a queue makes poll()'s null return ambiguous). It isn't thread-safe; use ConcurrentLinkedQueue/ConcurrentLinkedDeque or a BlockingQueue for concurrent work.

How would you reverse a linked list?

With Collections.reverse(list), or, in the classic interview version with your own singly linked nodes, by walking the list once and flipping each node's next pointer to the previous node, keeping three references: prev, current, next. O(n) time, O(1) extra space.

{{PRACTICE}}

Real-world scenario questions (asked in company interviews)

LinkedList questions in interviews often test whether you can resist the textbook answer and reason about real costs.

Backend · code reviewFresher

“LinkedList because we insert a lot”

A teammate chose LinkedList for a list of 200,000 transactions “because we insert a lot”. Inserts are always at the end, and the screen reads rows by index for paging. What do you say?

The interviewer is checking: matching the data structure to the actual access pattern.

Show a strong answer
  • Appending is O(1) amortised on ArrayList too, so LinkedList brings no benefit for these inserts.
  • Paging uses get(i)/subList, which is O(n) per access on LinkedList but O(1) on ArrayList.
  • LinkedList also costs much more memory per element (a node object each). Switch to ArrayList and measure.

Avoid: “LinkedList is always better for inserts.” Only inserts at the front or at an iterator's position are cheaper.

Ride-hailing · queueJunior

Pending ride requests

A service keeps pending ride requests in a queue: new ones at the back, drivers take from the front, sometimes a request is cancelled from the middle. LinkedList, ArrayDeque or something else?

The interviewer is checking: trade-offs between deque implementations.

Show a strong answer
  • For offer/poll alone, ArrayDeque is the best fit: O(1) and compact.
  • Cancelling from the middle is O(n) in both. If cancellations are frequent, keep a LinkedHashMap<RequestId, Request>: O(1) removal by ID and insertion-order iteration for “oldest first”.
  • If several threads take requests, use a concurrent queue (Module 12).

Avoid: picking LinkedList only because it has remove(Object). It still searches linearly.

Classic DSAFresher

Find the middle in one pass

Given the head of a singly linked list of unknown length, return its middle node in one pass without counting first.

The interviewer is checking: the slow/fast pointer technique.

Show a strong answer
  • Two references start at the head: slow moves one node, fast moves two nodes per step.
  • When fast reaches the end (null or last node), slow is at the middle. O(n) time, O(1) space.
  • The same idea detects cycles (if fast ever meets slow, there's a loop).

Avoid: copying the nodes into an ArrayList. It works, but uses O(n) extra memory and misses the point of the question.

Caching · designMid

Build an LRU cache

Design a cache of fixed capacity where get and put are O(1) and the least-recently-used entry is evicted when full.

The interviewer is checking: combining a hash map with a doubly linked list.

Show a strong answer
  • A HashMap from key to node for O(1) lookup, plus a doubly linked list ordered by recency: move a node to the tail on every access, evict from the head.
  • In Java, LinkedHashMap with accessOrder = true and an overridden removeEldestEntry gives exactly this in a few lines.
  • For multi-threaded use, add locking or use a library cache.

Avoid: a plain list scanned for the oldest entry: O(n) per operation.
