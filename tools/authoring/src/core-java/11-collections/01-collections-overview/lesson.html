The canteen that outgrew its array

Riya's canteen app started with String[] orders = new String[50];. On fest day there were 312 orders, the same customer was counted three times in “unique visitors”, the token queue was served out of order, and finding a dish's price meant looping over two parallel arrays.

Sir, my array overflowed, my visitor count is wrong, and searching prices is slow. Do I need to write my own data structures? No. Java already has them, tested by millions of programs. You have four different jobs here, so you need four different containers: a List for orders, a Set for unique visitors, a Queue for tokens and a Map for prices. Four new things to learn? Four interfaces, each a promise about behaviour, and a few classes that keep those promises in different ways. Learn the promises first; picking the class becomes easy.

What is the Collections Framework?

Formal definition (write this in exams)

The Java Collections Framework (in java.util, since Java 1.2) is a unified architecture for storing and manipulating groups of objects. It consists of interfaces (Collection, List, Set, Queue, Deque, Map and their sorted variants), implementations (such as ArrayList, LinkedList, HashSet, TreeSet, ArrayDeque, PriorityQueue, HashMap, TreeMap) and algorithms (static methods in Collections such as sort, max and frequency). Collections hold object references only, are generic, and (except for legacy classes) grow dynamically.

In simple words

A toolbox of ready-made containers for groups of objects. Each container type promises a behaviour (ordered? duplicates? first-in-first-out? lookup by key?), and you pick the one whose promise fits your job.

The family tree

Iterable
 └─ Collection
     ├─ List      → ArrayList, LinkedList            ordered, index, duplicates OK
     ├─ Set       → HashSet, LinkedHashSet           no duplicates
     │   └─ SortedSet → TreeSet                      sorted, no duplicates
     └─ Queue     → PriorityQueue                    process in order of priority
         └─ Deque → ArrayDeque, LinkedList           add/remove at both ends (queue or stack)

Map (NOT a Collection)  → HashMap, LinkedHashMap      key → value, keys unique
 └─ SortedMap → TreeMap                              keys sorted
Exam tip: Map does not extend Collection; it's a separate hierarchy. And Collection (interface, the root of List/Set/Queue) is not Collections (a utility class with static methods like sort). Both are classic MCQ traps. {{AD}}

Four promises, and which class to pick

List

Ordered by position, duplicates allowed, get(i). Default: ArrayList.

orders, marks, history

Set

No duplicates. HashSet (fast), LinkedHashSet (keeps insertion order), TreeSet (sorted).

unique IDs, tags

Queue / Deque

Process in order. ArrayDeque (FIFO queue or LIFO stack), PriorityQueue (smallest first).

tokens, tasks, undo

Map

Key → value, unique keys. HashMap (fast), LinkedHashMap (insertion order), TreeMap (sorted keys).

prices, counts, caches

The same data in four containers

import java.util.*;

public class Main {
    public static void main(String[] args) {
        String[] visits = {"Riya", "Kabir", "Riya", "Om", "Riya"};

        List<String> log = new ArrayList<>(Arrays.asList(visits));    // keeps everything
        Set<String> unique = new HashSet<>(log);                     // drops repeats
        Set<String> sorted = new TreeSet<>(log);                     // drops repeats, sorts
        Queue<String> line = new ArrayDeque<>(log);                  // first in, first out
        Map<String, Integer> count = new TreeMap<>();
        for (String v : log) count.put(v, count.getOrDefault(v, 0) + 1);

        System.out.println("List : " + log);
        System.out.println("Set  : " + unique.size() + " unique");
        System.out.println("Tree : " + sorted);
        System.out.println("Queue: serve " + line.poll() + ", next " + line.peek());
        System.out.println("Map  : " + count);
    }
}
List : [Riya, Kabir, Riya, Om, Riya] Set : 3 unique Tree : [Kabir, Om, Riya] Queue: serve Riya, next Kabir Map : {Kabir=1, Om=1, Riya=3}

Fixed, unmodifiable and immutable

import java.util.*;

public class Main {
    public static void main(String[] args) {
        List<Integer> fixed = Arrays.asList(1, 2, 3);   // fixed size: set OK, add not
        fixed.set(0, 9);
        System.out.println(fixed);

        List<Integer> frozen = List.of(1, 2, 3);        // Java 9+: fully immutable
        try {
            frozen.add(4);
        } catch (UnsupportedOperationException e) {
            System.out.println("List.of can't change");
        }
        System.out.println(Collections.max(frozen) + " " + Collections.frequency(List.of("a", "b", "a"), "a"));
    }
}
[9, 2, 3] List.of can't change 3 2
Rule of thumb: declare variables with the interface type (List<String> log = new ArrayList<>()). Your code then depends only on the promise, and you can switch to another class later by changing one word.

Picking a collection in four questions

  1. Do I look things up by a key?

    Yes → a Map. Price by dish, student by roll number, count by word. Then choose: any order (HashMap), insertion order (LinkedHashMap), sorted keys (TreeMap).

  2. Must every element be unique?

    Yes → a Set. The set uses equals/hashCode (Lesson 10.3) or compareTo (TreeSet) to spot duplicates.

  3. Do I process items in arrival or priority order?

    Yes → a Queue/Deque. FIFO tokens: ArrayDeque with offer/poll. Undo stack: ArrayDeque with push/pop. Most urgent first: PriorityQueue.

  4. Otherwise: a List

    ArrayList covers most cases: fast reads by index and fast adds at the end. Lesson 11.4 shows when LinkedList is (rarely) better.

  5. Declare the interface, create the class

    Map<String, Integer> price = new HashMap<>();
    The variable's type is the interface; the object is the class. Behind the scenes the variable is just a reference to a HashMap object on the heap, which itself holds references to the key and value objects.

Collections in real systems

Nearly every Java program uses collections; the skill is choosing the one whose promise matches the job.

{{ANIM2}}

1. Shopping carts and feeds: List

A cart, a timeline of posts, a train's list of stations: order matters and repeats are allowed. ArrayList is the usual choice.

add to cart→List.add→shown in order

2. De-duplication and membership: Set

Unique visitors, blocked card numbers, already-processed transaction IDs (so a retried payment isn't charged twice).

txn id→processed.add(id)→false = duplicate, skip

3. Work waiting its turn: Queue

Support tickets, print jobs, messages waiting to be sent, emergency patients by severity (PriorityQueue), and browser back/undo stacks (Deque).

new ticket→queue.offer→agent calls poll()

4. Lookups and caches: Map

IFSC code → branch, user ID → session, product ID → stock. Caches that avoid slow database calls are maps at heart.

IFSC→branches.get(code)→branch details

Examples are simplified. Multi-threaded systems use the concurrent versions (ConcurrentHashMap, BlockingQueue), covered in Module 12.

import java.util.*;

public class Main {
    public static void main(String[] args) {
        Map<String, Integer> price = new HashMap<>();
        price.put("chai", 15);
        price.put("dosa", 60);
        price.put("vada", 25);

        List<String> orders = new ArrayList<>();
        Set<String> customers = new HashSet<>();
        Queue<String> tokens = new ArrayDeque<>();

        String[][] today = {{"Riya", "chai"}, {"Kabir", "dosa"}, {"Riya", "vada"}};
        for (String[] t : today) {
            orders.add(t[1]);
            customers.add(t[0]);
            tokens.offer(t[0] + ":" + t[1]);
        }

        int total = 0;
        for (String dish : orders) total += price.get(dish);

        System.out.println("Orders: " + orders);
        System.out.println("Customers: " + customers.size());
        System.out.println("Serve first: " + tokens.poll());
        System.out.println("Takings: ₹" + total);
    }
}

Quick revision

Lesson 11.1 in one screen

  • Framework = interfaces + implementations + algorithms (Collections class), in java.util.
  • Iterable → Collection → List (ordered, duplicates), Set (unique), Queue/Deque (processing order). Map is separate.
  • Defaults: ArrayList, HashSet, ArrayDeque, HashMap. Sorted: TreeSet, TreeMap. Insertion order: LinkedHashSet, LinkedHashMap. Priority: PriorityQueue.
  • Choose by asking: lookup by key? unique? processing order? else List.
  • Arrays.asList = fixed size; List.of/Map.of = immutable; Collections.unmodifiableList = read-only view.
  • Declare with the interface type; collections hold references only.

Interview and viva questions

Why use collections instead of arrays?

Arrays have a fixed size and no built-in operations for searching, de-duplicating or key lookup. Collections grow automatically, offer rich, tested operations and data structures with known performance, and work through common interfaces so algorithms like sorting work on many of them.

List vs Set vs Map?

A List is an ordered sequence that allows duplicates and access by index. A Set holds unique elements (order depends on the implementation). A Map stores key–value pairs with unique keys and isn't a Collection.

What is the difference between Arrays.asList, List.of and Collections.unmodifiableList?

Arrays.asList is a fixed-size view backed by the array (set allowed, add/remove not). List.of is truly immutable and rejects nulls. Collections.unmodifiableList is a read-only view of another list: if the original changes, the view shows it.

Are the standard collections thread-safe?

No. ArrayList, HashMap and friends are not synchronised. Use java.util.concurrent classes such as ConcurrentHashMap and CopyOnWriteArrayList, or synchronise access yourself (Module 12). Legacy Vector and Hashtable are synchronised but rarely used today.

What is the root interface of the framework?

Collection is the root of List, Set and Queue; it itself extends Iterable, which is what makes the for-each loop work. Map has its own root, Map.

{{PRACTICE}}

Real-world scenario questions (asked in company interviews)

Collection questions in interviews are usually “which one would you use and why?” The best answers name the promise you need, then the class.

Payments · idempotencyFresher

Don't charge twice

A payment service sometimes receives the same request twice because of network retries. Each request has a txnId. Which collection would you use to make sure each transaction is processed once, and how?

The interviewer is checking: using a Set for membership and its add() result.

Show a strong answer
  • A Set<String> of processed IDs. if (!processed.add(txnId)) return "duplicate";: add returns false if the ID was already there, in O(1) on average.
  • In a real multi-server system, keep this state in a shared store (database unique key or a cache), since each server has its own memory, and use a concurrent set within one server.
  • Expire old IDs so the set doesn't grow forever.

Avoid: scanning an ArrayList with contains. It's O(n) per request and gets slower every day.

Healthcare · triageJunior

Emergency room queue

Patients arrive at a hospital emergency desk with a severity from 1 (critical) to 5. Doctors must always see the most critical patient next, and among equals, whoever came first. Which collection?

The interviewer is checking: PriorityQueue and tie-breaking.

Show a strong answer
  • A PriorityQueue<Patient> with a comparator on severity, then arrival time (a counter or timestamp) to break ties, since PriorityQueue alone isn't stable.
  • offer and poll are O(log n); peek shows the next patient.
  • If severity can change while waiting, remove and re-insert the patient.

Avoid: sorting a List after every arrival. It works, but costs O(n log n) each time.

E-commerce · reportsFresher

Category totals in alphabetical order

Finance wants daily sales per product category, printed in alphabetical order of category. Orders arrive in random order. What would you use?

The interviewer is checking: Map for aggregation, TreeMap for sorted keys.

Show a strong answer
  • Map<String, Long> totals = new TreeMap<>(); then totals.merge(category, amount, Long::sum) for each order.
  • The TreeMap keeps categories sorted, so printing it gives the report order directly.
  • If order only matters at the end and data is huge, a HashMap plus one sort at the end is also fine.

Avoid: two parallel lists of names and totals. Keeping them in sync is error-prone.

Platform · API designJunior

A getter that leaks internals

Order.getItems() returns the order's internal ArrayList. Another team calls getItems().clear() and empties real orders. How do you prevent this?

The interviewer is checking: unmodifiable views and defensive copies.

Show a strong answer
  • Return Collections.unmodifiableList(items) (a read-only view) or List.copyOf(items) (an immutable snapshot).
  • Offer intention-revealing methods like addItem/removeItem that enforce business rules.
  • Declare the return type as List, not ArrayList, so you're free to change the implementation.

Avoid: documenting “please don't modify”. Make it impossible instead.
