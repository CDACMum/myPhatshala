One thread per order? The server disagrees

Riya's canteen app goes viral during exam week. Her server creates a new thread for every incoming order. At lunchtime 5,000 orders arrive in a minute, the server runs out of memory, and nobody gets lunch.

Sir, threads were supposed to make it faster! Threads cost memory and switching time. Thousands of them help nobody. Keep a few workers and a queue of orders: each worker finishes an order and takes the next. Do I write that queue and the workers myself? No. Java has it ready: ExecutorService. You submit tasks; it runs them on a pool and gives you a Future for each result.

What are ExecutorService and thread pools?

Formal definition (write this in exams)

An executor separates task submission from task execution. java.util.concurrent.ExecutorService is an executor that manages a thread pool: a set of reusable worker threads that take submitted tasks from a queue and run them. Tasks are Runnable (no result) or Callable<V> (returns a V and may throw checked exceptions). submit() returns a Future<V>, which represents the pending result: get() waits for it, isDone() checks it, and cancel() attempts to stop the task. A pool is ended with shutdown() (finish queued tasks, accept no new ones) or shutdownNow() (interrupt running tasks).

In simple words

A thread pool is a call centre: a fixed team of agents (threads) and a waiting line (queue). You don't hire a new agent for every call. You get a ticket (Future) to collect your answer later.

{{CODE_FACTORIES}} Always shut pools down. Pool threads are normal (non-daemon) threads. Forget shutdown() and your program never exits; in a server, forgetting it on short-lived pools leaks threads until memory runs out. Use try/finally, or in Java 21 a try-with-resources block (ExecutorService is AutoCloseable).

The life of a submitted task

  1. Create the pool

    ExecutorService pool = Executors.newFixedThreadPool(4);
    A ThreadPoolExecutor object with an empty queue. Worker threads are started as the first tasks arrive.

  2. submit()

    Future<Integer> f = pool.submit(() -> fetchPrice("BuyNow"));
    The Callable is wrapped in a FutureTask. If a worker is free (or the pool may start one), it runs; otherwise it joins the queue. submit returns at once.

  3. A worker runs it

    The worker calls call(). The result (or the exception) is stored inside the FutureTask, which becomes done, and any thread waiting in get() is woken.

  4. The worker loops

    Instead of ending, the worker takes the next task from the queue, or waits for one (like the consumer in Lesson 12.5).

  5. shutdown()

    New submissions are rejected with RejectedExecutionException. Queued tasks still run. When the queue is empty, workers exit; awaitTermination lets you wait for that moment.

Pools power every Java server

Web servers, database connection handling, message consumers and schedulers are all built on executors.

{{ANIM2}}

1. Web request handling

Servers like Tomcat keep a pool of request threads (often a couple of hundred). Each request borrows a worker and returns it when the response is sent.

HTTP request→request pool→response

2. Fan-out calls

A product page calls price, stock, reviews and delivery-estimate services at once and combines the answers with Futures or CompletableFuture.

4 services→CompletableFuture.allOf→one page

3. Scheduled jobs

Send EMI reminders every morning, clear expired carts every 10 minutes, refresh exchange rates every hour.

every 10 min→scheduleAtFixedRate→carts cleaned

4. Virtual threads for I/O

Since Java 21, services that mostly wait on databases and APIs can run one cheap virtual thread per request, handling far more concurrent requests with simple blocking code.

10,000 requests→virtual threads→few OS threads

Sizes and timings are illustrative. Frameworks such as Spring configure and manage these executors for you, but they are the same ExecutorService underneath.

Quick revision

Lesson 12.6 in one screen

  • A thread pool = reusable workers + a task queue. Create it with Executors.newFixedThreadPool(n) and friends.
  • submit(Runnable | Callable) returns a Future; execute(Runnable) returns nothing.
  • Callable<V> returns a value and may throw checked exceptions.
  • get() waits; get(t, unit) may throw TimeoutException; failures come as ExecutionException.
  • invokeAll runs a list of Callables and returns Futures in the same order.
  • Always shutdown(); awaitTermination waits; submitting afterwards throws RejectedExecutionException.
  • CompletableFuture chains async steps; Java 21 virtual threads make one-thread-per-task cheap for I/O work.

Interview and viva questions

Why use a thread pool instead of creating threads?

Creating and destroying threads is costly, and unlimited threads exhaust memory and waste CPU on switching. A pool reuses a bounded number of threads, queues extra work, and centralises lifecycle management (shutdown, naming, error handling).

Difference between submit() and execute()?

execute(Runnable) comes from Executor and returns nothing; an exception in the task goes to the thread's uncaught-exception handler. submit() accepts Runnable or Callable and returns a Future; exceptions are captured and rethrown by get() as ExecutionException.

Difference between shutdown() and shutdownNow()?

shutdown() stops accepting tasks but lets queued and running tasks finish. shutdownNow() also interrupts running tasks and returns the list of tasks that never started. Neither waits; use awaitTermination for that.

How do you choose the pool size?

For CPU-bound work, about the number of cores (availableProcessors()). For I/O-bound work, more threads, roughly cores × (1 + wait time / compute time), or virtual threads. Always measure under realistic load.

What is the difference between Future and CompletableFuture?

A Future can only be polled or waited on with get(). A CompletableFuture can also be completed manually and lets you attach callbacks (thenApply, thenCombine, exceptionally) that run when the result arrives, so you can compose async steps without blocking threads.

{{PRACTICE}}

Real-world scenario questions (asked in company interviews)

Executors are where most production concurrency lives, so interviewers probe how you size, protect and shut them down.

Backend · resource leakFresher

Thread count keeps climbing

Each time a report is requested, the code does Executors.newFixedThreadPool(4), submits the work and returns. After a day the service has 20,000 threads and crashes. What's wrong?

The interviewer is checking: pool lifecycle.

Show a strong answer
  • A new pool per request is never shut down, so its 4 threads live forever.
  • Create one shared pool at startup and reuse it; shut it down when the application stops.
  • If a short-lived pool is really needed, close it in finally (or try-with-resources in Java 21).

Avoid: calling System.gc(); live threads are never garbage collected.

Debugging · silent failureJunior

Refunds that silently never happen

Refund tasks are submitted with pool.submit(refundTask) and the Future is ignored. Some refunds never complete and nothing appears in the logs. Why, and how do you fix it?

The interviewer is checking: exception handling with submit().

Show a strong answer
  • submit captures exceptions inside the Future; if nobody calls get(), the failure is swallowed.
  • Catch and log inside the task (with refund id), or keep the Futures and check them, or use CompletableFuture with exceptionally/whenComplete.
  • Add retries and an alert for failed refunds.

Avoid: assuming “no error in the logs” means success.

Performance · sizingMid

Sizing pools for two kinds of work

An 8-core server does image compression (pure CPU) and calls a partner API (mostly waiting, ~200 ms). Both use one pool of 8 threads. API calls queue up and pages are slow. What would you change?

The interviewer is checking: CPU-bound vs I/O-bound sizing and isolation.

Show a strong answer
  • Separate the workloads into two pools, so slow API calls can't starve compression (bulkheading).
  • CPU pool ≈ 8 threads; I/O pool much larger (or virtual threads), since those threads mostly wait.
  • Add timeouts on API calls and bounded queues with a rejection policy.

Avoid: one giant pool of 500 threads for everything; CPU work would thrash.

Release · shutdownMid

Orders lost during deployment

During a deployment, the app is stopped while order-confirmation tasks are still in the executor's queue. Some customers never get confirmations. Design a graceful shutdown.

The interviewer is checking: shutdown(), awaitTermination() and durability.

Show a strong answer
  • On stop: stop taking new requests, call shutdown(), then awaitTermination(30, SECONDS); only then call shutdownNow() and log the tasks it returns.
  • For anything that must not be lost, store it durably first (database or message broker) and process from there, so a restart can resume.

Avoid: relying on an in-memory queue for work that must survive a restart.
