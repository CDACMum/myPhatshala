The likes counter that couldn't count

Riya's canteen app has a “like” button for dishes. In testing, two phones tap Like 100,000 times each. The counter should say 200,000. It says 148,870. Run again: 169,997.

Sir, the code is just likes++. How can Java lose a plus-one? likes++ is three steps: read, add, write. If both threads read the same old value, one write overwrites the other. That's a race condition. So threads sharing data is dangerous? Unprotected sharing is. The fix is to make the read-add-write happen as one indivisible step, one thread at a time. That's what synchronized does.

What are race conditions and synchronization?

Formal definition (write this in exams)

A race condition occurs when the result of a program depends on the timing or interleaving of threads that access shared mutable data, at least one of them writing. The code that accesses such data is a critical section. Synchronization ensures mutual exclusion (only one thread executes a critical section at a time) and visibility (changes made by one thread are seen by others). In Java, every object has an intrinsic lock (monitor); a synchronized method or block acquires that lock on entry and releases it on exit, and a thread that cannot acquire it is BLOCKED.

In simple words

Shared data is a single-person changing room. synchronized is the lock on the door: one person inside at a time, the rest wait in line.

What happens at a synchronized block

  1. A thread reaches the block

    synchronized (account) {
    if (account.balance >= amt) account.balance -= amt;
}
    The JVM runs monitorenter on the account object's monitor.

  2. Lock free? Take it

    If no one owns the monitor, this thread becomes the owner and enters. It also sees every write made by the previous owner before it released the lock.

  3. Lock taken? Wait

    If another thread owns it, this thread joins the monitor's entry set and is BLOCKED. It uses no CPU while waiting.

  4. Leave the block

    monitorexit releases the lock, even if an exception is thrown inside (the compiler adds a hidden finally). All writes made inside become visible to the next owner.

  5. Next in line

    One BLOCKED thread acquires the lock and becomes RUNNABLE. Which one is not guaranteed. The same thread may re-enter a lock it already owns (locks are re-entrant).

Where races cost real money

Race conditions are behind overselling in flash sales, double payouts, duplicate order numbers and corrupted caches.

{{ANIM2}}

1. Balances and wallets

Debit must check and update the balance as one step, or two parallel payments can overdraw it.

2 payments at once→synchronized debit()→never negative

2. Inventory in flash sales

Thousands of buyers hit “Buy” for 100 units. Reservation must be atomic so exactly 100 orders succeed.

10,000 clicks→atomic reserve→100 orders

3. IDs and counters

Order numbers, page views and rate-limit counters use AtomicLong or LongAdder so no two orders get the same number.

new order→ids.incrementAndGet()→unique id

4. Shared caches and config

Concurrent maps (ConcurrentHashMap) and volatile references let many request threads read config and cached data safely while one thread refreshes it.

refresh thread→volatile config→all threads see it

Simplified: real banking systems also rely on database transactions and row locks, because many servers (not just many threads) share the data.

Quick revision

Lesson 12.4 in one screen

  • Race condition: result depends on thread timing; needs shared mutable data and at least one writer.
  • x++ is read-add-write, not atomic. Check-then-act (if (bal >= amt) bal -= amt) is also a race.
  • synchronized = mutual exclusion + visibility, using an object's monitor. Instance method → this; static → Class.
  • Threads must lock the same object to exclude each other.
  • volatile = visibility only. Atomic classes = lock-free safe updates of one variable.
  • Deadlock: circular wait for locks. Prevent with a fixed lock order and short critical sections.
  • Locks are re-entrant and released even when an exception is thrown.

Interview and viva questions

What is a race condition? Give an example.

A bug where the outcome depends on the interleaving of threads accessing shared mutable data. Example: two threads run count++ on a shared int; both read the same value and one increment is lost. Another: two withdrawals both pass a balance check before either debits.

Difference between a synchronized method and a synchronized block?

A synchronized method locks the whole method on this (or the Class for static methods). A block locks only its statements, on any object you choose. Blocks keep critical sections smaller and let you use private lock objects that outside code can't interfere with.

What is the difference between volatile and synchronized?

volatile ensures reads and writes of one variable go to main memory and aren't reordered, giving visibility. It doesn't make compound actions atomic. synchronized provides both mutual exclusion and visibility for any block of code, at the cost of possible blocking.

What is a deadlock and how do you prevent it?

Two or more threads each hold a lock and wait for a lock held by another, forever. Prevent it by acquiring locks in a consistent global order, holding locks briefly, avoiding calling unknown code while holding a lock, or using ReentrantLock.tryLock with a timeout.

How does AtomicInteger work without locks?

It uses a CPU compare-and-swap (CAS) instruction: read the value, compute the new one, and write it only if the value is still what was read; otherwise retry. No thread blocks, so there's no deadlock risk, though heavy contention can cause retries (LongAdder reduces that).

{{PRACTICE}}

Real-world scenario questions (asked in company interviews)

Concurrency bugs are favourite interview topics because they are expensive in production and invisible in simple tests.

E-commerce · oversellingFresher

103 orders for 100 phones

During a flash sale, 100 units were listed but 103 orders were confirmed. The code does if (stock > 0) { createOrder(); stock--; } in a request handler. Explain and fix.

The interviewer is checking: check-then-act races.

Show a strong answer
  • Several request threads passed the stock > 0 check before any of them decremented: a check-then-act race.
  • Make the check and decrement one atomic step: a synchronized method, an AtomicInteger with compareAndSet/getAndUpdate, or (across servers) a conditional database update UPDATE … SET stock = stock - 1 WHERE stock > 0.
  • Create the order only after the reservation succeeds.

Avoid: “add a small sleep” or “it only happens under load”. That's exactly when it matters.

Code review · locksJunior

Synchronized, yet still wrong

A colleague wrote synchronized (new Object()) { total += amount; } and says the method is now thread-safe. Tests still show wrong totals. Why?

The interviewer is checking: that exclusion requires a shared lock.

Show a strong answer
  • Every call locks a brand-new object, so no two threads ever compete for the same lock: no exclusion at all.
  • Use one shared, final lock object (private final Object lock = new Object();) or synchronized (this), or an atomic type.

Avoid: locking on strings or boxed Integers: they may be shared or replaced unexpectedly.

Payments · deadlockMid

Transfers freeze at month end

The transfer service locks the sender account, then the receiver. On salary day it sometimes freezes completely; a thread dump shows two threads BLOCKED, each holding the lock the other needs. Fix it.

The interviewer is checking: deadlock diagnosis and lock ordering.

Show a strong answer
  • A→B and B→A transfers ran at once: thread 1 holds A and wants B; thread 2 holds B and wants A. A circular wait.
  • Lock by a global order (e.g. smaller account id first), whatever the transfer direction.
  • Alternatively use tryLock with a timeout and retry, and alert on long lock waits.

Avoid: restarting the server as the fix. The deadlock will return on the next busy day.

Performance · contentionMid

Thread-safe, but now slow

To fix a race, someone made the whole handleRequest() method synchronized, including a 300 ms database call. Throughput dropped from 800 to 3 requests per second. What would you do?

The interviewer is checking: minimal critical sections.

Show a strong answer
  • The lock serialises every request, so all requests queue behind the slow call.
  • Identify the actual shared state, and lock only the few lines that touch it; do I/O outside the lock.
  • Use concurrent data structures (ConcurrentHashMap, atomics) where they fit, so most code needs no lock.

Avoid: removing synchronization entirely to regain speed; the race comes back.
