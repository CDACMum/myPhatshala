Who changed the balance?

In the college bank project, Kabir's report code accidentally wrote acc.balance = 0; while trying to print it. Every account in the demo showed zero. Riya asks Arjun Sir how to stop other code from touching what it shouldn't.

Sir, Kabir only wanted to print the balance, but his code wiped it. Can Java stop that? Yes, before the program even runs. Mark the field private. Then only code written inside the Account class can touch it, and the compiler rejects acc.balance = 0 anywhere else. But then how does the report print it? Give the class a public method, getBalance(), that only reads. You choose exactly what the outside world may do. There are four levels; let's learn them all.

What are access modifiers?

Formal definition (write this in exams)

Access modifiers are keywords that set the visibility of classes, constructors, fields and methods, that is, which other code may refer to them. Java has four access levels: public (accessible from everywhere), protected (accessible within the same package and from subclasses in other packages), default or package-private, written with no keyword (accessible only within the same package), and private (accessible only within the class that declares it). Access is checked by the compiler, and again by the JVM when classes are linked.

In simple words

A label on each member saying who may use it: everyone, family (subclasses) and neighbours (same package), neighbours only, or nobody outside the class.

Private members inside one file

class Account {
    private int balance = 5000;      // only Account's own code can use this
    int branchCode = 7;              // default: any class in this package

    public int getBalance() {        // read-only window
        return balance;
    }
}

public class Main {
    public static void main(String[] args) {
        Account acc = new Account();
        System.out.println(acc.getBalance());   // OK: public method
        System.out.println(acc.branchCode);     // OK: same package (same file)
        // System.out.println(acc.balance);     // error: balance has private access in Account
    }
}

Rule of thumb: start with private and open up only when you need to. It's easy to make something more visible later, but once other teams depend on a public field, you can never take it back.

How javac checks an access

  1. Find the member being used

    int b = acc.balance;
    javac resolves acc's type (bank.Account) and finds the field balance and its modifier.

  2. Compare where the code is with where the member is declared

    The using code is in class shop.Report; the member is declared in class bank.Account. Different class, different package, and Report is not a subclass of Account.

  3. Apply the table

    private requires the same class: ✗. javac reports balance has private access in Account and writes no class file.

  4. The JVM checks again when linking

    If someone edits bytecode or compiles against an old version of Account, the JVM still refuses with IllegalAccessError at run time. Access control is part of Java's security, not just a compile-time hint.

  5. Reflection can bypass it, with permission

    Field f = Account.class.getDeclaredField("balance");
f.setAccessible(true);   // frameworks do this for private fields
    Frameworks such as JSON mappers use reflection to read private fields. Since Java 9 the module system can block this for JDK internals. Treat private as “not part of the contract”, not as encryption.

Four accesses, four answers

Left: code in another package trying to use members of bank.Account. Right: javac checking each access against the four levels.

Access from package shop to class bank.Account 6 steps
What you see
  1. owner is public, so code in any package can read it.
  2. type is protected. The code is in package shop and the class Main isn't a subclass of Account: not allowed.
  3. branchCode has no modifier (default). Only classes inside package bank can use it.
  4. balance is private: only the Account class's own code may touch it.
  5. The public method getBalance() is declared inside Account, so it may read balance and return the value. Outsiders get the value without getting write access.
  6. A class Savings extends Account in package shop can use type in its own code, because it inherits it. That's what protected is for.
Behind the screen
  1. javac works out where the using code lives (class shop.Main) and compares it with where owner is declared. Public members pass from anywhere.
  2. Protected requires the same package, or a subclass using the member through inheritance. Neither applies, so it is denied.
  3. Default (package-private) requires the same package. shop isn't bank: denied.
  4. Private requires the same class. Denied, with the error Kabir would have seen.
  5. The call to the public method passes. Inside the method body, the use of balance is in class Account itself, so that check passes too.
  6. Inside Savings, a subclass, this.type refers to its own inherited field, so protected access is granted even across packages.

Access control in real systems

Access modifiers are how teams keep large codebases safe to change: what's private can be rewritten freely, what's public must keep working.

{{ANIM2}}

1. Protecting money and personal data

Balances, PAN numbers and passwords stay private. Changes go through methods that validate input and write audit logs; reads may be masked (XXXX1234).

Caller→public withdraw(…)→private balance updated safely

2. Stable public APIs

Libraries keep a small public surface. The JDK's ArrayList has a private elementData array; its implementation has changed across versions without breaking your code.

Your code→public add(), get()→Private internals can change

3. Package-private helpers

A payments package may have public PaymentService plus package-private UpiAdapter and CardAdapter that only the service uses. Other teams can't depend on them by accident.

Other packages→PaymentService only→Adapters hidden

4. Frameworks and protected hooks

Base classes expose protected methods for subclasses to customise, e.g. HttpServlet.doGet and doPost, which your servlet overrides.

Framework base class→protected doGet(…)→Your subclass fills it in

Examples are simplified. Since Java 9, modules add another layer: a package is only visible to other modules if its module exports it.

A wallet with private data and public methods

class Wallet {
    private final String owner;
    private int balance;

    public Wallet(String owner, int balance) {
        this.owner = owner;
        this.balance = balance;
    }

    public int getBalance() {
        return balance;
    }

    public boolean pay(int amount) {
        if (amount <= 0 || amount > balance) {
            return false;
        }
        balance -= amount;
        log("paid " + amount);
        return true;
    }

    private void log(String msg) {
        System.out.println("[" + owner + "] " + msg);
    }
}

public class Main {
    public static void main(String[] args) {
        Wallet w = new Wallet("Riya", 500);
        System.out.println(w.pay(120));
        System.out.println(w.pay(900));
        System.out.println("Left: " + w.getBalance());
    }
}
[Riya] paid 120 true false Left: 380
  • private int balanceOnly Wallet's own methods can change it.
  • public boolean pay(…)The only way to spend money, and it checks the rules first.
  • private void log(…)An internal helper. Outside code can't call it, so it can be changed freely.
  • private final String ownerPrivate and never reassigned after the constructor.

Private data changed only through a public method

Access rules are checked by the compiler, so they leave no trace at run time. What you can see is the effect: the only path to the private field goes through methods of its own class.

Quick revision

Lesson 6.5 in one screen

  • Four levels: public (everyone) > protected (package + subclasses) > default (package) > private (class).
  • Same program, one field, change only the modifier: public → 5 of 5 users compile, protected → 3, default → 2, private → 1 (the class itself).
  • Protected across packages works only through the subclass's own inheritance (ifsc, this.ifsc), not through a plain parent object.
  • No keyword = default (package-private).
  • Top-level classes: only public or default; one public class per file, named like the file.
  • Errors: has private access in …, is not public in …; cannot be accessed from outside package, has protected access in ….
  • Make fields private; expose behaviour through public methods (getters, validated setters).
  • Private constructors stop object creation (utility classes, singletons).
  • Checked by javac and again by the JVM (IllegalAccessError); reflection can bypass it with setAccessible.

Interview and viva questions

Explain the four access modifiers with an example.

In a bank system: public deposit() can be called by any code; protected calculateInterest() can be customised by subclasses like SavingsAccount; a default-level AuditHelper is used only inside the bank package; private balance can only be changed by Account's own methods.

A subclass in another package gets "has protected access" for a protected field. Why?

Because it read the field through a reference of the parent type, e.g. Account other = new Account(); other.ifsc. Outside the package, a subclass may use a protected member only on itself or objects of its own type (ifsc, this.ifsc, loan.ifsc). It is not a key to every Account object in the system.

What is the difference between protected and default?

Both allow access within the same package. protected additionally allows subclasses in other packages to use the member through inheritance. Default does not.

Why should fields be private?

So the class controls every change: it can validate values, keep related fields consistent, log changes, and change its internal representation later without breaking callers. Public fields can be set to anything by anyone, forever.

Can you reduce visibility when overriding a method?

No. An overriding method must be at least as visible as the method it overrides: a public method can't become protected in a subclass. You'll see this again in Lesson 7.4.

Is private access a security guarantee?

It's a strong design boundary enforced by the compiler and the JVM, but code with enough permission can use reflection to read private fields, and anyone with the class file can read its contents. Never rely on private to hide secrets such as passwords or API keys.

Real-world scenario questions (asked in company interviews)

Access-modifier questions in interviews are really design questions: what should the rest of the system be allowed to depend on?

Banking · code reviewFresher

A public balance field

A pull request adds public double balance; to Account “so the report screen can show it”. What do you suggest?

The interviewer is checking: do you understand why fields are private?

Show a strong answer
  • A public field lets any code anywhere write any value, skipping validation and audit logging.
  • Keep it private and add public double getBalance(). The report only needs to read.
  • Changes go through deposit/withdraw, which enforce rules. Later the field can even become a BigDecimal without breaking callers.

Avoid: “we'll just be careful”. The compiler should enforce it.

Platform · library design1–3 years

Another team depends on your helper

You built a payments package. Another team started calling your public class UpiSignatureHelper directly. Now you want to replace it, but their code would break. What should have been done, and what now?

The interviewer is checking: do you think about public surface as a commitment?

Show a strong answer
  • The helper was an internal detail; it should have been package-private so only your package could use it.
  • Now: offer the needed function through your public service, mark the helper @Deprecated with a migration note, and remove it in a later release.
  • For bigger systems, Java modules let you export only the API packages.

Avoid: silently deleting it and breaking another team's build.

E-commerce · inheritance1–3 years

protected or private?

A base class Order has a discount field. Subclasses PrimeOrder and FestiveOrder need different discount rules. A teammate makes the field protected so subclasses can set it. Any concerns?

The interviewer is checking: do you know protected fields also leak to the whole package?

Show a strong answer
  • A protected field is writable by every class in the package and by every subclass, so the base class loses control of its value.
  • Better: keep the field private and add a protected abstract int discountPercent() method (Lesson 7.6) that each subclass implements. The base class applies the rule.
  • Protected methods as hooks are fine; protected fields are usually a smell.

Avoid: thinking protected means “only my subclasses”.

Security · secretsFresher

“It's private, so the key is safe”

A developer stores an API key as private static final String KEY = "sk_live_…"; in the app's code and argues it's safe because it's private. Is it?

The interviewer is checking: do you know what access modifiers can and can't protect?

Show a strong answer
  • No. Access modifiers stop other code from using a name; they don't encrypt anything. The string sits in the class file, and tools like javap -v or any decompiler reveal it.
  • Secrets belong in environment variables or a secrets manager, read at run time, and never in source control.
  • Rotate the leaked key immediately.

Avoid: confusing visibility with confidentiality.
