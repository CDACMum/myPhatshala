Two Riyas in the attendance set

Kabir builds an attendance tracker. Each scan of an ID card creates a Student object and adds it to a HashSet, which is supposed to ignore duplicates. Riya scans her card twice. The set now says 2 students are present, and printing it shows gibberish like Student@4e25154f.

I scanned once, then again because the beep was soft. Now the dashboard says two students are present, and it doesn't even show my name! Your two scans made two Student objects with the same roll number. To Java they're different objects, because nobody told the class what “same student” means. That's the job of equals(). And the Student@4e25154f? That's the default toString() from the Object class: class name, @, and the hash code in hex. Every class inherits it. Override it to print something useful. So I just write equals, and the set will notice the duplicate? Not yet. A HashSet first uses hashCode() to pick a bucket, and only then calls equals. If equal objects can land in different buckets, equals never even runs. The rule is: override equals and hashCode together. Let's see why.

What is the Object class?

Formal definition (write this in exams)

java.lang.Object is the root of the class hierarchy: every class, including arrays, directly or indirectly extends it. A class with no extends clause extends Object implicitly. Object defines 11 methods inherited by all classes, including toString() (a text form of the object), equals(Object) (logical equality, by default the same as ==) and hashCode() (an integer used by hash-based collections). If a class overrides equals, it must override hashCode so that equal objects have equal hash codes.

In simple words

Object is the parent of everything. It gives every object a default way to print itself, compare itself and produce a hash number. For your own classes, you usually replace those defaults with ones that look at the fields.

Exam tip: the equals–hashCode contract: (1) if a.equals(b) is true, then a.hashCode() == b.hashCode() must be true; (2) equal hash codes do not require equals to be true (that's a collision, and it's allowed); (3) hashCode must return the same value each time while the fields used in equals don't change. Also: equals must be reflexive, symmetric, transitive, consistent, and x.equals(null) must be false. {{AD}}

2. equals(): same object vs same meaning

import java.util.Objects;

class Student {
    String roll, name;
    Student(String roll, String name) { this.roll = roll; this.name = name; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;                        // same object: equal
        if (!(o instanceof Student)) return false;         // null or another type
        Student other = (Student) o;
        return Objects.equals(roll, other.roll);           // same roll number = same student
    }
}

public class Main {
    public static void main(String[] args) {
        Student a = new Student("21CS07", "Riya");
        Student b = new Student("21CS07", "Riya");
        System.out.println(a == b);        // two objects
        System.out.println(a.equals(b));   // same student
        System.out.println(a.equals(null));
    }
}
false true false
Common mistake: writing public boolean equals(Student o). That overloads instead of overriding (the parameter must be Object), so collections still call Object's version. @Override catches it: javac reports method does not override or implement a method from a supertype.

3. hashCode(): keep the contract

import java.util.HashSet;
import java.util.Objects;

class Student {
    String roll, name;
    Student(String roll, String name) { this.roll = roll; this.name = name; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Student)) return false;
        return Objects.equals(roll, ((Student) o).roll);
    }

    @Override
    public int hashCode() {
        return Objects.hash(roll);         // the same field(s) as equals
    }
}

public class Main {
    public static void main(String[] args) {
        HashSet<Student> present = new HashSet<>();
        present.add(new Student("21CS07", "Riya"));
        present.add(new Student("21CS07", "Riya"));   // second scan
        present.add(new Student("21CS12", "Kabir"));
        System.out.println(present.size());
    }
}
2

Remove the hashCode method and run it again: the size becomes 3. The two Riya objects get different identity hash codes, land in different buckets, and the set never compares them with equals.

Rule of thumb: generate these three methods with your IDE (or use a record, Lesson 14.5, which writes them for you). Use the same fields in equals and hashCode, prefer fields that never change, and always add @Override.

How a HashSet decides “already there”

  1. Call hashCode()

    present.add(new Student("21CS07", "Riya"));
    HashSet is backed by a HashMap. It calls student.hashCode() and mixes the bits to get a number.

  2. Pick a bucket

    The number is reduced to a bucket index (with 16 buckets, roughly hash & 15). Only objects in that bucket are candidates for “the same”.

  3. Compare with equals() inside the bucket

    For each object already in the bucket, it checks the stored hash first, then calls equals. Different hash codes mean equals is never called.

  4. Equal one found: don't add

    add returns false and the set is unchanged. This only works if equal students produce equal hash codes, which is why hashCode must use the same fields as equals.

  5. No equal one: add a new entry

    The object goes into the bucket. Two unequal objects may share a bucket (a collision, e.g. "Aa" and "BB" both hash to 2112). That's allowed; it just makes lookups a little slower.

{{ANIM}}

equals, hashCode and toString in real systems

These three methods sit underneath logging, caching, de-duplication and every HashMap key in a codebase.

{{ANIM2}}

1. Readable logs

Log lines and error messages call toString(). Order[id=9912, total=₹1499] helps support teams; Order@1b6d3586 doesn't. Teams leave secrets like passwords and card numbers out of toString.

log.info("Saved " + order)→order.toString()→useful log line

2. De-duplicating records

Merging customer lists from two branches, or ignoring a double-tap on “Pay”, relies on a HashSet or HashMap recognising equal objects, by PAN, phone number or transaction ID.

Two records→equals + hashCode on the ID→stored once

3. Cache keys

A travel site caches fare searches in a map keyed by a SearchKey(from, to, date) object. Without proper equals/hashCode, every search misses the cache and hits the slow pricing system.

new SearchKey(...)→map.get(key)→hit, if equal keys hash equally

4. Unit tests

assertEquals(expected, actual) in JUnit calls equals, and prints both objects with toString when the test fails. Good overrides make test failures easy to read.

assertEquals→expected.equals(actual)→clear failure message

Examples are simplified. Persistence frameworks such as JPA have extra advice on equals/hashCode for entities with generated IDs.

An attendance register that counts each student once

import java.util.HashSet;
import java.util.Objects;

class Student {
    private final String roll;
    private final String name;

    Student(String roll, String name) {
        this.roll = roll;
        this.name = name;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Student)) return false;
        Student s = (Student) o;
        return roll.equals(s.roll);
    }

    @Override
    public int hashCode() {
        return Objects.hash(roll);
    }

    @Override
    public String toString() {
        return name + " (" + roll + ")";
    }
}

public class Main {
    public static void main(String[] args) {
        HashSet<Student> present = new HashSet<>();
        System.out.println(present.add(new Student("21CS07", "Riya")));
        System.out.println(present.add(new Student("21CS12", "Kabir")));
        System.out.println(present.add(new Student("21CS07", "Riya")));
        System.out.println("Present: " + present.size());
        System.out.println(present.contains(new Student("21CS12", "Kabir")));
    }
}

Check yourself

Quick revision

Lesson 10.3 in one screen

  • Object is the root of all classes; 11 inherited methods.
  • toString() default: ClassName@hex. Override for printing and logs (leave out secrets).
  • equals() default is ==. Override with parameter Object: check this == o, instanceof, then compare key fields.
  • hashCode(): override whenever you override equals; use the same fields (Objects.hash(...)).
  • Contract: equal objects → equal hash codes. Equal hash codes → not necessarily equal (collision).
  • HashSet/HashMap: hashCode picks the bucket, equals confirms. Missing hashCode → duplicates, failed lookups.
  • Always use @Override; consider IDE generation or records (Lesson 14.5).

Interview and viva questions

What is the difference between == and equals()?

== compares references for objects (same object in memory) and values for primitives. equals() asks the object whether another object is logically equal; its default is ==, but classes like String, Integer and List override it to compare contents.

Why must you override hashCode() when you override equals()?

Hash-based collections find objects by hash code first. If two equal objects returned different hash codes, a HashSet could store both, and HashMap.get with an equal key would look in the wrong bucket and return null. The contract requires equal objects to have equal hash codes.

instanceof or getClass() in equals?

instanceof lets a subclass object be equal to a parent object, which can break symmetry if the subclass adds fields. getClass() != o.getClass() requires the exact same class and is stricter. Many teams use getClass() for non-final classes and instanceof for final ones; records and IDEs choose for you.

What happens if a field used in hashCode changes after the object is in a HashSet?

The object stays in its old bucket, but lookups now compute a new hash and search a different bucket. contains and remove fail, and the object is effectively lost inside the set. Use immutable fields for equality, or remove the object, change it, and add it back.

Is the default hashCode the memory address?

Not necessarily. It's an identity hash code generated by the JVM (HotSpot typically uses a random-based number stored in the object header). It stays the same for the object's lifetime, even if the GC moves the object.

{{PRACTICE}}

Real-world scenario questions (asked in company interviews)

equals/hashCode questions are classics in Java interviews, from freshers to seniors. The best answers connect the contract to a real failure.

Travel · cachingFresher

The cache that never hits

A fare cache uses HashMap<SearchKey, Fare>. Every search creates new SearchKey(from, to, date). The hit rate is 0% even for repeated searches. What's missing?

The interviewer is checking: hashCode/equals for map keys.

Show a strong answer
  • SearchKey uses Object's identity-based equals and hashCode, so a new key object never matches the stored one.
  • Override both using from, to and date; make those fields final so the hash can't change.
  • Or declare it as record SearchKey(String from, String to, LocalDate date), which generates both correctly.
  • Add a test: two keys with the same values must be equal and give the same hash code.

Avoid: using a concatenated String key like from + to + date without a separator. "AB"+"C" and "A"+"BC" collide.

Banking · data qualityJunior

Duplicate customers after a merge

Two branch databases are merged into a HashSet<Customer>. Customer overrides equals on PAN, but the merged set has thousands of duplicates. Why, and how do you prove the fix?

The interviewer is checking: understanding of how HashSet uses hashCode first.

Show a strong answer
  • hashCode wasn't overridden, so equal customers usually land in different buckets and equals is never called.
  • Override hashCode with Objects.hash(pan): the same field as equals. Normalise PAN (upper-case, trimmed) in the constructor so equal PANs really are equal.
  • Prove it: a unit test with two objects having the same PAN gives set size 1; re-run the merge and compare counts.

Avoid: return 1; as hashCode. It's legal but puts every customer in one bucket and makes the set crawl.

Security · loggingJunior

Card numbers in the logs

A security audit finds full card numbers in application logs. The code just logs "Payment failed: " + payment. Where did the card number come from, and what do you change?

The interviewer is checking: toString as a hidden data channel.

Show a strong answer
  • String concatenation calls payment.toString(), which was generated to include every field, card number included.
  • Rewrite toString to include only safe fields and mask sensitive ones (XXXX-XXXX-XXXX-4421).
  • Add a log-scanning check in CI and purge the affected logs per the incident process.

Avoid: “just don't log payments”. You'll lose the information support needs; log safely instead.

Platform · designMid

An object lost inside a HashSet

A Ticket is added to a HashSet, then its status changes from OPEN to CLOSED. Afterwards set.contains(ticket) returns false for that very object, and remove doesn't work. Explain.

The interviewer is checking: mutable fields in hashCode.

Show a strong answer
  • hashCode includes status. When status changed, the hash changed, but the entry stayed in the bucket chosen by the old hash.
  • contains searches the new bucket and finds nothing.
  • Base equality on the immutable ticketId only. If equality must include mutable data, remove the object before changing it and re-add it after.

Avoid: blaming HashSet. It relies on the contract that hashCode stays stable while the object is in the set.
