The report hidden inside a loop

The canteen owner asks Riya: “What did big orders, ₹999 and above, bring in today, including GST?” Her answer is a loop with an if, a calculation, a running total and a temporary list. It works, but a week later even she has to read it twice.

Sir, the question was one sentence. Why is my code six lines of bookkeeping? Because a loop says how to do it. A stream says what you want: keep orders ≥ 999, add GST, sum them. Three steps, three words: filter, map, reduce. Does it make three passes over the list? No, and that's the clever part. Let's watch the orders flow.

What is the Stream API?

Formal definition (write this in exams)

A stream (java.util.stream.Stream<T>) is a sequence of elements from a source (a collection, array, I/O channel or generator) that supports aggregate operations in a pipeline. A pipeline consists of a source, zero or more intermediate operations (such as filter, map, sorted), which are lazy and return a new stream, and one terminal operation (such as collect, reduce, forEach, count), which triggers processing and produces a result or side effect. Streams do not store elements, do not modify their source, and can be consumed only once. Primitive streams (IntStream, LongStream, DoubleStream) avoid boxing.

In simple words

A stream is a conveyor belt with stations. You set up the stations (filter, map…), and nothing moves until someone at the end asks for the result.

Keep lambdas in a stream free of side effects. Don't add to an outside list or change shared variables inside map or filter; collect the result instead. Side effects make streams hard to read and break completely with parallelStream().

Building and running a pipeline

  1. Get a stream from a source

    orders.stream()
    A Stream object linked to the list. No elements are read yet.

  2. Add intermediate operations

        .filter(a -> a >= 999)
    .map(a -> a * 118 / 100)
    Each call returns a new Stream stage that remembers its lambda and the previous stage. Still nothing runs.

  3. Call a terminal operation

        .reduce(0, Integer::sum);
    Now the source is asked for elements, one at a time.

  4. Each element flows through every stage

    450: filter says no, so the next element starts. 1200: filter yes, map gives 1416, reduce adds it. Stateful steps like sorted are the exception: they must collect all elements first.

  5. The result, and the end of the stream

    The terminal operation returns its result. The stream is now consumed; build a new one for another query.

{{ANIM}}

Streams in real systems

Wherever Java code produces reports, dashboards or API responses from collections, you'll find stream pipelines.

{{ANIM2}}

1. Dashboards and reports

Sales per city, top products, orders per hour: groupingBy and summing collectors build the numbers behind the charts.

orders→groupingBy(city, summingInt)→bar chart

2. API responses

Services map database entities to response objects: products.stream().map(ProductDto::from).toList().

entities→map(Dto::from)→JSON list

3. File and log processing

Files.lines(path) is a lazy stream of lines: filter errors, map to fields, count, without loading the whole file.

app.log→lines().filter(...).count()→error rate

4. Validation

allMatch, anyMatch and noneMatch answer “are all items in stock?” or “is any field empty?” in one line.

cart→allMatch(i -> i.inStock())→allow checkout

Simplified: very large datasets are usually aggregated in the database (SQL GROUP BY) or a data platform; streams shine for data already in memory.

Quick revision

Lesson 14.3 in one screen

  • Pipeline = source → intermediate ops (lazy) → one terminal op.
  • filter (Predicate), map (Function), sorted, distinct, limit, skip are intermediate.
  • collect/toList, reduce, count, sum, forEach, findFirst, anyMatch are terminal.
  • Nothing runs until the terminal op; then elements flow one at a time through all stages.
  • Streams never modify the source and can be used once.
  • IntStream (mapToInt, range) for numbers: sum, average, max.
  • Collectors: toList, joining, groupingBy + counting/summingInt.

Interview and viva questions

What is the difference between intermediate and terminal operations?

Intermediate operations (filter, map, sorted…) return a new stream and are lazy; they only describe the pipeline. Terminal operations (collect, reduce, forEach, count…) produce a result or side effect and trigger the processing. A pipeline has exactly one terminal operation.

What does “streams are lazy” mean, and why is it useful?

Elements are processed only when a terminal operation needs them, one at a time through the whole pipeline. This avoids intermediate collections, allows short-circuiting (findFirst stops at the first match) and even works on infinite streams with limit.

map vs flatMap?

map turns each element into exactly one new element. flatMap turns each element into a stream of elements and flattens them into one stream, e.g. orders → their line items: orders.stream().flatMap(o -> o.items().stream()).

Collection vs Stream?

A collection stores elements in memory and can be iterated many times; a stream stores nothing, computes elements on demand from a source, and can be consumed once. Collections are about data; streams are about computation on data.

When should you not use parallelStream()?

For small collections, I/O-bound work, operations with side effects or shared mutable state, or when order matters and you'd need costly ordering. Parallel streams use the common ForkJoinPool; measure before using them.

{{PRACTICE}}

Real-world scenario questions (asked in company interviews)

Stream questions in interviews are usually about correctness and performance traps, not syntax.

Code review · side effectsFresher

Adding to a list inside forEach

A teammate writes List<String> out = new ArrayList<>(); names.stream().filter(...).forEach(n -> out.add(n.trim()));. It works. What would you suggest?

The interviewer is checking: idiomatic, side-effect-free streams.

Show a strong answer
  • Use the stream's result instead of mutating an outside list: List<String> out = names.stream().filter(...).map(String::trim).toList();
  • The side-effect version breaks (lost elements, exceptions) if someone later switches to parallelStream(), because ArrayList isn't thread-safe.

Avoid: “forEach is the stream version of a for loop”; collect is.

Performance · orderJunior

Sorting 10 lakh items to show 5

A product page runs products.stream().sorted(byPrice).filter(p -> p.inStock()).limit(5) on 10 lakh products. It's slow. How would you reorder or rewrite it?

The interviewer is checking: operation order and stateful operations.

Show a strong answer
  • sorted must see every element before passing any on, so it sorts all 10 lakh, including out-of-stock ones.
  • Filter first: filter(inStock).sorted(byPrice).limit(5) sorts fewer items.
  • Better still, let the database do WHERE in_stock ORDER BY price LIMIT 5 with an index.

Avoid: switching to parallelStream() before fixing the order.

Bug · duplicate keysJunior

IllegalStateException: Duplicate key

Building a map of customers by phone with Collectors.toMap(Customer::phone, c -> c) crashes in production with “Duplicate key 98xxxxxx10”. Explain and fix.

The interviewer is checking: collector behaviour with real data.

Show a strong answer
  • toMap throws when two elements produce the same key; two customers share a phone number (family accounts, data errors).
  • Decide the business rule: keep the latest with a merge function toMap(k, v, (a, b) -> b), or keep all with groupingBy(Customer::phone).
  • Log or report duplicates so data quality can be fixed.

Avoid: catching the exception and returning an empty map.

Performance · parallelMid

parallelStream made the API slower

To speed up a product-details API, a developer changed ids.stream().map(this::fetchFromDb) to parallelStream(). Under load the whole server got slower. Why?

The interviewer is checking: parallel streams and the common pool.

Show a strong answer
  • Parallel streams run on the shared ForkJoinPool (about one thread per core). Blocking DB calls tie up those few threads, and every request in the JVM competes for them.
  • For I/O, fetch in one batched query (WHERE id IN (...)), or use a dedicated executor / virtual threads with CompletableFuture.
  • Keep parallel streams for CPU-heavy work on large in-memory data, and measure.

Avoid: “parallel is always faster”.
