The crash that only happened to new students

Riya's canteen app greets students by name: findStudent(roll).getName(). It works for everyone already registered. On admission day, the app crashes for every new student, because findStudent returns null for them.

Sir, I can add if (s != null) everywhere. But how will I remember every place? You won't. Nobody does. Make the method return Optional<Student>. Then the type itself tells every caller: “this might be empty, handle it”. And handling it means more ifs? No: map, orElse, orElseThrow. Let's look inside the box.

What is Optional?

Formal definition (write this in exams)

java.util.Optional<T> is a container object that may or may not contain a non-null value of type T. It is intended mainly as a method return type where there may be no result, to make the absence explicit and avoid returning null. An Optional is created with Optional.of(value) (value must be non-null), Optional.ofNullable(value) or Optional.empty(). Its value is accessed through methods such as orElse, orElseGet, orElseThrow and ifPresent, and transformed with map, filter and flatMap, which return Optionals. Calling get() on an empty Optional throws NoSuchElementException.

In simple words

Optional is a gift box that might be empty. You're not allowed to assume there's something inside; you say what to do in both cases.

Why not just call get()?

{{CODE_GET}} Use Optional for return values, not everywhere. Don't make fields, method parameters or collection elements Optional (List<Optional<X>>): it's not Serializable, adds noise, and an empty list is already a fine “nothing”. And never return null from a method whose type is Optional.

What happens in find(id).map(f).orElse(d)

  1. The finder returns a box

    Optional<String> name = findName("98100");
    Inside: Optional.ofNullable(map.get(phone)): a box holding the name, or the shared empty box.

  2. map checks the box

    If a value is present, map calls your function and wraps the result (via ofNullable) in a new Optional. If empty, it returns empty without calling it.

  3. filter can empty it

    If you add .filter(test), a present value that fails the test becomes empty.

  4. orElse unwraps

    Present: return the value. Empty: return the fallback. Either way you get a plain value, never null (unless the fallback is null).

  5. Or fail clearly

    .orElseThrow(() -> new IllegalArgumentException("unknown id " + id))
    When there's no sensible default, throwing a meaningful exception at this point is much easier to debug than an NPE three methods later.

{{ANIM}}

Optional in real systems

Data-access layers, configuration lookups and stream results are the most common places you'll meet Optional.

{{ANIM2}}

1. Database lookups

Repository methods like findById(id) in Spring Data return Optional<Customer>: the record may not exist.

findById(42)→Optional<Customer>→orElseThrow(NotFound)

2. Configuration

Optional settings get defaults; required ones fail at startup with a clear message.

config.get("timeout")→orElse("30s")→value

3. Stream results

findFirst, min, max and reduce return Optional because a stream can be empty.

today's orders→max(byAmount)→Optional<Order>

4. Optional user input

Coupons, referral codes and nicknames may or may not be supplied; Optional chains turn them into discounts or display names.

coupon code→filter(valid).map(off)→orElse(0)

Simplified: APIs that return many results return an empty list, not an Optional list.

Quick revision

Lesson 14.4 in one screen

  • Optional = a box that holds one non-null value or nothing; use it as a return type.
  • Create: of (non-null), ofNullable, empty.
  • Unwrap: orElse, orElseGet (lazy), orElseThrow.
  • Act: ifPresent, ifPresentOrElse. Avoid bare get().
  • Transform: map, filter, flatMap; empty passes through untouched.
  • Streams' findFirst, min, max return Optional.
  • Not for fields, parameters or collections; never return null as an Optional.

Interview and viva questions

What problem does Optional solve?

It makes the possible absence of a result explicit in a method's return type, so callers are forced to handle the empty case, reducing NullPointerExceptions. It also provides a fluent API (map, filter, orElse) for working with possibly-missing values.

Difference between orElse and orElseGet?

orElse(x) takes an already-evaluated value, so the expression is computed even when the Optional has a value. orElseGet(supplier) calls the supplier only when the Optional is empty. Use orElseGet when the default is expensive or has side effects.

Difference between map and flatMap on Optional?

map applies a function returning a plain value and wraps it; flatMap applies a function that already returns an Optional, avoiding Optional<Optional<T>>. Use flatMap to chain lookups that each may be empty.

Should you use Optional as a field or parameter?

Generally no. Optional isn't Serializable, adds allocation, and as a parameter it forces callers to wrap values. Prefer overloading or nullable parameters documented clearly for inputs, and plain nullable fields with Optional-returning getters.

Is Optional.get() bad?

It throws NoSuchElementException on empty, so isPresent() + get() is just a disguised null check. Prefer orElse/orElseThrow/ifPresent/map. Java 10 added orElseThrow() as a clearer name for the same behaviour as get().

Real-world scenario questions (asked in company interviews)

Optional questions test whether you can remove NPEs without making the code worse.

Production · NPEFresher

NullPointerException on the order-tracking page

The tracking page calls order.getRider().getPhone(). Orders that aren't assigned to a rider yet crash the page. How would you fix it so the page shows “Rider not assigned yet”?

The interviewer is checking: chaining optional relationships.

Show a strong answer
  • Make the getter honest: Optional<Rider> rider().
  • Page code: order.rider().map(Rider::phone).orElse("Rider not assigned yet").
  • Search for other callers of getRider(); the new type makes the compiler point them out.

Avoid: wrapping the whole page in try { … } catch (NullPointerException e).

Performance · defaultsJunior

Every request hits the pricing service

Code reads cachedPrice(id).orElse(pricingService.fetch(id)). Monitoring shows the pricing service is called on every request, even when the cache has the price. Why?

The interviewer is checking: orElse vs orElseGet.

Show a strong answer
  • orElse's argument is evaluated before the call, so fetch(id) always runs.
  • Use orElseGet(() -> pricingService.fetch(id)): the supplier runs only on a cache miss.

Avoid: adding an if-isPresent around it; orElseGet already expresses it.

Code review · misuseJunior

Optional everywhere

A pull request changes every entity field to Optional<...> and every method parameter too, “to remove nulls from the codebase”. Serialization of sessions now fails. What feedback would you give?

The interviewer is checking: knowing Optional's intended scope.

Show a strong answer
  • Optional is designed for return types. It's not Serializable, so fields break serialization and many frameworks.
  • Keep fields as plain (possibly null) references and expose Optional-returning getters for the optional ones.
  • For parameters, use overloads or validate non-null inputs with Objects.requireNonNull.

Avoid: approving because it “looks modern”.

API design · errorsMid

Empty Optional or exception?

A PaymentService.getPayment(id) is called from refunds (where the id must exist) and from a search box (where it may not). Should it return Optional<Payment> or throw when not found?

The interviewer is checking: designing for callers.

Show a strong answer
  • Return Optional<Payment> from the lookup: “not found” is a normal outcome for search.
  • Refunds call getPayment(id).orElseThrow(() -> new PaymentNotFound(id)), choosing their own exception and message.
  • One method serves both cases; each caller decides what absence means.

Avoid: returning null for search and throwing for refunds from two near-identical methods.
