1 The story

“Where is my file, really?”

Riya uploaded canteen_orders.csv to HDFS yesterday. Today she asks a simple question nobody in the lab can answer: on which disk, of which machine, are those bytes? Kabir opens a shell on one DataNode, digs through folders, and finds a file called blk_1073741825. He runs head on it. Out come order_id,item,amount and Riya's orders, as plain text.

R> So HDFS is just… files on ordinary Linux disks? A> Exactly. A DataNode stores each block as an ordinary file in its own folders. What makes it a distributed file system is the NameNode: it keeps the whole directory tree, who owns what, and which blocks make up each file. And it knows, from the DataNodes' own reports, which machines hold each block. K> And if I lose the NameNode? A> The bytes are still on the disks, but nobody knows which blk_ file belongs to which file. That's why the NameNode's metadata is protected so carefully, and why HA exists. Today we open both: the NameNode's metadata folder and a DataNode's block folder, on a real cluster with four DataNodes in two racks.
2 Definition

NameNode and DataNode

Formal definition (write this in exams)

HDFS has a master–worker architecture. The NameNode manages the file system namespace (the tree of directories and files with their permissions, owners, replication factor and the ordered list of blocks of each file) and regulates client access. It persists the namespace in the fsimage and edit log, and keeps it in memory together with the block map (block → DataNodes holding a replica), which it rebuilds from DataNode block reports. DataNodes, usually one per worker machine, store blocks as files on their local disks (each with a .meta checksum file), serve read and write requests from clients directly, create, delete and copy replicas when the NameNode instructs, and send heartbeats and block reports to the NameNode. File data never passes through the NameNode.

In simple words

The NameNode is the index of a huge library: it knows every book's title and on which shelves its pages are. DataNodes are the shelves that hold the pages. Readers ask the index where to go, then fetch pages straight from the shelves.

LEVELS> NameNode and DataNode at three levels L1> The library and its index
  • A big book is torn into chapters (blocks) and each chapter is photocopied three times onto different shelves (DataNodes).
  • The index card (NameNode) says: “Canteen orders: chapter 1 on shelves 1, 2 and 4.”
  • A reader reads the card, then walks to the shelf. The librarian at the index never carries pages.
L2> What each daemon does
  • NameNode: create/delete/rename files and folders, check permissions, choose DataNodes for new blocks, track replicas, order re-replication when one is lost.
  • DataNode: store and checksum blocks, stream data to and from clients, forward blocks in the write pipeline, delete or copy blocks on command.
  • Client (your hdfs dfs, Spark, Hive): asks the NameNode for metadata, then talks to DataNodes for data.
L3> Details that matter in production
  • The block map is not saved in the fsimage. After a restart the NameNode waits for block reports (safe mode, Lesson 5.6).
  • NameNode heap grows with the number of objects, not bytes: 10 crore tiny files hurt far more than 1 PB in big files (the small-files problem, Lesson 7.5).
  • DataNodes spread blocks over all disks listed in dfs.datanode.data.dir; a failed disk can be tolerated (dfs.datanode.failed.volumes.tolerated).
  • Clusters with very large namespaces split it across several NameNodes with federation; each namespace gets its own block pool on the same DataNodes.
/LEVELS EXAM> “Explain the roles of NameNode and DataNode”: NameNode = master, namespace + metadata (fsimage, edit log, block map), handles client metadata requests, directs replication; DataNode = worker, stores blocks, serves reads/writes, sends heartbeats (every 3 s) and block reports. Add: data flows client ↔ DataNode, never through the NameNode.

5 See it happen

Following one file from its name to the disk

On the left, the commands from Part 4. On the right, which daemon answers and what it holds.

From path to bytes 6 steps
What you see
  1. -ls shows a normal-looking file: owner, size, replication 3. This answer comes only from the NameNode.
  2. fsck asks the NameNode for the file's blocks and where each replica is.
  3. On the NameNode's disk there is no data: just the fsimage, the edit log and identity files.
  4. On a DataNode's disk: the block as a plain file, plus its checksum file.
  5. The block's bytes are literally the CSV text Riya uploaded.
  6. The NameNode also tracks every DataNode: rack, capacity, last heartbeat and number of blocks.
Behind the screen
  1. The NameNode answers from its in-memory namespace: path, owner, size, replication.
  2. It also knows the file's blocks and, from the block map, which DataNodes hold each replica.
  3. Only the namespace is saved to disk (fsimage + edit log). The block map lives in memory only.
  4. On each chosen DataNode, the replica is a data file and a checksum file.
  5. When you read, the client gets locations from the NameNode and the bytes straight from a DataNode.
  6. DataNodes keep the NameNode up to date with heartbeats and block reports, which is how the block map is (re)built.

Try it yourself: the NameNode's view

Open the NameNode metadata tab under the cluster: it is the playground's version of fsck -files -blocks -locations.

6 Real-world use

NameNodes and DataNodes in production

1. NameNode sizing is about objects

Large companies size NameNode memory by the number of files, directories and blocks, not by petabytes. Teams that create millions of tiny files are asked to compact them because they cost NameNode heap.

Objects→Heap needed→Server size

2. Workers packed with disks

DataNode servers commonly hold 12 or more large disks, each listed in dfs.datanode.data.dir. A dead disk is swapped while the node keeps serving from the others.

Disk fails→Node keeps running→Hot-swap

3. Protecting the metadata

Admins write the NameNode metadata to more than one disk (a comma-separated dfs.namenode.name.dir), run HA, and back up the fsimage regularly. Losing it means losing the meaning of every block.

fsimage + edits→Several copies→Backups

4. Daily health checks

On-call engineers start the day with the NameNode UI or hdfs dfsadmin -report: live and dead DataNodes, remaining capacity, missing and under-replicated blocks.

Report→Spot problems→Act before users notice

Simplified; organisations differ in tools and policies.
