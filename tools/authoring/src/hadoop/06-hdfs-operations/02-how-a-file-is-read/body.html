1 The story

Nearest copy first, and never trust a damaged one

Kabir reads the 5-block canteen file twice: once from the namenode container, once from datanode-2. From the namenode container the blocks come from datanode-2, then datanode-3 three times, then datanode-1. From datanode-2, every single block comes from datanode-2 itself. Then Riya does something wicked: she overwrites one byte of a block file on datanode-2's disk with an X, and reads again from datanode-2. A warning appears: Found Checksum error … at 499712. Yet the file that comes out is byte-for-byte identical to the original.

A> A read has two parts. First the client asks the NameNode “where are the blocks of this file?”. The NameNode answers with every block's replica locations, sorted by distance from the client. Then the client reads each block directly from the first DataNode in that list. K> And from the namenode container there was no “nearest”? A> Right: it isn't a DataNode, and all three replicas were equally far, so the order was shuffled to spread the load. From datanode-2, its own disk is always closest. And the corrupted byte? Every 512 bytes of a block has a checksum. The client verified it, saw a mismatch, quietly fetched that part from another replica, and told the NameNode the copy on datanode-2 was bad. A few seconds later the NameNode had made a fresh copy elsewhere and deleted the bad one.
2 Definition

The HDFS read path

Formal definition (write this in exams)

To read a file, the client calls open; the DFSInputStream asks the NameNode (getBlockLocations) for the locations of the file's blocks, in batches. For each block the NameNode returns the DataNodes holding a replica, sorted by network distance from the client (local node, then same rack, then other racks; equal distances are shuffled). The client connects to the closest DataNode and streams the block directly; at a block boundary it moves to the best DataNode for the next block. Data is verified with checksums (one per 512 bytes) as it is read. On a checksum error or a DataNode failure, the client reads from the next replica, remembers the bad DataNode for that stream, and reports corrupt replicas to the NameNode (reportBadBlocks), which schedules re-replication from a good replica and deletes the corrupt one. The NameNode serves only metadata; data never passes through it.

In simple words

Ask the NameNode where the pieces are, then fetch each piece from the nearest machine that has it, checking every 512 bytes. If a piece is broken or a machine doesn't answer, use another copy and tell the NameNode.

LEVELS> The read path at three levels L1> A library with photocopies
  • You ask the index desk: “Where is chapter 1?” The librarian lists shelves holding copies, the nearest first.
  • You walk to the nearest shelf and read it there. The librarian never fetches pages.
  • If a page is smudged, you take another copy and tell the librarian, who replaces the smudged one.
L2> Step by step
  • open(): client asks the NameNode for block locations of the first part of the file.
  • read(): connect to the first (closest) DataNode for block 0 and stream it, verifying checksums.
  • At the end of block 0, pick the best DataNode for block 1 (maybe a different one), and so on.
  • For long files, ask the NameNode for more locations as needed.
  • close(): release connections.
L3> Robustness and performance
  • Failures: a DataNode that doesn't respond is added to the stream's dead-node list and the next replica is used.
  • Corruption: detected end-to-end by the client (checksums were created by the writer), so disk, network and memory errors are all caught.
  • DataNodes also run a background block scanner that finds corrupt replicas nobody has read for weeks.
  • Data locality in MapReduce and Spark is the same idea: put the task where the closest replica is distance 0.
  • Hedged reads (optional) start a second read from another replica if the first is slow.
/LEVELS EXAM> “Explain the anatomy of a file read in HDFS”: client open() → NameNode returns block locations sorted by proximity → client reads each block directly from the nearest DataNode, verifying checksums → moves to the next block → on error, tries another replica and reports the bad block → close(). Stress that the NameNode never sends data.

Read-side protections

Checksums

CRC per 512 bytes, checked by the reading client. Catches disk and network corruption.

Integrity

Replica failover

Dead or slow DataNode → next replica in the sorted list.

Availability

Block scanner

Each DataNode re-verifies its blocks in the background (default every 3 weeks).

Background

reportBadBlocks

Corrupt replicas are replaced from good ones automatically.

Self-healing
TIP> hdfs dfs -checksum path prints a file-level checksum built from block checksums. Compare it between two clusters (with the same block size) to check that a copy is identical without reading the data yourself.

printf 'X' | dd of=$f bs=1 seek=500000 conv=notrunc
    One byte in the middle of a 1 MB block replica on datanode-2 is overwritten. The file size doesn't change and HDFS isn't told. (Never do this on a real cluster: it's a demonstration of corruption.)

    The client noticed that the 512-byte chunk starting at 499,712 didn't match its checksum, read that block from another replica, and produced a file identical to the original (same MD5).

  6. The NameNode heals the block

    The client reported the bad replica; six seconds later a good copy existed on datanode-4 (.7), and the corrupt files on datanode-2 were deleted (0 left). Three healthy replicas again, without anyone running a command.
WARN> If every replica of a block is corrupt or unavailable, the read fails with a BlockMissingException and fsck marks the file CORRUPT. Replication protects against independent failures, not against writing bad data in the first place.
5 See it happen

A read that survives a corrupt replica

Steps 3 to 6 from the lab, frame by frame.

Reading canteen_1mb.csv from datanode-2 6 steps
What you see
  1. Normally a client on datanode-2 reads every block from datanode-2 itself.
  2. We damage one byte of one replica on datanode-2's disk.
  3. The next read detects the damage: the 512-byte chunk at offset 499,712 fails its checksum.
  4. Still, the output is identical to the original file: the client read that block from another replica.
  5. The client reported the bad replica; the NameNode copied a good one to datanode-4.
  6. Three healthy replicas, none on datanode-2: the corrupt copy was deleted.
Behind the screen
  1. The NameNode sorted dn-2 first for this client, so it reads from its own machine.
  2. The replica on dn-2 now has one wrong byte; its stored checksums still describe the original data.
  3. The client recomputes the checksum of each 512-byte chunk as it reads; chunk 976 doesn't match.
  4. It discards that data and reads the block from the next replica in the list.
  5. It reports the corrupt replica; the NameNode schedules a copy from a good replica to dn-4.
  6. The corrupt replica on dn-2 is invalidated (deleted). The block is fully protected again.
6 Real-world use

The read path at work

1. Data-local tasks

Schedulers place map and Spark tasks on nodes holding a replica, so most reads are distance 0, like step 3. Job counters such as “Data-local map tasks” show how well this worked.

Block on dn-2→Task on dn-2→Local read

2. Short-circuit reads for fast engines

Interactive SQL engines and HBase enable short-circuit local reads so they read block files straight from disk, skipping the DataNode's network stack and cutting latency.

Local block→Read file directly→Lower latency

3. Silent disk errors caught

On thousands of disks, bit rot and bad sectors happen. Checksum errors show up as WARN lines and DataNode metrics; the data is healed automatically, and repeated errors on one disk tell admins to replace it.

Bad sector→Checksum error→Replace replica, then disk

4. Verifying copies between clusters

After copying data to a DR cluster, teams compare hdfs dfs -checksum (or let DistCp do it) instead of reading terabytes back to compare.

Copy→Compare checksums→Proven identical

Simplified; organisations differ in tools and policies.
