1 The story

When the shell is not enough

The canteen app's backend, written in Java, must save every order batch into HDFS and read daily totals back. Riya's first version calls hdfs dfs -put from Java with Runtime.exec(). It works, but each call starts a new JVM: 1.8 seconds per batch, and errors arrive as text she has to parse. Arjun shows her that every hdfs dfs command is itself a small Java program built on one class, FileSystem, and her backend can use that class directly.

A> Everything you did with the shell, you can do from code: fs.create() is -put, fs.open() is -cat, fs.rename() is -mv. The JVM starts once, connections are reused, and errors are real Java exceptions. R> Is it different from writing a normal file? A> Almost the same streams you know from Java. The difference is what happens underneath: a create asks the NameNode, the bytes go through the write pipeline from Lesson 6.1, and open reads from the nearest DataNode as in Lesson 6.2. Spark and Hive use this same class, which is why they can read HDFS and S3 with the same code.
2 Definition

The Hadoop FileSystem API

Formal definition (write this in exams)

The Hadoop FileSystem API (org.apache.hadoop.fs) is the Java interface through which all Hadoop clients access storage. FileSystem.get(Configuration) returns an implementation chosen by the URI scheme of fs.defaultFS or of a Path; for hdfs:// it is DistributedFileSystem, which uses a DFSClient to call the NameNode over RPC and to stream data to and from DataNodes. Files are created with create() (returning an FSDataOutputStream that supports hflush() and hsync()) and read with open() (returning a seekable FSDataInputStream). Metadata is returned as FileStatus and block placement as BlockLocation; namespace operations include mkdirs, listStatus, rename and delete.

In simple words

A Java library that lets your program open, write, list, rename and delete HDFS files, the way the shell does, but inside your own application.

Words you'll meet in this lesson

API facts worth remembering

FileSystem.get(conf)Returns a cached, shared instance per scheme, authority and user; closing it closes it for the whole JVM
rename()Returns false on many failures instead of throwing: always check it
delete(path, true)Recursive and permanent: the API does not use the trash
create(path, true)true = overwrite an existing file
VisibilityOther readers see written data after hflush() or close()
Classpathhadoop classpath prints the jars to compile and run with
LEVELS> The API at three levels L1> Like Java file handling you already know
  • Path is like java.io.File, open()/create() give streams.
  • You wrap them in a BufferedReader or write bytes, as usual.
  • Always close streams (try-with-resources).
L2> Everyday use
  • Upload: fs.copyFromLocalFile(src, dst), or create() and write.
  • Check before reading: fs.exists(p), fs.getFileStatus(p).getLen().
  • Walk a tree: fs.listFiles(dir, true) (recursive iterator, includes block locations).
  • Publish results: write into a temporary folder, then one fs.rename().
L3> What library and framework authors care about
  • getFileBlockLocations is how MapReduce and Spark place tasks near data.
  • hflush() vs hsync(): visible to readers vs also forced to disk on DataNodes.
  • Seek + read lets a reader start in the middle of a file: that is how input splits work.
  • Use FileSystem.newInstance() if your code must close its own instance without affecting others.
  • On a secure cluster, the same code needs a Kerberos login (UserGroupInformation).
/LEVELS EXAM> “Write a Java program to read a file from HDFS.” Steps: create a Configuration; FileSystem fs = FileSystem.get(conf); FSDataInputStream in = fs.open(new Path(...)); read lines with a BufferedReader (or IOUtils.copyBytes(in, System.out, 4096, false)); close the stream. Mention that open() gets block locations from the NameNode and reads from DataNodes.

4 Step by step

Two real programs on the lab cluster

Both Java files are in “Run it on your PC” below. We compiled and ran them inside the namenode container, where Java and the Hadoop jars are already installed.

  1. Compile and package

    javac -cp $(hadoop classpath) HdfsBasics.java ItemCount.java
jar cf hdfs-demo.jar *.class
hadoop jar hdfs-demo.jar HdfsBasics
    Connected to: hdfs://namenode
    hadoop classpath lists every Hadoop jar. hadoop jar runs the class with that classpath and the cluster's configuration, so new Configuration() finds fs.defaultFS=hdfs://namenode and FileSystem.get() returns a DistributedFileSystem.

  2. Write and read back

    try (FSDataOutputStream out = fs.create(file, true)) {
    out.write("order_id,item,amount\n".getBytes(StandardCharsets.UTF_8));
    out.write("3001,samosa,18\n3002,chai,15\n".getBytes(StandardCharsets.UTF_8));
}
try (FSDataInputStream in = fs.open(file); BufferedReader r = ...) {
    while ((line = r.readLine()) != null) System.out.println("  read: " + line);
}
    read: order_id,item,amount read: 3001,samosa,18 read: 3002,chai,15
    create = NameNode create + addBlock; the bytes went through a 3-DataNode pipeline; closing the stream completed the file. open fetched block locations and streamed from a DataNode.

  3. Metadata and block locations

    FileStatus st = fs.getFileStatus(file);
for (BlockLocation b : fs.getFileBlockLocations(bs, 0, bs.getLen())) ...
    orders.csv 49 bytes replication 3 block size 128 MB owner hadoop block at offset 0 length 134,217,728 on ab3b1bedf98a, 46201bb62e68, 264eb9c0f8e2 block at offset 134,217,728 length 6,542,542 on ab3b1bedf98a, 46201bb62e68, 264eb9c0f8e2
    The hosts are Docker container IDs: datanode-1, datanode-2 and datanode-3. orders_x30.csv (140,760,270 bytes) has a full 128 MB block plus a 6.5 MB tail block. A job scheduler uses exactly this list to run tasks next to the data.

  4. List, rename, delete

    System.out.println("rename: " + fs.rename(file, renamed));
System.out.println("exists after rename: " + fs.exists(file));
System.out.println("delete: " + fs.delete(dir, true));
    ls: hdfs://namenode/user/hadoop/api_demo/orders.csv rename: true exists after rename: false delete: true
    Both return booleans. A rename to a missing parent folder returns false without an exception, so check it. delete(dir, true) removed the folder and the file permanently: the API skips the trash.

  5. Count items in one file

    hadoop jar hdfs-demo.jar ItemCount /user/hadoop/data/canteen_orders.csv
    chai 50,170 dosa 49,948 idli 49,984 poha 49,891 samosa 50,021 vada pav 49,986 took 1327 ms in one JVM
    300,000 orders (4.5 MB) streamed through one client in 1.3 seconds, including connecting. The program reads the file block after block like -cat does.

  6. Same program, 90× the data, and a bug

    hadoop jar hdfs-demo.jar ItemCount /user/hadoop/data/orders_x90.csv
    chai 4,515,300 dosa 4,495,320 idli 4,498,560 item 89 poha 4,490,190 samosa 4,501,890 vada pav 4,498,740 took 5890 ms in one JVM
    403 MB took 5.9 s: about 68 MB/s through one client. A 4 TB file would take about 17 hours this way, which is why MapReduce (Module 8) runs one reader per block in parallel. And “item 89”: orders_x90.csv was made by concatenating the file 90 times, so 89 header lines sit inside the data. HDFS stores bytes; cleaning data is the program's job.

  7. The same file over HTTP: WebHDFS

    curl -s "http://namenode:9870/webhdfs/v1/user/hadoop/canteen/raw/day1.csv?op=GETFILESTATUS&user.name=hadoop"
curl -s -i "http://namenode:9870/webhdfs/v1/user/hadoop/canteen/raw/day1.csv?op=OPEN&user.name=hadoop" | grep -iE "^HTTP|^Location"
    {"FileStatus":{"accessTime":1792579946689,"blockSize":134217728,"childrenNum":0,"fileId":16425,"group":"supergroup","length":47,"modificationTime":1792575484677,"owner":"hadoop","pathSuffix":"","permission":"640","replication":3,"storagePolicy":0,"type":"FILE"}} HTTP/1.1 307 Temporary Redirect Location: http://46201bb62e68:9864/webhdfs/v1/user/hadoop/canteen/raw/day1.csv?op=OPEN&user.name=hadoop&namenoderpcaddress=namenode:8020&offset=0
    The NameNode answers metadata itself but never sends file data: for OPEN it redirects (HTTP 307) to a DataNode (datanode-2, port 9864). The same split as the Java client, in plain HTTP.
WARN> Don't call fs.close() on the instance from FileSystem.get() in a long-running server: it is shared, and other parts of the application will start failing with “Filesystem closed”. Close streams, keep the FileSystem open (or use FileSystem.newInstance()). Our short demo programs close it on exit, which is fine.
5 See it happen

Six API calls, and who answers each

The calls from HdfsBasics, in order.

From Java call to NameNode and DataNodes 6 steps
What you see
  1. FileSystem.get reads the configuration and connects.
  2. create returns an output stream.
  3. Writing and closing stores the file.
  4. open returns an input stream.
  5. Reading prints the three lines.
  6. Rename and delete both return true.
Behind the screen
  1. The configuration's fs.defaultFS picks DistributedFileSystem, which wraps a DFSClient.
  2. create is one RPC to the NameNode: the file exists, still empty and open for writing.
  3. write + close: addBlock, the DataNode pipeline (Lesson 6.1), then complete.
  4. open asks the NameNode where the blocks are (Lesson 6.2).
  5. Reading streams bytes directly from a DataNode.
  6. rename and delete touch only the NameNode.
6 Real-world use

The API at work

1. Ingestion services

Services that collect events (from Kafka, logs or apps) keep an HDFS file open, write records and call hflush() regularly so readers see recent data, then roll to a new file every hour.

Events→create + write + hflush→Hourly files

2. Moving to the cloud

Teams migrating from on-premise Hadoop to cloud object stores often change only paths and configuration: Spark and Hive jobs keep working because they talk to the FileSystem abstraction.

hdfs:// paths→FileSystem API→s3a:// paths

3. Non-Java tools

Dashboards and Python scripts read result files through WebHDFS or HttpFS (a gateway that also hides the DataNodes), with no Hadoop installation on the client.

Python app→HTTP/JSON→HDFS

4. Housekeeping tools

Admins write small Java tools that walk the namespace once with listFiles(dir, true) to find small files, old data or wrong replication, far faster than thousands of shell calls.

listFiles→Filter in Java→Report or fix

Simplified; organisations differ in tools and policies.
