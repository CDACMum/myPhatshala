2 Definition

Scaling out and cluster sizing

{{RECAP}}
Formal definition (write this in exams)

Horizontal scaling (scaling out) increases a system's capacity by adding more nodes and spreading data and work across them, rather than making one machine larger. Cluster sizing (capacity planning) is the process of estimating how many nodes, and of what configuration, a cluster needs to meet its requirements for storage (data volume × replication factor + temporary space + free headroom), compute (tasks that must finish within a time window), memory and network, including expected growth over the planning period. The final size is set by whichever requirement needs the most nodes.

In simple words

Scaling out means adding more ordinary computers. Sizing means doing the maths first: how much disk do we really need after copies and spare room, how much CPU to finish the work in time, and how fast will it grow? Work out the nodes needed for each, and buy the biggest of those numbers.

Words you'll meet in this lesson

Raw capacityTotal disk in all nodes added together, before any copies.
Usable capacityWhat is left for business data after replication, temp space and headroom.
Replication factorHow many copies HDFS keeps of each block. Default: 3.
HeadroomFree space you keep on purpose (often 20–30%) so the cluster never runs full.
Temp (intermediate) spaceDisk used by jobs for in-between results, like map outputs. A common rule of thumb is about 25% of raw.
WaveOne round of tasks when there are more tasks than slots. 100 tasks on 40 slots = 3 waves.
BalancerAn HDFS tool that moves blocks from full nodes to emptier ones, for example after adding nodes.
Elastic scalingAdding and removing nodes as the load changes. Easy in the cloud.

The sizing formulas

Raw disk neededdata × replication ÷ (1 − temp share − headroom). With 3 copies, 25% temp and 25% headroom: data × 3 ÷ 0.5 = data × 6
Storage nodesraw disk needed ÷ disk per node, rounded up
Compute nodestotal task-minutes ÷ (time window × slots per node), rounded up
Final sizethe larger of storage nodes and compute nodes, plus spare nodes for failures
Growthdata after n years = today × (1 + growth rate)n
Compressionif data is stored compressed (for example 3× smaller as Parquet), divide the data size first

Rules of thumb vary by company and workload. These numbers are a sensible starting point, not a standard.

LEVELS> Sizing at three levels L1> The tiffin box shelf
  • You must store 200 tiffin boxes, and for safety you keep 3 identical copies of each: that's 600 boxes.
  • The kitchen also needs some shelf space for boxes that are being packed right now (temp space).
  • And you never fill shelves to the last inch, or you can't move anything (headroom).
  • So you need shelves for about six times the boxes you thought. That's cluster sizing in one line.
L2> Storage, compute and the bigger number
  • Storage-bound clusters keep years of data but run light jobs: size by disk.
  • Compute-bound clusters run heavy jobs on less data, or must finish in a short window: size by CPU slots.
  • Compute: if the nightly job is 6,000 task-minutes and each node runs 16 tasks at once, a 2-hour window needs 6,000 ÷ (120 × 16) ≈ 3.2, so 4 nodes worth of slots.
  • Then take the bigger of the two answers. Most Hadoop clusters end up storage-bound.
  • Add a few spare nodes so that losing one or two still meets the requirements.
L3> Trade-offs a senior engineer weighs
  • Many small nodes vs few big nodes: a node with 24 × 20 TB = 480 TB holds a lot, but when it dies, re-copying 480 TB of replicas takes many hours and heavy network use. Smaller nodes recover faster and spread load more evenly.
  • Disks vs cores: keep a sensible ratio (often around one or two disks per few cores) so jobs are not starved of disk bandwidth or CPU.
  • Erasure coding (Hadoop 3) can store cold data with about 1.5× overhead instead of 3×, cutting raw disk sharply for old data (Module 7).
  • Separate storage and compute: in the cloud, data often lives in object storage (S3, GCS, ADLS), and clusters are sized only for compute, then shut down after the job.
  • Diminishing returns: doubling nodes rarely halves job time exactly. The master, the shuffle and the slowest task add a fixed part (Amdahl's law).
/LEVELS EXAM> A typical exam or interview question: “You have X TB growing Y% a year, replication 3. How many nodes of Z TB do you need in 3 years?” Write the formula, show each step (growth → ×3 → temp + headroom → ÷ node size → round up), and state your assumptions.
3 Types and ways to use it

Ways to grow a cluster

Add worker nodes

The normal way to scale Hadoop. Install the DataNode and NodeManager, add the host to the topology script, start them. New nodes join while the cluster runs.

Scale out

Add disks to nodes

If nodes have empty disk slots, adding disks raises storage without new servers. Compute stays the same.

More storage

Bigger nodes

Replace old nodes with newer ones that have more cores, RAM and disk. Each node is “scaled up” while the cluster keeps scaling out.

Refresh

Elastic cloud nodes

Add task-only nodes for a busy night or a festive sale, then remove them. Storage can stay in object storage.

Pay per hour

Tiered storage

Move old, rarely used data to cheaper storage (archive disks, erasure coding, cloud archive), keeping fast disks for hot data.

Save cost

TIP> After adding nodes, run the HDFS balancer (hdfs balancer -threshold 10). New nodes start empty; new writes go everywhere, but old blocks stay where they were until the balancer moves them. Jobs on old data won't use the new nodes' disks until then.
4 Step by step

Size TiffinGo's cluster for the next three years

  1. Grow the data to the end of the planning period

    data_tb = 200 * 1.4 ** 3        # 200 TB growing 40% a year, for 3 years
print(round(data_tb), "TB in year 3")
    549 TB in year 3
    Growth compounds: 200 → 280 → 392 → 549 TB. Sizing for today's data only means buying again in a few months.

  2. Apply compression (if any)

    TiffinGo will store its clicks as compressed Parquet files, about 3× smaller: 549 ÷ 3 ≈ 183 TB on disk. Orders stay as they are. For simplicity, say 300 TB must be stored.

    Compression ratios depend on the data. Measure on a sample before you trust a number.

  3. Multiply by replication

    print(300 * 3, "TB of replicas")
    900 TB of replicas
    Each block is on three DataNodes, on at least two racks. Every TB of business data uses 3 TB of disk.

  4. Add temp space and headroom

    raw = 900 / (1 - 0.25 - 0.25)   # 25% temp space, 25% free headroom
print(raw, "TB raw disk")
    1800.0 TB raw disk
    Half of each disk is reserved for in-between job data and safety margin. Running HDFS close to 100% full causes failed writes and slow jobs.

  5. Turn disk into nodes

    import math
print(math.ceil(1800 / 144), "storage nodes of 144 TB")
    13 storage nodes of 144 TB
    Always round up: 12.5 nodes means 13.

  6. Check compute, then pick the bigger number

    The nightly report is 9,000 task-minutes; each node runs 16 tasks at once; the window is 2 hours. 9,000 ÷ (120 × 16) = 4.7, so 5 nodes are enough for compute. Storage needs 13, so storage wins.

    Add 2 spare nodes so that a failure or two doesn't break the plan: 15 nodes, which fit in 2 racks of 8 (better for rack awareness than 1 rack). Kabir has his answer, with every assumption written down.
5 See it happen

Adding nodes to a full cluster: the dashboard, and what the blocks do

TiffinGo's cluster is getting full. Watch the admin add three nodes. Left: the dashboard. Right: where the blocks are.

Scaling out a running cluster 6 steps
What you see
  1. The dashboard turns red: HDFS is 86% full on 6 nodes. Time to scale out.
  2. Three new nodes are installed and started. Overall usage drops to about 57%.
  3. But the old nodes are still 86% full and the new ones are empty. The nightly report is no faster.
  4. The admin runs the HDFS balancer, which moves blocks to the new nodes until every node is within 10% of the average.
  5. Now the report's tasks are spread over 9 nodes: it drops from 96 to 64 minutes.
  6. Half again as many nodes gave about a third less time, not half: part of the job doesn't split. (Times here are illustrative.)
Behind the screen
  1. Six DataNodes, each 86% full. Writes start failing on the fullest nodes soon.
  2. Three new DataNodes start, register with the NameNode and report zero blocks.
  3. HDFS sends new blocks to all nodes, but existing blocks stay where they are. Old data is still read from only six nodes.
  4. The balancer copies blocks from over-full nodes to under-full ones and deletes the old copies, slowly, so jobs are not disturbed.
  5. All nine nodes now hold about the same share. Tasks for old data can run on any of them.
  6. Reads, writes and processing are spread over more disks and more cores. That is scaling out working.

6 Real-world use

Where sizing decisions are made

1. The yearly hardware budget

On-premises teams (banks, telecoms, government) size clusters once or twice a year, because buying servers takes weeks or months. They forecast data growth and new projects, then order nodes in batches.

Growth forecast→Sizing sheet→Purchase order

2. Festive sales and big cricket matches

E-commerce and streaming companies see traffic jump many times for a few days. In the cloud they add extra task nodes for those days and remove them after, instead of owning hardware for the peak all year.

Peak forecast→Temporary nodes→Remove after

3. Cloud: size compute, not storage

With data in object storage, a managed cluster (such as Amazon EMR or Google Dataproc) is sized just for the job, often with autoscaling, and deleted when the job ends. You pay for storage and for compute hours separately.

Data in object store→Cluster for 2 hours→Shut down

4. Hot, warm and cold data

A telecom may keep call records for years for regulation, but only the last few weeks are queried often. Old data moves to cheaper, denser storage (or erasure-coded HDFS), so the expensive nodes are sized for hot data only.

New data (hot)→Age policy→Archive tier (cold)

5. Adding nodes without downtime

Platform teams add nodes to live clusters regularly: install, add to the topology, start the services, then run the balancer at low speed overnight. Users keep working throughout. You'll do it in Module 12.

New servers→Join + balancer→Bigger cluster

Examples are simplified; figures in this lesson are illustrative. Real sizing also considers licences, support contracts, staff and data-centre limits.
