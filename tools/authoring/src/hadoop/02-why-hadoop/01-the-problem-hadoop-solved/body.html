1 The story

BharatSearch: a search engine on four laptops

For their hackathon, Riya and Kabir build “BharatSearch”, a search engine for college websites. A crawler downloads pages, a program builds an index of words, and a web page answers searches. It works beautifully for 500 colleges. Then the judges say: “Nice. Now do it for every website in India.” Riya opens a calculator, and goes quiet.

R> Sir, billions of pages won't fit on any disk we have. And even if they did, building the index would take months. A> This is almost exactly the problem web search companies faced around 2003. The web was exploding. They needed to store it, process it every few days, and do it on thousands of cheap machines that kept breaking. K> Couldn't they just split the pages over many machines with a script? Machine 1 gets URLs starting with A, machine 2 with B… A> People did. And then a machine died in the middle of the night, and someone had to find which pages were lost, rerun the script, fix the split when they added machines… Every team was writing the same messy plumbing again and again. R> So the real problem wasn't search. It was store huge data, process it in parallel, and survive failures, without every programmer becoming a distributed-systems expert. A> Exactly, Riya. That problem is what Hadoop was built to solve. Today you'll pin it down precisely, see why the tools of that time couldn't do it, and then answer the question every student asks me: is Hadoop still worth learning in 2026?
2 Definition

The problem Hadoop solved

Formal definition (write this in exams)

By the early 2000s, organisations needed to store and process data sets far larger than any single machine (hundreds of terabytes to petabytes of web pages, logs and clicks) economically, using clusters of commodity servers. This required: (1) scalable, reliable distributed storage that keeps working when disks and nodes fail; (2) parallel batch processing that runs close to the data; (3) automatic fault tolerance for long-running jobs; and (4) a simple programming model that hides distribution, so ordinary developers can write jobs. Apache Hadoop is an open-source framework that provides these: HDFS for storage, MapReduce for processing and, from version 2, YARN for resource management.

In simple words

Data became too big for one computer. Companies needed a way to spread it over thousands of cheap machines, crunch all of it in parallel, keep going when machines break, and let normal programmers write the code without worrying about any of that. Hadoop is the free, open-source software that does exactly this.

The four requirements, and Hadoop's answer

Store data bigger than any machineHDFS: files split into blocks spread over many nodes
Survive failures of cheap hardwareReplication (3 copies), heartbeats, automatic re-replication and task retries
Process all of it in parallel, fastMapReduce: many tasks at once, each next to its data (data locality)
Let ordinary programmers write jobsWrite two functions, map and reduce; the framework handles everything else
And keep it affordableRuns on commodity servers; free, open-source licence (Apache 2.0)
LEVELS> The problem at three levels L1> The wedding caterer
  • Cooking for 50 guests: one kitchen, one cook. Easy.
  • Cooking for 50,000 guests: you need many kitchens, many cooks, a way to split the menu, a way to replace a cook who falls sick, and a head chef who coordinates it all.
  • Building that system from scratch for every wedding would be madness. A catering company has it ready: you just give the recipe.
  • Hadoop is that catering company for data. You give the recipe (map and reduce); it brings the kitchens (cluster) and the coordination.
L2> Why the usual tools of 2003 didn't fit
  • Big databases needed data cleaned into tables first, scaled up rather than out, and cost a lot per TB in licences and hardware.
  • Central storage (SAN/NAS) held a lot, but every server pulled data across the network from one place: the network became the bottleneck.
  • Supercomputing (MPI) was fast, but programmers had to handle splitting data, moving it and recovering from failures themselves.
  • Home-grown scripts (manual sharding) worked until a machine died or a new one was added, then needed manual repair.
L3> The design bets Hadoop made
  • Throughput over latency: read whole files fast in large sequential chunks; don't optimise for small random reads or instant answers.
  • Write once, read many: files are written once and appended to, not edited in the middle. This keeps replication simple.
  • Move computation to data instead of pulling data to a central place.
  • Failure is normal: handle it in software, so hardware can be cheap.
  • Simple, restricted programming model: by limiting what a job can express (map then reduce), the framework can split, schedule and retry automatically.
  • These bets are also why Hadoop is not good at some things: low-latency queries, many small files, and fast iterative jobs. Spark and other tools later filled those gaps.

Is Hadoop still relevant in 2026? An honest answer

Still running

Many banks, telecoms, government bodies and large enterprises still run on-premises Hadoop clusters (HDFS, YARN, Hive), often for years of historical data and compliance.

Jobs exist

Partly replaced

Classic MapReduce jobs have largely been replaced by Spark (and Hive on Tez). New cloud projects often store data in object storage (S3, GCS, ADLS) instead of HDFS.

Know the shift

Ideas everywhere

Blocks, replication, data locality, master–worker, shuffle and YARN-style scheduling are the foundations of Spark, Kafka, cloud data platforms and lakehouses.

Concepts transfer

Interviews and migrations

Data engineering interviews still ask about HDFS, MapReduce and YARN, and many current projects are migrations from Hadoop, which need people who understand it.

Career value
TIP> Learn Hadoop as the foundation, not the destination. Once you understand HDFS, MapReduce and YARN, Spark, Hive, cloud data warehouses and lakehouse tables become much easier, because they solve the same problems with the same ideas. This course ends with exactly that bridge (Module 13).
4 Step by step

Scaling BharatSearch by hand, and where each step hurts

  1. Too big for one disk: split by a rule

    import zlib
def machine_for(url, machines):
    return zlib.crc32(url.encode()) % machines     # a stable hash of the URL
print(machine_for("https://iitb.ac.in", 4), machine_for("https://coep.org.in", 4))
    2 1
    A hash spreads URLs evenly over 4 machines. Every program that reads or writes a page must know this rule. That is manual sharding.

  2. Add a fifth machine

    Now % 5 instead of % 4. Most URLs suddenly belong to a different machine.

    With modulo hashing, about 80% of the pages must be moved when going from 4 to 5 machines (you'll measure it in the code below). Someone has to write and run that migration.

  3. A disk dies at 2 am

    Machine 3's disk fails. A quarter of the pages are gone, and the indexing job that was reading them crashes.

    No copies, no automatic detection, no retry. The team re-crawls those pages and re-runs the whole job by hand.

  4. Build the index in parallel

    Kabir writes a script that starts the indexer on each machine, waits, collects results and merges them.

    He is now writing a scheduler, a progress tracker and a merge step: the same distributed plumbing every team rebuilds. Hadoop's MapReduce provides all of it.

  5. The realisation

    The interesting code (parse a page, count words) is 50 lines. The plumbing (splitting, copying, retrying, merging) is thousands.

    Hadoop's promise: you write the 50 lines. Storage, splitting, placement, parallelism and recovery come from the framework, tested on clusters of thousands of nodes.
5 See it happen

Growing from 1 machine to 40: what the team sees, and what is really happening

Follow BharatSearch as the data grows. Left: the team's chat and screens. Right: the machines and the data.

Scaling without Hadoop, then with it 6 steps
What you see
  1. Small data, one laptop: the index is built in 20 minutes. Life is good.
  2. The crawl reaches 50 TB. Kabir splits it over 4 machines by hashing each URL.
  3. At 2 am a disk fails. A quarter of the pages are gone and the indexer crashes at 71%.
  4. Adding a fifth machine forces most data to move. Riya's home-made retry script keeps growing.
  5. Arjun Sir's advice: store pages in HDFS and express the indexing as map and reduce.
  6. On 40 nodes the job finishes despite two node failures, with no data lost. The plumbing code is gone. (Numbers are illustrative.)
Behind the screen
  1. All data on one laptop. No distribution, no problems.
  2. Four machines, each holding a quarter of the pages. Exactly one copy of each page.
  3. m3's disk fails: its quarter of the pages is simply gone, and the job depending on it fails.
  4. Adding m5 changes the hash rule, so most pages must move to new homes. All of this is done by hand.
  5. With Hadoop, the framework takes over storage, replication, scheduling, retries and merging. The team writes only map and reduce.
  6. Two of 40 nodes die during the job. Other replicas are read and the lost tasks re-run. The job completes.

6 Real-world use

The same problem, in many industries

1. Web search and crawling

The original problem: crawl and index the web. Hadoop grew out of an open-source web search project (Apache Nutch) and was scaled up at Yahoo! for its search data.

Crawled pages→HDFS + MapReduce→Search index

2. Clickstream and app logs

Shopping, food delivery and streaming apps record every tap. Storing all of it cheaply and analysing it in bulk (funnels, recommendations, A/B tests) is the same store-process-survive problem.

App events→Cheap scalable storage→Daily analytics

3. Telecom call detail records

A telecom operator with crores of users produces billions of call and data records. Regulation requires keeping them, and network planning needs them analysed: a classic Hadoop workload.

CDRs→Years in HDFS→Planning and compliance

4. Banking risk and fraud analytics

Banks keep years of transactions for risk models and audits. Many built Hadoop data lakes so that raw data from many systems lands in one place before being modelled.

Many source systems→Data lake→Risk reports

5. Science and government

Genome sequencing, satellite imagery and census-scale data share the same need: store huge data sets and run the same analysis on every part in parallel.

Huge data set→Same code on every part→Results

Examples are simplified and describe common patterns, not any one company's setup.
