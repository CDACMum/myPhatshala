1 The story

“Don't log in to the NameNode!”

On his third day, Kabir needs to run a quick script on the cluster. He finds the host name of the biggest, most powerful server, the NameNode, logs in to it, and starts a Python job that reads a large file into memory. Five minutes later the whole team's chat lights up: “HDFS is slow!”, “NameNode GC pauses!”, “Who is on nn1?” His lead calls him over, calm but firm.

A> Kabir, which machine did you use? K> The one with the most RAM… nn1. I thought it would be fastest. A> It is the most important machine in the cluster. The NameNode keeps all of HDFS's metadata in its memory. Your script took memory and CPU from it, so it paused, and every user's reads and writes waited. R> So where should he have run it? A> On an edge node, the machine built for people. Every cluster has roles: masters that coordinate and must be protected, workers that store and compute and are managed by YARN, utility nodes for supporting services, and edge nodes where users and tools connect. Today you'll learn each role, what runs on it, and how companies lay them out for small and large clusters. K> And I'll never touch nn1 again.
2 Definition

Node roles in a Hadoop cluster

Formal definition (write this in exams)

Nodes in a Hadoop cluster are assigned roles according to the services they run. Master nodes host the coordinating daemons (NameNode and its standby, ResourceManager, JobHistory Server, and in HA setups JournalNodes and ZKFCs) and are provisioned for reliability. Worker nodes (historically “slave” nodes) host DataNodes and NodeManagers and provide the cluster's storage and compute capacity. Edge nodes (also called gateway or client nodes) host client libraries, configuration and tools, and are the controlled entry point for users and applications; they run no core daemons. Utility (management) nodes host supporting services such as ZooKeeper, the Hive Metastore and its database, HiveServer2, Oozie, security and cluster-management servers.

In simple words

Masters are the managers: few, important, protected. Workers are the staff: many, doing the storage and processing. Edge nodes are the reception desk where people come in to submit work. Utility nodes run the helper services everyone else depends on. Users only ever log in at reception.

LEVELS> Roles at three levels L1> A hospital again
  • Masters = the records office and the bed manager. If they stop, everyone stops, so nobody else is allowed to use their desks.
  • Workers = the wards, where the actual work happens. There are many, and one can close for repairs.
  • Edge node = reception. Visitors come here, not into the records office or the operating theatre.
  • Utility = the pharmacy and the IT room: support services the whole hospital relies on.
L2> What runs where in a typical medium cluster
  • master1: active NameNode, ZKFC, JournalNode, ZooKeeper.
  • master2: standby NameNode, ZKFC, JournalNode, ZooKeeper, ResourceManager.
  • master3 / utility: JournalNode, ZooKeeper, standby ResourceManager, JobHistory Server, Hive Metastore + database, HiveServer2.
  • edge1–2: HDFS/YARN/Hive/Spark clients, Hue or Jupyter, scheduler workers; user logins.
  • worker1–N: DataNode + NodeManager (and, for HBase, a RegionServer).
  • The three JournalNodes and three ZooKeeper servers sit on three different machines so the cluster survives losing any one of them.
L3> Why roles are kept separate
  • Blast radius: a user's runaway process on a master can pause the NameNode (long Java garbage-collection pauses) and stall the whole cluster.
  • Resource accounting: work on workers must go through YARN so it is counted, queued and limited. A script started by hand on a worker steals memory YARN thinks is free, and containers get killed.
  • Security: only edge nodes are reachable from the corporate network; masters and workers sit on a private cluster network. Users get Kerberos tickets on the edge node.
  • Upgrades and failures: workers are replaced like identical parts; masters are changed carefully, one at a time, with failover.
  • Cloud versions: managed services keep the same roles: Amazon EMR has a primary node, core nodes (HDFS + YARN) and task nodes (YARN only); Google Dataproc has master and worker nodes plus optional secondary workers.

4 Step by step

Designing the roles for a 30-node cluster

  1. Decide what must be highly available

    TiffinGo's dashboards depend on HDFS all day, so they want NameNode and ResourceManager HA.

    HA means two NameNodes, two ResourceManagers, three JournalNodes and three ZooKeeper servers, spread over three machines so any one can fail.

  2. Place the masters

    masters = {
    "m1": ["NameNode (active)", "ZKFC", "JournalNode", "ZooKeeper"],
    "m2": ["NameNode (standby)", "ZKFC", "JournalNode", "ZooKeeper", "ResourceManager"],
    "m3": ["JournalNode", "ZooKeeper", "ResourceManager (standby)", "JobHistoryServer"],
}
print(sum(1 for roles in masters.values() if "JournalNode" in roles), "JournalNodes")
    3 JournalNodes
    Put m1, m2 and m3 on different racks and power feeds. The active NameNode gets the lightest load of other services.

  3. Add utility services

    Hive Metastore with its database and HiveServer2 go on a utility node (or on m3 in a small cluster).

    The metastore database holds every table definition: back it up and give it a standby, or every Hive and Spark SQL query stops.

  4. Add edge nodes

    Two edge nodes with the client configuration, Hive Beeline, spark-submit, Jupyter and the Airflow workers.

    Two, so users can keep working while one is patched. Only these two are reachable from the office network.

  5. Everything else is a worker

    total, masters, utility, edge = 30, 3, 1, 2
print(total - masters - utility - edge, "workers (DataNode + NodeManager)")
    24 workers (DataNode + NodeManager)
    The workers provide all storage and compute, so capacity planning (Lesson 1.3) is done on these 24, not on all 30.
5 See it happen

One Hive query: what Riya does on the edge node, and which role does what

Riya runs a SQL query from the edge node. Left: her screen. Right: the request travelling through each kind of node.

A query through every role 6 steps
What you see
  1. Riya logs in to edge1 and connects Beeline (the Hive client) to HiveServer2.
  2. She types a GROUP BY query on the orders table.
  3. The query is running. She sees only a progress message.
  4. Progress shows map and reduce tasks. They run somewhere on the cluster, not on her machine.
  5. The result table appears.
  6. From start to finish, Riya used only the edge node. Every other role worked on her behalf.
Behind the screen
  1. The edge node runs only the client (Beeline). It sends the query to HiveServer2 on the utility node over JDBC (port 10000 by default).
  2. HiveServer2 asks the Hive Metastore (also on the utility node, backed by a database) where the orders table lives in HDFS and what its columns are.
  3. It then talks to the masters: the NameNode for the files' block locations, the ResourceManager to start an ApplicationMaster for the query.
  4. Map and reduce tasks run in containers on the workers, mostly on the nodes holding the table's blocks.
  5. Results flow back through HiveServer2 to Riya's Beeline session on the edge node.
  6. Every role did one job. None of the work ran on the edge node or on a master.

6 Real-world use

Roles in real platforms

1. Cluster managers assign roles

In Cloudera Manager or Apache Ambari, an admin builds a cluster by assigning roles to hosts (“NameNode on m1”, “DataNode on all workers”, “Gateway on edge1”). The tool installs, configures and monitors each role.

Host list→Role assignment→Running cluster

2. Cloud clusters keep the same roles

Amazon EMR has a primary node (masters), core nodes (HDFS + YARN) and task nodes (YARN only, safe to remove). Google Dataproc has master and worker nodes, with optional secondary (preemptible) workers that add compute only.

Primary→Core (data + compute)→Task (compute only)

3. Data science on edge nodes

Analysts open Jupyter or Hue on an edge node and submit Spark or Hive work to YARN. Their notebooks never run heavy processing on the edge itself; the cluster does it.

Notebook on edge→spark-submit / Hive→Workers compute

4. Incident reviews

A common root cause in incident reports: “a user ran a script on a master” or “a manual process on workers exhausted memory, so YARN killed containers”. The fix is usually access control: logins only on edge nodes.

Outage→Root cause: wrong role→Restrict logins

5. Quorum services on separate machines

ZooKeeper and JournalNodes are always placed on three (or five) different machines and racks, so the majority survives a failure. Putting all three on one host is a classic design-review mistake.

3 hosts→Majority of 2→Survives 1 failure

Simplified. Exact role layouts differ by distribution and company.
