2 Definition

The write path, the read path and the job lifecycle

Formal definition (write this in exams)

The HDFS write path: the client asks the NameNode to create the file; for each block it calls addBlock, receives a block ID and a list of target DataNodes chosen by the placement policy, and streams the data as packets through a pipeline of those DataNodes, each storing and forwarding the packet and returning acknowledgements; finally the client calls complete. The read path: the client calls open, receives the block locations sorted by network distance, and reads each block directly from the closest DataNode, verifying checksums. The job lifecycle on YARN: the client computes input splits, copies the job resources to HDFS and submits the application to the ResourceManager; the RM launches an ApplicationMaster, which requests containers (preferably on nodes holding each split), runs map tasks, lets reducers shuffle and merge map outputs, runs reduce tasks that write output to HDFS, commits the output and unregisters from the RM.

In simple words

Writing a file: ask the NameNode “where should block 1 go?”, send it to three DataNodes in a chain, repeat for each block, then tell the NameNode “done”. Reading: ask the NameNode “where are the blocks?”, then fetch each block from the nearest DataNode. Running a job: hand the job to the ResourceManager, which starts a small manager for your job; that manager runs map tasks next to the data, gathers their results to reducers, and writes the answer back into HDFS.

Words you'll meet in this lesson

PipelineThe chain of DataNodes (usually 3) a block is written through: client → DN1 → DN2 → DN3.
PacketA small piece of a block (64 KB by default) sent through the pipeline. Each packet is acknowledged.
LeaseA lock the NameNode gives one writer, so only one client writes a file at a time.
Staging directoryA folder in HDFS where the client puts the job's jar, configuration and split list before submitting.
MRAppMasterMapReduce's ApplicationMaster: plans and supervises one job's tasks.
SpillWhen a map task's in-memory buffer fills (80% of 100 MB by default), its sorted contents are written to local disk.
Output committerMoves task outputs from a temporary folder to the final output folder only when tasks succeed.
_SUCCESSAn empty file written into the output directory when a MapReduce job completes successfully.

LEVELS> The two lives at three levels L1> A courier and a census
  • Writing a file is like sending a parcel by courier with three copies: the head office (NameNode) tells you which three branches, you hand it to the first branch, and each branch passes a copy on to the next.
  • Reading a file: ask head office which branches have your parcels, and collect each from the nearest one.
  • Running a job is like a census: the government (ResourceManager) appoints a supervisor (ApplicationMaster), the supervisor sends counters (map tasks) to every area, area totals go to district officers (reducers), and the final report is filed (written to HDFS).
L2> The RPC calls you would see in a trace
  • Write: create() → addBlock() (per block) → data streamed to DataNodes → complete().
  • Read: getBlockLocations() (in batches) → data read from DataNodes → checksums verified on the client.
  • Job: getNewApplication() → upload jar/conf/splits to the staging directory → submitApplication() → RM starts the AM → AM registerApplicationMaster() → repeated allocate() calls (container requests and grants) → startContainers() on NodeManagers → finishApplicationMaster().
  • The NameNode only ever sees small metadata calls; the ResourceManager only sees resource requests. All heavy data moves between DataNodes, tasks and NodeManagers.
L3> Where things go wrong, and how each step recovers
  • A DataNode in the write pipeline dies: the client removes it, finishes the block on the remaining nodes with a new generation stamp, and the NameNode re-replicates later.
  • A replica is corrupt during a read: checksum mismatch → the client reads another replica and reports the bad one.
  • The client dies mid-write: its lease expires; the NameNode recovers the last block and closes the file.
  • A map or reduce task fails: the AM retries it (up to 4 attempts). The AM itself fails: YARN restarts it (MapReduce allows 2 AM attempts by default) and it recovers completed tasks.
  • The output directory already exists: the job is rejected at submission (FileAlreadyExistsException) to protect old results.
/LEVELS EXAM> “Explain the anatomy of a file write in HDFS” and “anatomy of a file read” are among the most frequent university questions. Number the steps (create → addBlock → pipeline + acks → complete; open → getBlockLocations → read nearest → checksum) and draw client, NameNode and three DataNodes with arrows. 4 Step by step

Riya's 300 MB file and her job, every step

  1. Write: create the file

    hdfs dfs -put canteen_orders.csv /data/
    The client calls create("/data/canteen_orders.csv") on the NameNode, which checks permissions and that the file doesn't exist, adds it to the namespace as “under construction” and gives the client a lease.

  2. Write: three blocks, three pipelines

    import math
size_mb, block_mb = 300, 128
print(math.ceil(size_mb / block_mb), "blocks; last block", size_mb - 2 * block_mb, "MB")
    3 blocks; last block 44 MB
    For each block the client calls addBlock; the NameNode picks 3 DataNodes on 2 racks. The data streams as 64 KB packets: client → DN1 → DN2 → DN3, with acks flowing back. The last block uses only 44 MB of disk, not 128.

  3. Write: close

    After the last packet is acknowledged, the client calls complete(). The file is now visible and readable.

    The DataNodes also tell the NameNode “I received block X” so its block map is up to date.

  4. Job: submit

    hadoop jar orders.jar ItemTotals /data/canteen_orders.csv /out/item_totals
    The client checks that /out/item_totals does not exist, computes 3 input splits (one per block), uploads the jar, configuration and split list to a staging directory in HDFS, and submits the application to the ResourceManager.

  5. Job: the ApplicationMaster takes over

    The ResourceManager starts the MRAppMaster in a container on some worker. The AM reads the split list and asks for 3 map containers, naming the nodes that hold each block.

    The RM grants containers (ideally node-local); NodeManagers launch the map tasks. Each map sorts its output in memory, spills to local disk, and merges the spills into one partitioned file.

  6. Job: shuffle, reduce, commit

    Reducers fetch their partition from every map's NodeManager, merge-sort them, run the reduce function and write part-r-00000 into a temporary folder.

    When all tasks succeed, the output committer moves the files into /out/item_totals and writes _SUCCESS. The AM unregisters and exits; the job's history goes to the JobHistory Server. The output file is written through the same pipeline as step 2.
5 See it happen

The life of a file: what Riya types, and every message behind it

Riya writes a 300 MB file and reads it back. Left: her terminal. Right: the client, the NameNode and four DataNodes.

Write and read a file 7 steps
What you see
  1. Riya runs hdfs dfs -put. Nothing visible happens yet, but the client is already talking to the NameNode.
  2. The upload starts. Block 1 (128 MB) is being written.
  3. Block 2 is being written. Each block goes to a different set of three DataNodes.
  4. The last block (44 MB) finishes. The command returns.
  5. hdfs dfs -ls -h shows the file with replication 3 and size 300 MB.
  6. Riya reads the file back with -cat.
  7. The first lines appear. The bytes came from DataNodes, not from the NameNode.
Behind the screen
  1. The client asks the NameNode to create the file. The NameNode checks permissions, records the new file and grants a lease (a write lock).
  2. addBlock: the NameNode chooses DN1, DN3, DN4 for block 1. The client streams packets to DN1, which forwards to DN3, which forwards to DN4. Acknowledgements flow back along the chain.
  3. For block 2 the client asks again and gets a different set of DataNodes: a new pipeline per block.
  4. The small last block is written, then the client calls complete. The lease is released.
  5. The file is closed: 3 blocks × 3 replicas spread over 4 nodes and 2 racks. The NameNode stores only where they are.
  6. Reading: the client calls getBlockLocations. The NameNode returns each block's DataNodes, sorted closest first.
  7. The client reads block 1 straight from the nearest DataNode, verifies its checksums, and moves on to block 2.

6 Real-world use

The life of a job, and where these journeys matter

Real-time scenario

The life of Riya's job, from submit to _SUCCESS

Follow hadoop jar orders.jar ItemTotals through YARN and MapReduce, one stage at a time.

The life of a job 6 steps
Animated example
  1. Submit: the client checks the output path, computes 3 splits, uploads the jar, configuration and split list to an HDFS staging directory, and submits the application to the ResourceManager.
  2. Start the AM: the RM finds a free container and asks that NodeManager to launch the MRAppMaster. The application moves from ACCEPTED to RUNNING.
  3. Map: the AM requests one container per split, naming the nodes that hold each block. Three map tasks start, each reading its local block.
  4. Sort and spill: each map writes its output to an in-memory buffer, sorts it by key and spills it to the node's local disk, partitioned for the reducers.
  5. Shuffle and reduce: the reducer fetches its partition from every map's NodeManager over HTTP, merges them in key order and runs the reduce function.
  6. Commit: the reducer's output is written to HDFS and committed; _SUCCESS appears. The AM unregisters and the job's history goes to the JobHistory Server.

Where knowing these journeys pays off

1. Reading error messages correctly

Each step has typical errors: permission denied at create, “could only be written to 0 of the 1 minReplication nodes” at addBlock (no healthy DataNodes), FileAlreadyExistsException at job submission. Knowing the step tells you where to look.

Error→Which step failed?→Right fix

2. A job stuck in ACCEPTED

An application that stays ACCEPTED is waiting for a container for its ApplicationMaster: the queue is full or the AM's memory request doesn't fit any node. Understanding the lifecycle turns a mystery into a queue-capacity question.

Stuck job→No AM container yet→Check queue / memory

3. Pipelines that wait for _SUCCESS

Workflow tools (Airflow, Oozie) often start the next step only when the previous job's output folder contains _SUCCESS, so half-written output is never consumed.

Job A→_SUCCESS appears→Job B starts

4. Tuning ingestion speed

Write throughput depends on the pipeline: the slowest of the three DataNodes and the cross-rack hop. Ingestion teams write many files in parallel from several clients to keep all DataNodes busy.

Many writers→Many pipelines→Full cluster bandwidth
