1 The story

Who decides the value: the jar, the file, or you?

Kabir's Docker cluster has dfs.replication=3 in its settings. He uploads a file with -D dfs.replication=2 and gets 2 copies. Then he marks the setting final, sure it can't be changed now, uploads again with -D dfs.replication=2, and still gets 2. Riya asks: “If a final setting can be changed, what does final even mean?”

A> Think of it in layers. Hadoop ships with a default for every one of its settings, inside its jar files. Your *-site.xml files override those defaults. And a client or job can set a value on top, for its own work, with -D. K> And final? A> final protects a value against configuration files loaded later, for example the job.xml that comes with every submitted job. Your -D didn't load a file; it set the value directly in your own client, so it still won. That's exactly what we saw: 2 copies. R> So how do I know which value a daemon is really using? A> Ask it. Each daemon's web UI has a /conf page that lists every setting and which file it came from. Today: the files in etc/hadoop, the layers, the settings you'll change most, and the web UIs you'll open every day.
2 Definition

Hadoop configuration and web UIs

Formal definition (write this in exams)

Hadoop configuration is a set of name–value properties loaded in layers by the Configuration class: read-only defaults (core-default.xml, hdfs-default.xml, yarn-default.xml, mapred-default.xml, packaged in the jars), then site files in $HADOOP_CONF_DIR (by default $HADOOP_HOME/etc/hadoop: core-site.xml, hdfs-site.xml, yarn-site.xml, mapred-site.xml), then values set by programs or on the command line (-D). A later resource overrides an earlier one unless the earlier one marked the property <final>true</final>. Shell scripts (hadoop-env.sh, yarn-env.sh, mapred-env.sh) set environment variables such as JAVA_HOME and heap sizes; workers lists worker hosts. Each daemon also runs an embedded web server (NameNode 9870, DataNode 9864, ResourceManager 8088, NodeManager 8042, JobHistory Server 19888) with status pages and the /conf, /jmx and /logs endpoints.

In simple words

Hadoop has a default for everything. You change what you need in four XML files. A single command can change a setting just for itself. And every daemon has a web page where you can see its state and the settings it is really using.

LEVELS> Configuration at three levels L1> School rules, class rules, today's rule
  • The school rulebook (defaults) covers everything: “uniform every day”.
  • Your class teacher (site files) can change some rules for the class: “sports shoes on Friday”.
  • For one event (-D), a rule can change for that day only.
  • A rule marked final by the principal can't be changed by a later notice from a teacher.
L2> The files in etc/hadoop
  • core-site.xml: settings shared by everything (default file system, I/O, security).
  • hdfs-site.xml: NameNode and DataNode (replication, block size, storage folders, addresses).
  • yarn-site.xml: ResourceManager and NodeManagers (hosts, memory and cores per node, shuffle service).
  • mapred-site.xml: MapReduce jobs (framework, task memory, history server).
  • hadoop-env.sh / yarn-env.sh / mapred-env.sh: environment (Java, heap sizes, log and PID folders).
  • workers (hosts), capacity-scheduler.xml (YARN queues), log4j.properties (logging).
L3> Rules that matter in production
  • Server vs client settings: dfs.replication and dfs.blocksize are applied by the client that writes a file; changing the NameNode's file does not change existing files or other clients.
  • Restart to apply: daemons read their site files at start-up. Some settings can be refreshed (hdfs dfsadmin -refreshNodes, yarn rmadmin -refreshQueues); most need a restart.
  • Same files everywhere: every node must have the same configuration; cluster managers push it and track versions.
  • final is for administrators protecting cluster-wide values from job configurations (job.xml), not a lock against code running in the same client.
  • Values can use ${other.property} and ${env.VAR}; units such as 256m or 30s are accepted by many properties.
/LEVELS EXAM> For “Explain Hadoop configuration files”, list the four site files with one example property each (fs.defaultFS, dfs.replication, yarn.resourcemanager.hostname, mapreduce.framework.name), mention hadoop-env.sh (JAVA_HOME) and workers, and state the rule: site files override the defaults, and final properties cannot be overridden by later resources.

4 Step by step

Inspect and change configuration on a running cluster

All outputs are from the Docker practice cluster of Lesson 4.3 (Hadoop 3.5.0, 3 DataNodes). On the Path A install, drop the docker compose exec namenode prefix.

  1. See the files

    ls $HADOOP_HOME/etc/hadoop
    capacity-scheduler.xml kms-log4j.properties configuration.xsl kms-site.xml container-executor.cfg log4j.properties core-site.xml mapred-env.cmd hadoop-env.cmd mapred-env.sh hadoop-env.sh mapred-queues.xml.template hadoop-metrics2.properties mapred-site.xml hadoop-policy.xml shellprofile.d hadoop-user-functions.sh.example ssl-client.xml.example hdfs-rbf-site.xml ssl-server.xml.example hdfs-site.xml user_ec_policies.xml.template httpfs-env.sh workers httpfs-log4j.properties yarn-env.cmd httpfs-site.xml yarn-env.sh kms-acls.xml yarn-site.xml kms-env.sh yarnservice-log4j.properties
    32 entries ship in etc/hadoop. The four site files, the env scripts and workers are the ones you'll edit; the rest configure optional services (KMS, HttpFS, router-based federation).

  2. Ask for the value Hadoop really uses

    docker compose exec namenode hdfs getconf -confKey fs.defaultFS
docker compose exec namenode hdfs getconf -confKey dfs.replication
docker compose exec namenode hdfs getconf -confKey dfs.blocksize
docker compose exec namenode hdfs getconf -confKey dfs.namenode.http-address
docker compose exec namenode hdfs getconf -confKey dfs.heartbeat.interval
    hdfs://namenode 3 134217728 0.0.0.0:9870 3
    getconf prints the final, merged value: from your site file if set (fs.defaultFS, dfs.replication), otherwise the default (block size, address, heartbeat).

  3. See where each value came from

    curl -s http://localhost:9870/conf | grep -o "<source>[^<]*</source>" | sort | uniq -c | sort -rn
curl -s http://localhost:9870/conf | grep -o "<property><name>dfs.replication</name>[^/]*</value><final>[a-z]*</final><source>[^<]*</source>"
    542 <source>hdfs-default.xml</source> 523 <source>yarn-default.xml</source> 376 <source>core-default.xml</source> 194 <source>mapred-default.xml</source> 89 <source>hdfs-rbf-default.xml</source> 17 <source>programmatically</source> 5 <source>yarn-site.xml</source> 4 <source>mapred-site.xml</source> 2 <source>hdfs-site.xml</source> <property><name>dfs.replication</name><value>3</value><final>false</final><source>hdfs-site.xml</source>
    The running NameNode knows about 1,750 settings. All but a handful are defaults; only a few come from our site files. “programmatically” means the daemon set the value itself at start-up.

  4. Override for one command with -D

    hdfs dfs -D dfs.replication=2 -put canteen_orders.csv data/copy2.csv
hdfs dfs -D dfs.blocksize=1048576 -put canteen_orders.csv data/small_blocks.csv
hdfs dfs -stat "%r %o %b %n" data/*
hdfs fsck /user/hadoop/data/small_blocks.csv | grep "Total blocks"
    3 134217728 4692009 canteen_orders.csv 2 134217728 4692009 copy2.csv 3 1048576 4692009 small_blocks.csv Total blocks (validated): 5 (avg. block size 938401 B)
    %r = replication, %o = block size, %b = bytes. Same file, three different storage layouts: replication and block size are chosen by the writing client, per file. With 1 MB blocks the 4.5 MB file becomes 5 blocks. (Open a shell with docker compose exec namenode bash; the CSV was copied to /tmp in Lesson 4.3.)

  5. Change an existing file, and test “final”

    hdfs dfs -setrep -w 3 data/copy2.csv
# a copy of the configuration with dfs.replication marked final
cp -r /opt/hadoop/etc/hadoop /tmp/fconf
#   in /tmp/fconf/hdfs-site.xml: <value>3</value><final>true</final>
HADOOP_CONF_DIR=/tmp/fconf hdfs dfs -D dfs.replication=2 -put canteen_orders.csv data/final_test.csv
hdfs dfs -stat "%r %n" data/copy2.csv data/final_test.csv
    Replication 3 set: data/copy2.csv Waiting for data/copy2.csv .... done 3 copy2.csv 2 final_test.csv
    -setrep -w changes an existing file and waits until the new copies exist. The second line is the surprise from the story, tested for real: final blocks later configuration files, but -D sets the value directly in the client, so 2 still wins.

  6. Open the web UIs

    In a browser on your PC: http://localhost:9870 (NameNode) and http://localhost:8088 (ResourceManager). Below are the real pages of the practice cluster, cropped.

    Screenshots show only the parts used in this course. The same data is available as JSON from /jmx (next step).

  7. Read the same facts as JSON

    curl -s "http://localhost:9870/jmx?qry=Hadoop:service=NameNode,name=FSNamesystemState" \
  | python3 -c "import sys,json; b=json.load(sys.stdin)['beans'][0]; [print(k,'=',b[k]) for k in ['FSState','NumLiveDataNodes','NumDeadDataNodes','FilesTotal','BlocksTotal','UnderReplicatedBlocks']]"
    FSState = Operational NumLiveDataNodes = 3 NumDeadDataNodes = 0 FilesTotal = 8 BlocksTotal = 8 UnderReplicatedBlocks = 0
    This is how monitoring systems watch a cluster: they poll /jmx and raise alerts when, for example, dead DataNodes or under-replicated blocks appear.
WARN> After editing a *-site.xml file, restart the daemons that read it (and copy the file to every node). Editing the file alone changes nothing in a running daemon, which is the most common “my setting doesn't work” mistake.
5 See it happen

One property, four layers

Follow dfs.replication through Kabir's experiments. Each terminal line is from the real run in Part 4.

Where does dfs.replication come from? 6 steps
What you see
  1. Inside Hadoop's jar, hdfs-default.xml says replication is 3.
  2. The running NameNode's /conf page shows the value 3 and its source: hdfs-site.xml (the cluster's own setting, also 3).
  3. Kabir writes one file with -D dfs.replication=2: that file gets 2 copies.
  4. -setrep changes the existing file to 3 copies and waits until the NameNode has made them.
  5. With final=true in the site file, -D still sets 2: final protects against later files, not a direct setting.
  6. Every file remembers the replication and block size it was written with.
Behind the screen
  1. The bottom layer always exists: every property has a default in the jars.
  2. Site files sit on top. Here the cluster's own file says 3 as well, so only the source changes.
  3. A client's -D sits on top of both, for that client's own work only.
  4. Replication of an existing file is changed with setrep, which tells the NameNode to add or remove copies.
  5. final stops later configuration files from overriding the value. A value set directly with -D or in code is not a file, so it still applies.
  6. The result is stored per file: four files, each with the settings it was written with.

Try it yourself: settings in the playground

The upload controls are settings a client sends: Block is dfs.blocksize and Replication is dfs.replication. Change them per upload and compare the files in the NameNode metadata tab.

6 Real-world use

Configuration and UIs at work

1. Configuration under version control

Site files live in Git or in the cluster manager, with a history of every change. A change is reviewed, pushed to all nodes, and followed by a rolling restart, one node at a time.

Change + review→Push to all nodes→Rolling restart

2. Per-job tuning without touching the cluster

A heavy nightly job asks for more memory per task and a specific queue with -D options, while every other job keeps the cluster defaults.

Cluster defaults→Job overrides→Only that job changes

3. Monitoring from /jmx

Monitoring systems (Prometheus exporters, Grafana dashboards, cluster managers) poll the daemons' /jmx endpoints for live DataNodes, capacity, missing blocks and queue usage, and page the on-call engineer when thresholds are crossed.

/jmx→Dashboards→Alerts

4. The UIs are the first stop in an incident

When users say “jobs are slow”, engineers open the ResourceManager UI (queues full? nodes lost?) and the NameNode UI (dead DataNodes? safe mode? disk full?) before reading any log.

Complaint→RM + NN UIs→Then logs

Simplified; organisations differ in tools and policies.
