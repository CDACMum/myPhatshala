Riya downloads Hadoop 3.5.0 onto her Windows laptop, double-clicks the file, and nothing useful happens. Kabir tries on his old Ubuntu laptop: start-dfs.sh prints ERROR: JAVA_HOME is not set and could not be found three times. Then Permission denied (publickey,password). They come to Arjun Sir, frustrated. “Hadoop is broken!”

A> Hadoop isn't broken. It's standing on three legs, and each of you is missing one. R> Which ones? A> Riya, Hadoop is built for Linux. 2 Definition

Hadoop's prerequisites

Formal definition (write this in exams)

Apache Hadoop requires: (1) a supported operating system, in practice Linux (GNU/Linux is the supported production platform; on Windows, WSL 2 or a virtual machine provides a Linux environment); (2) a Java Development Kit of a supported version: for Hadoop 3.5 the server daemons require JDK 17 (clients support JDK 17 and 21), while Hadoop 3.3 and 3.4 run on Java 8 or 11; the JAVA_HOME environment variable must point to it, typically set in etc/hadoop/hadoop-env.sh; and (3) SSH with an sshd service running and passwordless key-based login from the master to every node (including localhost), because the cluster start/stop scripts use SSH to launch remote daemons.

In simple words

You need a Linux machine (or Ubuntu inside Windows), Java 17 installed and its location written in Hadoop's settings, and SSH set up so your computer can log in to itself without asking for a password. Then Hadoop's start scripts can do their job.

Words you'll meet in this lesson

WSL 2Windows Subsystem for Linux: runs a real Linux (e.g. Ubuntu) inside Windows 10/11.
JDKJava Development Kit: the Java runtime plus compiler and tools like jps.
JAVA_HOMEEnvironment variable holding the Java install folder, e.g. /usr/lib/jvm/java-17-openjdk-amd64.
Environment variableA named value the shell passes to programs, set with export NAME=value.
PATHThe list of folders the shell searches for commands. Add Hadoop's bin and sbin so hdfs works anywhere.
~/.bashrcA script that runs every time you open a terminal. Put your export lines here so they persist.
SSHSecure Shell: log in to and run commands on another machine over the network.
Key pairA private key (kept secret) and public key (copied to ~/.ssh/authorized_keys) that allow login without a password.

LEVELS> Prerequisites at three levels L1> Cooking needs a kitchen, gas and a key
  • Linux is the kitchen Hadoop was designed for. Windows users borrow a Linux kitchen through WSL.
  • Java is the gas: no daemon can “cook” without it, and Hadoop must know which cylinder to use (JAVA_HOME).
  • SSH is a master key: the head chef (start script) walks into every room (node) to switch things on, without knocking each time.
L2> The Linux you actually need
  • Move around: pwd, ls -l, cd, mkdir -p.
  • Files: cat, less, nano (to edit XML), cp, mv, tar -xzf.
  • Install software: sudo apt update, sudo apt install ….
  • Variables: export JAVA_HOME=…, echo $JAVA_HOME, add lines to ~/.bashrc, then source ~/.bashrc.
  • Processes: jps (Java processes), ps aux | grep java, kill.
  • Logs: tail -f on files in $HADOOP_HOME/logs.
L3> Why SSH, and when you don't need it
  • start-dfs.sh reads the workers file and runs ssh <host> hdfs --daemon start datanode for each host. On one machine, the only host is localhost, so SSH still runs.
  • You can skip SSH by starting each daemon yourself: hdfs --daemon start namenode, hdfs --daemon start datanode, yarn --daemon start resourcemanager… This is how containers and cluster managers start Hadoop.
  • Keys must be protected: ~/.ssh should be 700 and authorized_keys 600, or sshd refuses them.
  • In production, Hadoop runs as dedicated service users (hdfs, yarn, mapred), and configuration management or Cloudera Manager/Ambari handles start-up, not hand-made keys.
  • Hadoop 3.5's requirement of JDK 17 for servers is a real break from older releases; a cluster upgrade usually starts with a Java upgrade.
/LEVELS EXAM> For “List the prerequisites for installing Hadoop”, write: Linux OS (or a Linux VM/WSL), Java (JDK) of a supported version with JAVA_HOME set (in hadoop-env.sh), SSH with passwordless login to all nodes, enough RAM and disk, and the Hadoop binary tarball. 4 Step by step

Prepare a fresh Ubuntu (or WSL) for Hadoop

  1. Windows only: install WSL 2 with Ubuntu

    wsl --install -d Ubuntu-24.04
    Restart when asked, open “Ubuntu” from the Start menu and create a Linux user name and password. From now on, every command runs in that Ubuntu terminal.

  2. Install Java 17 and SSH

    sudo apt update
sudo apt install -y openjdk-17-jdk-headless openssh-server openssh-client wget
    headless means no graphical parts, which servers don't need. openssh-server provides sshd, which the start scripts connect to.

  3. Find where Java lives

    java -version
readlink -f $(which java)
    openjdk version "17.0.20.1" 2026-08-18 OpenJDK Runtime Environment (build 17.0.20.1+1-1-24.04-Ubuntu) OpenJDK 64-Bit Server VM (build 17.0.20.1+1-1-24.04-Ubuntu, mixed mode, sharing) /usr/lib/jvm/java-17-openjdk-amd64/bin/java
    JAVA_HOME is that path without /bin/java: /usr/lib/jvm/java-17-openjdk-amd64. The exact update number on your machine will differ.

  4. Set variables permanently

    export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64
export HADOOP_HOME=$HOME/hadoop-3.5.0
export PATH=$PATH:$HADOOP_HOME/bin:$HADOOP_HOME/sbin
    Then run source ~/.bashrc. HADOOP_HOME points to where you'll unpack Hadoop in Lesson 4.3; adding bin and sbin to PATH lets you type hdfs and start-dfs.sh from any folder.

  5. Start the SSH server

    sudo service ssh start
    On WSL, services don't always start automatically: run this each time you open Ubuntu (or enable systemd in WSL). Passwordless keys are set up in Lesson 4.3, right before the first start-dfs.sh.
5 See it happen

Kabir's three errors: what he sees, and what is really missing

Every message on the left is real output from Hadoop 3.5.0 on Ubuntu 24.04. On the right: which leg was missing.

From errors to a ready machine 6 steps
What you see
  1. Fresh Ubuntu: Java isn't installed at all. Ubuntu even suggests the install command.
  2. After installing OpenJDK 17, java -version works.
  3. But start-dfs.sh still says JAVA_HOME is not set (this is real Hadoop 3.5.0 output). Why, if java works?
  4. Because the start script launches daemons over SSH in a new, non-interactive shell. Setting JAVA_HOME in hadoop-env.sh fixes it for every daemon.
  5. SSH to localhost is refused: no key is authorised and password logins aren't allowed for scripts.
  6. Create a key pair and authorise it: now SSH works without a password, and the start scripts can do their job.
Behind the screen
  1. Linux is there, but the Java leg is missing entirely.
  2. Installing the JDK fixes Java for Kabir's own terminal.
  3. Start scripts launch daemons through SSH in a new non-interactive shell. It doesn't load his terminal settings, so the daemons can't find Java.
  4. hadoop-env.sh is read by every Hadoop command and daemon, whatever shell starts it. Setting JAVA_HOME there fixes the leg for good.
  5. The SSH leg: sshd is running but has no authorised key for Kabir, so scripted logins fail.
  6. With a key pair in authorized_keys, all three legs are in place.
6 Real-world use

Prerequisites at work

1. Upgrades start with Java

Moving a cluster to Hadoop 3.5 means moving every server to JDK 17 first, and checking that Hive, Spark and custom jobs work on it. Java versions are often the longest part of an upgrade plan.

Old JDK→Test on JDK 17→Then upgrade Hadoop

2. Automating prerequisites on hundreds of servers

Platform teams don't install Java and SSH keys by hand. Tools like Ansible (or the cluster manager) install the same JDK, users, keys and kernel settings on every node, so all nodes are identical.

Playbook→Same setup on every node→No surprises

3. Laptops of data engineers

Many engineers on Windows laptops use WSL 2 for daily data work: Hadoop and Spark clients, Python, Git, Docker. It gives the same Linux commands as the servers they deploy to.

Windows laptop→Ubuntu on WSL→Same as servers

4. Service users instead of personal accounts

In production, NameNode and DataNodes run as the hdfs user, YARN as yarn, and history as mapred. Each has only the permissions it needs, which limits damage if one is compromised.

One daemon→Its own Linux user→Least privilege

Simplified; organisations differ in tools and policies.
