1 The story

Two install paths, one working cluster each

Install day in the lab. Riya wants to see every file Hadoop needs, so she installs it by hand inside WSL Ubuntu. Kabir wants three DataNodes on his laptop, which is impossible by hand on one machine, so he reaches for Docker. Both start with a coffee and an error message.

R> Sir, which way is the “correct” install? A> Both are used at work. Admins who build clusters know the files and steps of Path A by heart, because every installer, Docker image and cluster manager does exactly those steps underneath. And Path B is how many teams spin up a practice or test cluster in minutes. K> Then why not only Docker? It's faster. A> Because when Docker hides something and it breaks, you'll need to know what it hid. Today, Riya's machine becomes a one-node cluster; Kabir's laptop gets one NameNode, three DataNodes and YARN. Every command and output you'll see was run for real on Hadoop 3.5.0, including the errors.
2 Definition

Installing Hadoop

Formal definition (write this in exams)

Installing Apache Hadoop from the binary release means: downloading the release tarball and verifying its checksum; unpacking it and setting HADOOP_HOME and PATH; setting JAVA_HOME in etc/hadoop/hadoop-env.sh; writing the site configuration files (core-site.xml, hdfs-site.xml, mapred-site.xml, yarn-site.xml, and workers); setting up passwordless SSH for the start scripts; formatting the NameNode once; and starting HDFS (start-dfs.sh) and YARN (start-yarn.sh). A containerised installation runs the same daemons from a prebuilt image (e.g. apache/hadoop:3.5.0), with configuration supplied through environment variables and one container per daemon, orchestrated by Docker Compose.

In simple words

Download Hadoop, check it isn't damaged, unpack it, tell it where Java is, fill in four settings files, let it log in to itself, prepare an empty HDFS, and start it. Or let Docker start ready-made Hadoop containers for you.

Words you'll meet in this lesson

TarballA .tar.gz archive. Hadoop's binary release is one tarball; unpack it with tar -xzf.
Checksum (SHA-512)A fingerprint of the file. If yours matches the published one, the download is complete and untampered.
HADOOP_HOMEThe folder where Hadoop is unpacked, e.g. ~/hadoop-3.5.0.
hadoop-env.shA script every Hadoop command reads first. Set JAVA_HOME here.
*-site.xmlYour settings. They override Hadoop's built-in defaults (Lesson 4.4).
Docker imageA ready-made file system with Hadoop and Java installed: apache/hadoop:3.5.0.
ContainerA running copy of an image with its own host name and IP. Here: one container per daemon.
Docker ComposeStarts several containers from one docker-compose.yaml file, on a shared network.

LEVELS> Installing at three levels L1> Setting up a new canteen
  • Download and verify: the equipment arrives; check every box is sealed.
  • Configure: decide where the store room (HDFS) and the kitchen (YARN) are.
  • Format: label the empty shelves of the store room once, on opening day.
  • Start: switch on the store room and the kitchen. Docker is a ready-made food truck: everything installed, just drive it in.
L2> The order matters
  • Java and SSH first (Lesson 4.1), then unpack, then hadoop-env.sh, then the XML files.
  • Format once, before the first start-dfs.sh. Formatting again erases HDFS.
  • Start HDFS before YARN: jobs read input from HDFS.
  • Wait until safe mode is off (hdfs dfsadmin -safemode wait) before writing.
  • Check each stage: hadoop version → jps → hdfs dfs -ls → yarn node -list → run an example job.
L3> What production installs add
  • Dedicated users (hdfs, yarn, mapred), data on dedicated disks (dfs.datanode.data.dir lists several mount points), logs and PIDs outside /tmp.
  • Configuration pushed identically to all nodes by automation or a cluster manager; a workers file or service manager instead of hand-run scripts.
  • Kerberos security, TLS for web UIs, high availability (two NameNodes, JournalNodes, ZooKeeper), monitoring and log rotation.
  • Container setups mount volumes for the NameNode and DataNode folders, otherwise data disappears with the container (you'll see this happen below).
/LEVELS EXAM> For “Explain the steps to install Hadoop in pseudo-distributed mode”, list: install Java and SSH → download and extract Hadoop → set JAVA_HOME, HADOOP_HOME, PATH → edit core-site.xml (fs.defaultFS), hdfs-site.xml (dfs.replication=1), mapred-site.xml (mapreduce.framework.name=yarn), yarn-site.xml (yarn.nodemanager.aux-services=mapreduce_shuffle) → passwordless SSH → hdfs namenode -format → start-dfs.sh, start-yarn.sh → verify with jps and the web UIs.

4 Step by step

Path A: install natively on Ubuntu or WSL

Prerequisites from Lesson 4.1 must be done: Java 17, SSH server running, JAVA_HOME in ~/.bashrc. All commands run in the Ubuntu terminal as your normal user; the user here is riya, so replace /home/riya with your own home folder.

  1. Download and verify

    cd ~
wget https://dlcdn.apache.org/hadoop/common/hadoop-3.5.0/hadoop-3.5.0.tar.gz
wget https://dlcdn.apache.org/hadoop/common/hadoop-3.5.0/hadoop-3.5.0.tar.gz.sha512
sha512sum -c hadoop-3.5.0.tar.gz.sha512
    hadoop-3.5.0.tar.gz: OK
    Anything other than OK means a broken or altered download: delete it and download again. If a newer 3.5.x exists when you read this, change the version number everywhere.

  2. Unpack and set the environment

    tar -xzf hadoop-3.5.0.tar.gz
cat >> ~/.bashrc <<'EOF'
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64
export HADOOP_HOME=$HOME/hadoop-3.5.0
export PATH=$PATH:$HADOOP_HOME/bin:$HADOOP_HOME/sbin
EOF
source ~/.bashrc
hadoop version | head -1
    Hadoop 3.5.0
    If you added the JAVA_HOME line in Lesson 4.1, don't add it twice. bin holds the user commands (hdfs, yarn, hadoop); sbin holds the start and stop scripts.

  3. Tell Hadoop where Java is

    echo "export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64" >> $HADOOP_HOME/etc/hadoop/hadoop-env.sh
    This is the fix for ERROR: JAVA_HOME is not set and could not be found: daemons started over SSH read this file, not your ~/.bashrc.

  4. core-site.xml and hdfs-site.xml

    <configuration>
    <property>
        <name>fs.defaultFS</name>
        <value>hdfs://localhost:9000</value>
    </property>
</configuration>
    <configuration>
    <property>
        <name>dfs.replication</name>
        <value>1</value>
    </property>
    <property>
        <name>dfs.namenode.name.dir</name>
        <value>file:///home/riya/hadoop-data/namenode</value>
    </property>
    <property>
        <name>dfs.datanode.data.dir</name>
        <value>file:///home/riya/hadoop-data/datanode</value>
    </property>
</configuration>
    The two dir settings move HDFS out of /tmp, which Linux may empty on reboot. Open each file with nano and replace the empty <configuration> block.

  5. mapred-site.xml and yarn-site.xml

    <configuration>
    <property>
        <name>mapreduce.framework.name</name>
        <value>yarn</value>
    </property>
    <property>
        <name>mapreduce.application.classpath</name>
        <value>$HADOOP_MAPRED_HOME/share/hadoop/mapreduce/*:$HADOOP_MAPRED_HOME/share/hadoop/mapreduce/lib/*</value>
    </property>
</configuration>
    <configuration>
    <property>
        <name>yarn.nodemanager.aux-services</name>
        <value>mapreduce_shuffle</value>
    </property>
    <property>
        <name>yarn.nodemanager.env-whitelist</name>
        <value>JAVA_HOME,HADOOP_COMMON_HOME,HADOOP_HDFS_HOME,HADOOP_CONF_DIR,CLASSPATH_PREPEND_DISTCACHE,HADOOP_YARN_HOME,HADOOP_HOME,PATH,LANG,TZ,HADOOP_MAPRED_HOME</value>
    </property>
    <property>
        <name>yarn.nodemanager.disk-health-checker.max-disk-utilization-per-disk-percentage</name>
        <value>99.5</value>
    </property>
</configuration>
    The first two properties come from the official single-node guide: they run MapReduce on YARN and let containers find the MapReduce jars. The third is for laptops: by default a NodeManager whose disk is over 90% full marks itself unhealthy and runs nothing (see the errors table). Leave it out on real servers.

  6. Passwordless SSH to localhost

    ssh-keygen -t rsa -P '' -f ~/.ssh/id_rsa
cat ~/.ssh/id_rsa.pub >> ~/.ssh/authorized_keys
chmod 0600 ~/.ssh/authorized_keys
ssh localhost "echo connected"
    Warning: Permanently added 'localhost' (ED25519) to the list of known hosts. connected
    The first connection asks to trust the host key (type yes). After that, no questions and no password: exactly what start-dfs.sh needs.

  7. Format the NameNode (once)

    hdfs namenode -format
    … INFO common.Storage: Storage directory /home/riya/hadoop-data/namenode has been successfully formatted. …
    Look for “successfully formatted” in the long output. Never run this again on a cluster with data you need.

  8. Start HDFS and check it

    start-dfs.sh
jps
hdfs dfsadmin -safemode wait
hdfs dfs -mkdir -p /user/riya
hdfs dfs -mkdir input
hdfs dfs -put $HADOOP_HOME/etc/hadoop/*.xml input
    Starting namenodes on [localhost] Starting datanodes Starting secondary namenodes [vm] vm: Warning: Permanently added 'vm' (ED25519) to the list of known hosts. 4865 NameNode 4966 DataNode 5304 Jps 5166 SecondaryNameNode Safe mode is OFF
    /user/riya is your HDFS home: relative paths like input mean /user/riya/input. The NameNode web UI is now at http://localhost:9870 (WSL forwards it to Windows).

  9. Start YARN and run a job

    start-yarn.sh
yarn node -list
hadoop jar $HADOOP_HOME/share/hadoop/mapreduce/hadoop-mapreduce-examples-3.5.0.jar \
    grep input output 'dfs[a-z.]+'
hdfs dfs -cat output/*
    Starting resourcemanager Starting nodemanagers Total Nodes:1 Node-Id Node-State Node-Http-Address Number-of-Running-Containers localhost:40123 RUNNING localhost:8042 0 … INFO mapreduce.Job: Job job_1792562428511_0001 completed successfully … 1 dfsadmin 1 dfs.replication 1 dfs.namenode.name.dir 1 dfs.datanode.data.dir
    The ResourceManager UI is at http://localhost:8088. The result lists the dfs… property names found in the XML files you uploaded, including the ones you just wrote.

  10. Stop, and start again later

    stop-yarn.sh
stop-dfs.sh
# next time:
start-dfs.sh
start-yarn.sh
hdfs dfs -cat output/*
    Stopping nodemanagers Stopping resourcemanager Stopping namenodes on [localhost] Stopping datanodes Stopping secondary namenodes [vm] … 1 dfsadmin 1 dfs.replication 1 dfs.namenode.name.dir 1 dfs.datanode.data.dir
    The output is still there after a full stop and start, because HDFS lives in ~/hadoop-data. On WSL, also run sudo service ssh start after reopening Ubuntu.

Path B: a 3-DataNode cluster with Docker Compose

Install Docker Desktop (Windows/macOS, with the WSL 2 back end on Windows) or Docker Engine (Linux), and give it at least 6 GB of memory. Then make a folder hadoop-cluster with these two files.

  1. docker-compose.yaml

    services:
  namenode:
    image: apache/hadoop:3.5.0
    hostname: namenode
    command: ["hdfs", "namenode"]
    ports:
      - 9870:9870
    env_file:
      - ./config
    environment:
      ENSURE_NAMENODE_DIR: "/tmp/hadoop-hadoop/dfs/name"
  datanode:
    image: apache/hadoop:3.5.0
    command: ["hdfs", "datanode"]
    env_file:
      - ./config
  resourcemanager:
    image: apache/hadoop:3.5.0
    hostname: resourcemanager
    command: ["yarn", "resourcemanager"]
    ports:
      - 8088:8088
    env_file:
      - ./config
  nodemanager:
    image: apache/hadoop:3.5.0
    command: ["yarn", "nodemanager"]
    env_file:
      - ./config
    One service per daemon. ENSURE_NAMENODE_DIR: if this folder does not exist, the image formats the NameNode before starting it. It must be the NameNode's real folder; the image runs as user hadoop, so that is /tmp/hadoop-hadoop/dfs/name. (With /tmp/hadoop-root/…, as in some older examples, the NameNode is re-formatted on every start; this happened during testing.) Only the NameNode and ResourceManager UIs are published to your PC.

  2. config (the settings)

    CORE-SITE.XML_fs.defaultFS=hdfs://namenode
HDFS-SITE.XML_dfs.namenode.rpc-address=namenode:8020
HDFS-SITE.XML_dfs.replication=3
MAPRED-SITE.XML_mapreduce.framework.name=yarn
MAPRED-SITE.XML_yarn.app.mapreduce.am.env=HADOOP_MAPRED_HOME=/opt/hadoop
MAPRED-SITE.XML_mapreduce.map.env=HADOOP_MAPRED_HOME=/opt/hadoop
MAPRED-SITE.XML_mapreduce.reduce.env=HADOOP_MAPRED_HOME=/opt/hadoop
YARN-SITE.XML_yarn.resourcemanager.hostname=resourcemanager
YARN-SITE.XML_yarn.nodemanager.pmem-check-enabled=false
YARN-SITE.XML_yarn.nodemanager.vmem-check-enabled=false
YARN-SITE.XML_yarn.nodemanager.aux-services=mapreduce_shuffle
YARN-SITE.XML_yarn.nodemanager.disk-health-checker.max-disk-utilization-per-disk-percentage=99.5
CAPACITY-SCHEDULER.XML_yarn.scheduler.capacity.maximum-am-resource-percent=0.5
CAPACITY-SCHEDULER.XML_yarn.scheduler.capacity.root.queues=default
CAPACITY-SCHEDULER.XML_yarn.scheduler.capacity.root.default.capacity=100
CAPACITY-SCHEDULER.XML_yarn.scheduler.capacity.root.default.maximum-capacity=100
    Each line is FILE_property=value; the image writes them into the matching XML file when a container starts. Write /opt/hadoop literally: this file does not expand variables like $HADOOP_HOME.

  3. Start with three DataNodes

    docker compose up -d --scale datanode=3
docker compose ps --format "table {{.Name}}\t{{.Status}}"
    NAME STATUS hadoop-cluster-datanode-1 Up 35 seconds hadoop-cluster-datanode-2 Up 35 seconds hadoop-cluster-datanode-3 Up 35 seconds hadoop-cluster-namenode-1 Up 36 seconds hadoop-cluster-nodemanager-1 Up 36 seconds hadoop-cluster-resourcemanager-1 Up 36 seconds
    The first run downloads the image (about 2.2 GB unpacked). Six containers, six “machines”, one network.

  4. Check the cluster

    docker compose exec namenode hdfs dfsadmin -printTopology
docker compose exec resourcemanager yarn node -list
    Rack: /default-rack 172.18.0.6:9866 (hadoop-cluster-datanode-3.hadoop-cluster_default) In Service 172.18.0.5:9866 (hadoop-cluster-datanode-1.hadoop-cluster_default) In Service 172.18.0.7:9866 (hadoop-cluster-datanode-2.hadoop-cluster_default) In Service Total Nodes:1 Node-Id Node-State Node-Http-Address Number-of-Running-Containers 8f368ea04df2:45495 RUNNING 8f368ea04df2:8042 0
    Three DataNodes in HDFS, one NodeManager in YARN. The NodeManager's name is its container ID.

  5. Store a file and see its three copies

    docker compose exec namenode hdfs dfs -mkdir -p /user/hadoop/data
docker compose cp canteen_orders.csv namenode:/tmp/canteen_orders.csv
docker compose exec namenode hdfs dfs -put /tmp/canteen_orders.csv data/
docker compose exec namenode hdfs fsck /user/hadoop/data/canteen_orders.csv -files -blocks -locations
    /user/hadoop/data/canteen_orders.csv 4692009 bytes, replicated: replication=3, 1 block(s): OK 0. BP-1055690327-172.18.0.2-1792562685335:blk_1073741825_1001 len=4692009 Live_repl=3 [DatanodeInfoWithStorage[172.18.0.6:9866,…], DatanodeInfoWithStorage[172.18.0.7:9866,…], DatanodeInfoWithStorage[172.18.0.5:9866,…]] Status: HEALTHY Number of data-nodes: 3
    canteen_orders.csv is a 3 lakh-row practice file (order_id, item, amount); any CSV works. One 4.5 MB block, stored on all three DataNodes.

  6. Run a job, then see what down does

    docker compose exec namenode yarn jar \
    /opt/hadoop/share/hadoop/mapreduce/hadoop-mapreduce-examples-3.5.0.jar \
    grep data out "vada pav|samosa|dosa"
docker compose exec namenode hdfs dfs -cat "out/*"
docker compose down
docker compose up -d --scale datanode=3
docker compose exec namenode hdfs dfs -ls data
    INFO Job:1765 - Job job_1792562696287_0001 completed successfully Rack-local map tasks=1 … 50021 samosa 49986 vada pav 49948 dosa ls: `data': No such file or directory
    down deletes the containers, and with them the HDFS data. The map task is “rack-local”, not “data-local”, because DataNodes and the NodeManager are separate containers here.

  7. Pause and resume without losing data

    docker compose stop
docker compose start
docker compose exec namenode hdfs dfsadmin -safemode wait
docker compose exec namenode hdfs dfs -ls data
    Safe mode is OFF Found 1 items -rw-r--r-- 3 hadoop supergroup 4692009 2026-10-21 06:15 data/canteen_orders.csv
    stop keeps the containers and their disks, so the file is still there (after uploading it again following the down above). Use stop/start at the end of each practice session.

5 See it happen

What docker compose up builds, and what down destroys

Kabir's cluster from Path B, step by step. Every terminal line is from the real test run.

Life of the Docker practice cluster 6 steps
What you see
  1. Compose reads docker-compose.yaml, creates a private network and starts the master containers first.
  2. Three DataNode containers (because of --scale datanode=3) and a NodeManager start next.
  3. Each DataNode registers with the NameNode. Three addresses, three “machines”.
  4. A 4.5 MB file becomes one block, and the NameNode places a copy on each of the three DataNodes.
  5. A MapReduce job counts three canteen items across 3 lakh orders and writes the result to HDFS.
  6. down removes the containers. The new cluster is empty: the old HDFS data lived inside the removed containers.
Behind the screen
  1. The masters start on a private Docker network. Only their web ports are forwarded to your PC.
  2. Workers join the same network. Docker gives each a host name and an IP address.
  3. Each DataNode sends heartbeats to the NameNode at namenode:8020 and reports its storage.
  4. The client writes one block; the pipeline stores a replica on each DataNode (replication 3).
  5. YARN runs the map task in a container on the NodeManager, which reads one replica from a DataNode container.
  6. After down and up, brand-new containers start with empty disks: a fresh, formatted NameNode and no blocks.
6 Real-world use

Installs at work

1. The manual steps become a script

Platform teams turn exactly the Path A steps into automation (Ansible roles, shell scripts, images), so a new worker is installed in minutes and identical to the others.

Manual once→Automated→Same on every node

2. Throw-away test clusters

Developers start a Compose cluster to test a job, a new configuration or an upgrade, then delete it. Because down removes everything, every test starts clean.

up→Test→down

3. Verifying what is installed

Security teams require checksums (and often GPG signatures) for every downloaded binary, and keep an internal copy of approved releases instead of downloading on each server.

Download→Verify→Internal repository

4. Runbooks for known errors

Support teams keep a table like the one in Part 4: the exact error text, the cause and the fix. Searching the log for the exact message is the first step in almost every Hadoop incident.

Error text→Runbook→Fix in minutes

Simplified; organisations differ in tools and policies.
