Data engineering · ingestionFresher

Load a JSON API into the warehouse

A partner sends orders through an API as JSON. Each order has a nested list of items and an optional coupon object. Your manager wants revenue per dish in the warehouse by tomorrow.

The interviewer is checking: do you know how to land, flatten and validate semi-structured data?

Show a strong answer
  1. Land the raw JSON as-is in the lake (bronze) so you can always reprocess.
  2. Define the target tables: orders (one row per order) and order_items (one row per item, with order_id).
  3. Explode items into order_items; keep the coupon fields as nullable columns.
  4. Validate types and required fields; send failing rows to a quarantine table.
  5. Compute revenue from order_items (qty × price), not from a repeated order total.

Avoid: flattening straight into one wide table and summing a repeated order-level amount.

Analytics · unstructured1–3 years

What are customers complaining about?

You have 2 lakh free-text reviews from the last month in English, Hindi and Hinglish. The product head wants the top five complaint themes by city.

The interviewer is checking: can you turn unstructured text into a structured, trustworthy result?

Show a strong answer
  • Store the raw reviews with order id, city and date (metadata).
  • Clean the text (lower-case, remove emojis or map them, normalise common spellings).
  • Classify each review into themes with a language model or a trained classifier; record the label and a confidence score.
  • Check a random sample by hand to measure accuracy before trusting the numbers.
  • Aggregate counts per theme per city, and show example reviews behind each number.

Avoid: counting single keywords like “bad” and presenting it as insight without checking accuracy.

Reliability · schema drift1–3 years

Revenue dropped 40% overnight

The morning dashboard shows revenue down 40%, but the business team says orders were normal. An app release went out yesterday.

The interviewer is checking: do you suspect the data before the business, and know how to prevent it next time?

Show a strong answer

First, compare raw event counts with orders in the database: if raw counts are normal, the pipeline lost data. Check rejected and quarantined rows and diff the event schema before and after the release; you are likely to find a renamed or retyped field. Fix the parser to handle both versions, backfill the affected day from the raw zone, and publish a corrected dashboard. To prevent repeats: schema checks on every batch, quarantine instead of silent drops, alerts on row-count changes, and a versioned data contract checked before app releases.

Avoid: telling leadership that revenue fell, or patching the dashboard by hand.

Design · storage choiceFresher

Where should each kind of data live?

A new ed-tech start-up has student records, quiz-attempt events from the app, lecture videos and doubt-chat messages. They ask you where to store each.

The interviewer is checking: can you match each shape to sensible storage?

Show a strong answer
  • Student records (structured, updated often) → a relational database such as PostgreSQL.
  • Quiz events (semi-structured, high volume) → a stream (Kafka) into the data lake as JSON, then flattened Parquet tables for analysis.
  • Lecture videos (unstructured, huge) → object storage plus a CDN for streaming; a metadata table for titles, durations and tags.
  • Doubt chats (unstructured text) → stored raw, labelled by topic, and searchable through a search engine.

Avoid: putting videos inside database tables, or forcing every event into a fixed table schema on day one.
