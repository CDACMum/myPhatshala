Platform design · storageFresher

Where should each kind of data live?

A new fintech app has customer accounts, a stream of transactions, KYC document scans and seven years of history for audits. Where would you store each?

The interviewer is checking: can you match workloads to block, file and object storage?

Show a strong answer
  • Accounts and live transactions: a relational database on SSD block storage, replicated across zones.
  • Transaction history for analytics: Parquet tables in object storage (the lake), partitioned by date.
  • KYC scans: object storage with encryption, restricted access and the object key stored in the database.
  • Seven-year audit data: lifecycle rules moving old partitions to cool and archive tiers, with deletion after the legal period.

Avoid: putting scanned documents in database tables, or everything on expensive SSD volumes.

Performance · small files1–3 years

The report got slower every week

A daily Spark report on a Kafka-fed table took 5 minutes in January and 50 minutes in June. Data volume grew only 20%.

The interviewer is checking: do you suspect the small-files problem and know how to confirm and fix it?

Show a strong answer
  1. Count files and their average size per partition; you will likely find thousands of KB-sized files per day.
  2. Check where time goes in the Spark UI: listing and task scheduling for tiny tasks dominate.
  3. Fix the writer: larger micro-batches, fewer output partitions (coalesce), or a table format with optimised writes.
  4. Run compaction (for example Delta OPTIMIZE) on old partitions.
  5. Add a monitor on average file size so it doesn’t creep back.

Avoid: adding more executors, which only creates even more tiny tasks.

Migration · HDFS to cloud1–3 years

Our jobs broke after moving to S3

A team copied its Hadoop jobs from HDFS to S3 unchanged. Jobs now run much longer at the commit step, and once a crash left a half-written output folder that a dashboard read.

The interviewer is checking: do you know the semantic differences between HDFS and object storage?

Show a strong answer

HDFS renames are atomic metadata operations; on S3 a directory rename is copy-plus-delete of every object, slow and not atomic. Use object-store-aware committers (such as the S3A committers) or, better, write through a table format (Delta Lake, Iceberg, Hudi) that commits via a transaction log. Also revisit file sizes, listing-heavy code and data-locality assumptions, since compute and storage are now separate.

Avoid: blaming S3 performance and adding bigger clusters.

Fundamentals · interviewFresher

“Explain HDFS architecture”

A standard interview question: describe how HDFS stores a file and handles failures.

The interviewer is checking: can you explain blocks, replication, NameNode and DataNodes clearly?

Show a strong answer

A file is split into large blocks (128 MB by default). Each block is stored on several DataNodes (replication factor 3 by default, placed on different racks for safety). The NameNode holds the namespace (directories, files) and the mapping of blocks to DataNodes in memory; DataNodes store the blocks and send heartbeats and block reports. On a DataNode failure, the NameNode re-replicates the affected blocks from surviving copies. Clients get block locations from the NameNode and read data directly from DataNodes. For high availability, a standby NameNode takes over if the active one fails.

Avoid: confusing the NameNode with storage of the actual data.
