Choose a shard key for a chat app

A chat app stores messages. The main screens are “messages in this conversation, newest first” and “my conversations”. Messages reach crores per day. How would you partition the messages table?

The interviewer is checking: can you choose a key from the access pattern and spot hotspots?

Show a strong answer

Partition by conversation_id (all messages of a chat together, so one query reads one partition), clustered by time descending. Bound partition size for huge group chats by adding a time bucket: (conversation_id, month). Keep “my conversations” in a separate table partitioned by user_id. Avoid partitioning by date (write hotspot) or by user for messages (a conversation would span many partitions).

Avoid: picking a key without saying which queries it serves.

Operations · rebalancing1–3 years

We need to go from 8 to 12 shards

A sharded MySQL setup uses user_id % 8. Growth means you need 12 shards. How do you migrate safely?

The interviewer is checking: do you understand the cost of mod-N resharding and safe migration steps?

Show a strong answer
  1. Recognise that changing the modulus moves most users. Consider moving to a directory-based or consistent-hash scheme, or to many logical shards (for example 1,024) mapped onto physical servers, so future growth moves whole logical shards.
  2. Copy data to the new layout in the background, then dual-write new changes to old and new locations.
  3. Verify counts and checksums per user range.
  4. Switch reads gradually, then writes; keep a rollback path.
  5. Finally, clean up the old copies.

Avoid: changing the modulus in production and copying everything in one big bang.

Streaming · Kafka1–3 years

Order events are processed out of order

Consumers sometimes process “order delivered” before “order placed” for the same order. The topic has 12 partitions and producers don’t set a message key.

The interviewer is checking: do you know how Kafka partitioning affects ordering?

Show a strong answer

Without a key, messages are spread across partitions, and Kafka guarantees order only within one partition. Set the message key to order_id so all events for an order go to the same partition and are consumed in order by one consumer. Choose enough partitions for the needed parallelism, and watch for hot keys. Changing partition count later remaps keys, so plan it up front.

Avoid: adding a sleep in consumers or using a single partition for everything.

Fundamentals · interviewFresher

“What is the difference between partitioning and replication?”

Interviewers often ask this to check basic distributed-systems vocabulary.

The interviewer is checking: can you separate splitting data from copying data?

Show a strong answer

Partitioning (sharding) splits data into parts so each node stores and processes only a subset; it increases capacity and throughput. Replication stores copies of the same data on several nodes; it increases availability, durability and read capacity. Real systems use both: each partition is replicated (for example HDFS blocks with 3 replicas, Kafka partitions with a replication factor, Cassandra partitions on several nodes).

Avoid: using the two words as if they mean the same thing.
