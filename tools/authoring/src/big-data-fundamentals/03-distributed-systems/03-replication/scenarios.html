Database design · availabilityFresher

Make the orders database survive a server failure

The orders database runs on one server. Management wants it to survive a hardware failure with at most a minute of downtime and no lost orders.

The interviewer is checking: can you design basic replication with clear RPO/RTO?

Show a strong answer
  • Add a synchronous (or semi-synchronous) standby in another availability zone: RPO ≈ 0 for committed orders.
  • Automate failover with health checks and a managed service or a tool like Patroni, aiming for an RTO under a minute.
  • Connect apps through a stable endpoint (DNS or proxy) that moves to the new primary.
  • Add async read replicas for reports.
  • Keep point-in-time backups for mistakes and test restores regularly.

Avoid: saying “take nightly backups” as the answer to availability.

Consistency · user experience1–3 years

“I paid but the app says unpaid”

After adding read replicas, some customers see “payment pending” for a few seconds right after paying, and pay again.

The interviewer is checking: do you recognise replication lag and read-your-writes?

Show a strong answer

Reads go to asynchronous replicas that haven’t applied the payment yet. Fix: route a user’s reads to the primary for a short window after they write (or for critical screens like payment status), or read from a replica only if it has caught up to the user’s last write position. Make the payment API idempotent so a second tap doesn’t charge twice, and show “processing” instead of “unpaid” while confirming.

Avoid: removing replicas entirely, or adding a fixed sleep before reading.

Streaming · durability1–3 years

Messages lost during a broker restart

During a rolling restart of Kafka brokers, a few order events disappeared, although producers logged success.

The interviewer is checking: do you know how acks, ISR and unclean leader election interact?

Show a strong answer

Producers were probably using acks=1 (or the topic allowed unclean leader election), so a leader acknowledged messages and then lost leadership before followers copied them. Fix: replication factor 3, min.insync.replicas=2, producers with acks=all and idempotence enabled, and unclean.leader.election.enable=false. Restart brokers one at a time, waiting for under-replicated partitions to return to zero.

Avoid: adding retries in consumers, which can’t bring back a message that was never stored.

Fundamentals · interviewFresher

“Is replication the same as backup?”

Interviewers like this question because many candidates say yes.

The interviewer is checking: do you understand what each protects against?

Show a strong answer

No. Replication keeps live copies so the system survives machine, disk or zone failures with little downtime; every change, including mistakes and corruption, is copied within seconds. Backups are point-in-time copies kept separately so you can restore data after accidental deletes, bugs, ransomware or logical corruption. Production systems need both, and backups must be tested by actually restoring them.

Avoid: saying “we have three replicas, so we don’t need backups”.
