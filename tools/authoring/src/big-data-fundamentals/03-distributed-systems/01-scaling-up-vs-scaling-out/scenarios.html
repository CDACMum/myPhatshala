System design · estimationFresher

Estimate storage for a photo feature

A food app will let users attach up to 2 photos to each review. 50 lakh reviews are written a day and 20% include photos. Estimate storage per year.

The interviewer is checking: can you structure an estimate with clear assumptions and units?

Show a strong answer

Assume 1.5 photos per review that has photos, 3 MB per photo, plus 2 thumbnails of 100 KB. Photos per day = 50 lakh × 20% × 1.5 = 15 lakh. Storage per day ≈ 15 lakh × 3.2 MB ≈ 4.6 TB. Per year ≈ 1.7 PB before replication (object storage handles durability internally). Then discuss: compress or resize images, move old photos to cheaper tiers, serve through a CDN.

Avoid: jumping to a number without assumptions, or forgetting thumbnails and tiers.

Scaling · architecture1–3 years

The API is slow at 8 pm every day

A delivery app’s API slows down every evening. Adding more API servers didn’t help.

The interviewer is checking: do you find the real bottleneck before scaling?

Show a strong answer
  1. Check where time goes: API CPU, database CPU and connections, cache hit ratio, external calls.
  2. If the database is the bottleneck, more API servers just add more database connections and make it worse.
  3. Fixes: cache hot reads, add read replicas, tune slow queries and indexes, pool connections, scale the database up; shard if writes are the limit.
  4. Then autoscale the stateless tier with a sensible maximum.

Avoid: adding servers blindly; scaling the wrong tier.

Reliability · statelessness1–3 years

Users get logged out randomly

After moving from one server to five behind a load balancer, users complain of random logouts and empty carts.

The interviewer is checking: do you recognise in-memory session state?

Show a strong answer

Sessions and carts are stored in each server’s memory, so requests landing on another server don’t find them. Move session state to a shared store (Redis) or use signed tokens (JWT) for authentication, and store carts in Redis or the database. Avoid relying on sticky sessions, which break when servers restart and unbalance load.

Avoid: increasing session timeouts or pinning all users to one server.

Performance · advanced3+ years

Doubling the cluster made the job slower

A distributed job ran in 40 minutes on 50 nodes. On 100 nodes it took 55 minutes.

The interviewer is checking: do you understand contention and coordination costs?

Show a strong answer

Look for shared bottlenecks (one metadata service, one database, a global lock, a single reducer) and coordination overhead (shuffles that grow with node count, many small tasks, frequent synchronisation). Measure stage by stage. Fixes include fewer, larger partitions, reducing shuffles (broadcast small tables, pre-partition data), removing global locks, and choosing the node count near the measured optimum rather than “as many as possible”.

Avoid: assuming linear scaling and adding even more nodes.
