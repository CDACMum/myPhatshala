System design · consistencyFresher

Which parts of a food app need strong consistency?

For a food-delivery app, decide the consistency level for: wallet balance, cart, restaurant ratings, “only 5 left” limited-dish stock, and order status shown to the customer.

The interviewer is checking: can you choose consistency per piece of data with reasons?

Show a strong answer
  • Wallet: strong (never double-spend).
  • Limited stock: strong at checkout (never oversell); browsing can show a slightly stale count.
  • Cart: eventual/available, with a correct merge.
  • Ratings: eventual.
  • Order status: read-your-writes and monotonic reads per user (status never goes backwards), not necessarily global linearizability.

Avoid: labelling the whole app “CP” or “AP”.

Distributed DB · Cassandra1–3 years

Users sometimes see old profile data

A Cassandra cluster with replication factor 3 uses consistency level ONE for reads and writes. Users occasionally see their old profile after updating it.

The interviewer is checking: do you understand tunable consistency and its trade-offs?

Show a strong answer

With W = 1 and R = 1, R + W = 2 is not greater than N = 3, so a read can hit a replica that hasn’t received the write. Use QUORUM for both (2 + 2 > 3) on profile reads and writes, accepting slightly higher latency, or LOCAL_QUORUM in multi-datacentre setups. Keep ONE for data where staleness is harmless. Make sure clocks are synchronised, since Cassandra resolves conflicts by timestamp (last-write-wins).

Avoid: switching everything to ALL, which fails whenever any replica is down.

Architecture · multi-region3+ years

Go active-active in two regions?

Leadership wants the app to accept writes in both Mumbai and Hyderabad at the same time, so a regional outage causes no downtime.

The interviewer is checking: do you see the consistency consequences of multi-leader designs?

Show a strong answer

Active-active means concurrent writes to the same data in both regions, so conflicts are certain during network issues. For each entity decide: can it be partitioned by region (each user’s data has a home region), can it merge automatically (counters, sets via CRDTs), or must it be strongly consistent (wallet, inventory), which then needs a single leader or consensus with cross-region latency on every write. Often the answer is active-active for most data plus a single-region leader for money, with fast failover.

Avoid: promising zero downtime and strong consistency everywhere without discussing the latency or conflicts.

Fundamentals · interviewFresher

“Explain the CAP theorem”

The classic question. Many candidates answer “pick any two of three”.

The interviewer is checking: can you explain it precisely and correct the myth?

Show a strong answer

In a distributed system, when a network partition happens, you must choose between consistency (every read returns the latest write) and availability (every request gets a non-error response). Partitions can’t be prevented, so partition tolerance is required, and “CA” only applies to non-distributed systems. Example: a bank ledger chooses consistency and refuses some requests during a partition; a like counter chooses availability and reconciles later. Without partitions, PACELC adds a latency vs consistency trade-off, and many databases let you tune consistency per query.

Avoid: saying “Cassandra is AP, MongoDB is CP, done” without explaining what is traded and when.
