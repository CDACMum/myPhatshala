2 Definition

What is the big data ecosystem?

Formal definition (write this in exams)

The big data ecosystem is the collection of tools and services that together form a data platform: they ingest data from sources, store it at scale, process it in batch or in real time, make it available for querying and analysis, serve the results to people and applications, and orchestrate, monitor and govern every step. Each tool specialises in one or two of these layers, and a working platform combines several of them into data pipelines.

In simple words

No single tool does everything. A data platform is a team of tools: one brings data in, one keeps it, one cleans and calculates, one answers questions, one draws the charts, and one acts as the manager who decides what runs when.

Words you'll meet in this lesson

Data sourceWhere data is born: an app, a website, a database, a sensor, a log file.
IngestionBringing data from sources into the platform, continuously or in batches.

TopicIn Kafka, a named stream of events, like orders or payments.
Data lakeCheap, huge storage that keeps raw files of any format (more in Lesson 4.3).

DAGDirected Acyclic Graph: a list of tasks with arrows showing which must finish first. Airflow pipelines are DAGs.

The six layers at a glance

1. IngestCollect data from apps, databases and devices · Kafka, NiFi, Debezium, Flume, Sqoop (older)
2. StoreKeep data safely at huge scale · HDFS, Amazon S3 / Azure ADLS / Google Cloud Storage, HBase, Cassandra
3. ProcessClean, join, aggregate · Spark, Flink, MapReduce (older), Kafka Streams, dbt
4. Query & analyseAnswer questions with SQL · Hive, Trino/Presto, Spark SQL, Snowflake, BigQuery, Redshift
5. Visualise & serveShow results to people and apps · Power BI, Tableau, Superset, APIs, ML models
6. Orchestrate & governSchedule, monitor, secure, catalogue · Airflow, Oozie (older), YARN/Kubernetes, data catalogs
LEVELS> The same map at three levels L1> The restaurant kitchen

Think of TiffinGo's data platform as a big restaurant kitchen:

  • Ingest = the delivery van that brings vegetables every few minutes.
  • Store = the store-room and fridge. Everything is kept, even things you might need later.
  • Process = the cooks who wash, cut and cook raw vegetables into dishes.
  • Query = the order counter, where anyone can ask “how many thalis today?”
  • Visualise = the menu board and the plated food: results people can see.
  • Orchestrate = the head chef with a timetable: dal must be ready before rice is served.

If you remember the kitchen, you can place any tool. That is all you need for now.

L2> What each layer must handle, and how to pick a tool
  • Ingest must cope with many sources and bursts. Use Kafka for continuous events (orders, clicks), CDC tools like Debezium to copy database changes, and file or API pulls for daily batches.
  • Store must be cheap, huge and safe. Raw files go to HDFS or cloud object storage (S3, ADLS, GCS); fast lookups by key go to NoSQL (HBase, Cassandra).
  • Process splits into batch (Spark on yesterday's data) and stream (Flink or Spark Streaming on events as they arrive). That's Lesson 4.2.
  • Query gives analysts SQL: Hive/Trino on lake files, or a warehouse like Snowflake or BigQuery for clean tables.
  • Orchestrate: Airflow runs the daily DAG: check data arrived → Spark job → load warehouse → refresh dashboard, and retries failures.

Quick rule: “Need it live?” → stream tools. “Need SQL?” → query engine or warehouse. “Need it every night at 2 am?” → orchestrator.

L3> How real platforms are designed today
  • Storage and compute are separated. Data sits in object storage; Spark, Trino or a warehouse start compute only when needed, and scale independently. Old Hadoop clusters tied both to the same machines.
  • Open table formats (Apache Iceberg, Delta Lake, Apache Hudi) add database features (transactions, schema changes, time travel) to files in a lake. This is the lakehouse idea, covered in Lesson 4.3.
  • Resource managers moved: many teams now run Spark and Flink on Kubernetes instead of Hadoop's YARN. Kafka 4.0 removed its ZooKeeper dependency in favour of its built-in KRaft mode.
  • Legacy you will still meet: MapReduce, Sqoop (retired by Apache in 2021), Flume and Oozie appear in exams and older clusters, but are rarely chosen for new projects.
  • Managed vs self-hosted: cloud services (EMR, Dataproc, Databricks, BigQuery) trade higher unit prices and some lock-in for far less operations work. The right answer depends on team size, scale and cost.
  • Governance is a layer, not an afterthought: a catalog (what data exists), lineage (where it came from), access control and data-quality checks.

3 Types and ways to use it

Three ways to build the same platform

Classic Hadoop (on-premises)

HDFS for storage, YARN for resources, MapReduce/Hive/Spark for processing, Oozie for scheduling, all on the company's own servers.

2008 → still in banks, telecom, government

Cloud-native, open source

Object storage (S3/ADLS/GCS), Spark or Flink on Kubernetes, Kafka, Trino, Airflow. You run the tools; the cloud provides machines.

Flexible

Fully managed cloud

Kinesis or Pub/Sub, a cloud warehouse (BigQuery, Snowflake, Redshift), managed Spark (Databricks, EMR, Dataproc), managed Airflow.

TIP> Kafka is not Airflow. A common beginner mix-up: Kafka moves data continuously; Airflow schedules jobs and moves no data itself. One is the delivery van, the other is the head chef's timetable.
4 Step by step

Follow one TiffinGo order through all six layers

  1. Source: the app creates an event

    {"order_id": 90017, "user": "kabir", "kitchen": "K12", "city": "Pune",
 "item": "veg thali", "amount": 120, "ts": "2026-10-19T12:31:08"}
    The moment Kabir taps Place order, the app sends this event. At lunch rush thousands of phones send events like this every minute.

  2. Ingest: Kafka receives it

    kafka-console-producer --topic orders --bootstrap-server broker1:9092
    The event is appended to the orders topic. Kafka doesn't process it; it keeps events in order, durably, and lets many systems read them: the live dashboard, the fraud checker and the lake loader.

  3. Store: raw copy in the lake

    s3://tiffingo-lake/raw/orders/date=2026-10-19/hour=12/part-0003.json
    A loader writes Kafka events into the lake every few minutes, in folders by date and hour. Raw data is never changed, so it can always be reprocessed if a bug is found later.

  4. Process: Spark cleans and joins

    orders = spark.read.json("s3://tiffingo-lake/raw/orders/date=2026-10-19/")
kitchens = spark.read.parquet("s3://tiffingo-lake/clean/kitchens/")
daily = (orders.dropDuplicates(["order_id"])
               .join(kitchens, "kitchen")
               .groupBy("city", "kitchen_name").sum("amount"))
daily.write.mode("overwrite").parquet("s3://tiffingo-lake/gold/daily_sales/date=2026-10-19/")
    This is real PySpark (you'll write it in the Spark course). Spark splits the day's files across many executors, removes duplicate events, joins kitchen names and totals sales, exactly the partition → process → combine pattern from Lesson 1.3.

  5. Query: SQL on the result

    SELECT city, SUM(amount) AS revenue
FROM gold.daily_sales
WHERE date = '2026-10-19'
GROUP BY city ORDER BY revenue DESC;
    Trino, Hive or a warehouse runs this SQL directly over the Parquet files or loaded tables. Analysts never need to know where the files live.

  6. Visualise and orchestrate

    The Power BI dashboard refreshes, and the city manager sees yesterday's sales at 6 am.

    Behind all of it, an Airflow DAG ran at 2 am: check raw data arrived → run Spark job → check row counts → load warehouse → refresh dashboard. If Spark fails, Airflow retries it and alerts the on-call engineer.
5 See it happen

One order: what Kabir sees, and what the platform does

Step through the six frames. Left: Kabir's phone and his manager's dashboard. Right: the layer that is working at that moment.

An order travels the ecosystem 6 steps
What you see
  1. Kabir orders a veg thali for ₹120 on the TiffinGo app.
  2. The order is confirmed in about a second.
  3. He tracks the rider. Nothing else about data is visible to him.
  4. At 2 am the city manager's dashboard still shows the day before yesterday.
  5. By morning the dashboard shows yesterday's sales by city.
  6. It updated at 05:42, ready for the 6 am meeting, and Kabir's ₹120 is one tiny part of the Pune bar.
Behind the screen
  1. Source: the app turns Kabir's tap into a small JSON event.
  2. Ingest: the event is appended to Kafka's orders topic. The live dashboard, the fraud checker and the lake loader each read it independently.
  3. Store: a loader writes the raw event into the data lake, in a folder for that date and hour.
  4. Process: at 2 am, Spark executors process all of yesterday's files in parallel: remove duplicates, join kitchen details, total by city.
  5. Query and visualise: the dashboard runs SQL over the clean table and draws the bars.
  6. Orchestrate: an Airflow DAG ran every step in order, so the report was ready before 6 am.
6 Real-world use

The ecosystem in real time: three live scenarios

The same layers behave very differently at lunch rush, at 2 am and when a company moves to the cloud. Watch all three.

Real-time scenario 1

Lunch rush: the streaming path saves a kitchen

12:00 to 13:00 on a weekday. Orders flow through Kafka into a stream processor (Flink) that counts orders per kitchen every minute. Watch what happens when one kitchen is overloaded.

Live orders per kitchen 5 steps
Animated example
  1. 12:00: every order event flows Kafka → Flink, which keeps a running count of orders per kitchen for the last 5 minutes.
  2. 12:25: the rush starts and all counts rise. The stream processor updates them continuously.
  3. 12:41: kitchen K12 crosses its limit. An alert fires within seconds, not the next day.
  4. Action: the app automatically marks K12 as busy and shows a longer delivery time, so customers spread to other kitchens.
  5. Result: the rush is absorbed. This is the streaming path of the ecosystem; Lesson 4.2 goes deep into it. (Numbers are illustrative.)
Real-time scenario 2

2 am: the orchestrator handles a failure while everyone sleeps

The nightly daily_sales DAG starts at 02:00. Halfway through, a cloud machine running the Spark job disappears. Watch Airflow deal with it.

An Airflow night 5 steps
Animated example
  1. 02:00: Airflow starts the DAG. The first task checks that yesterday's raw files have arrived.
  2. 02:04: the Spark job starts on 40 executors.
  3. 02:31: the cloud reclaims a machine and the job fails. Airflow marks downstream tasks as waiting, so no half-finished data reaches the dashboard.
  4. 02:36: Airflow automatically retries after a delay, as configured, and posts an informational alert.
  5. 05:42: everything succeeds and the dashboard refreshes before the 6 am meeting. Orchestration turns failures into delays instead of disasters.

Where you'll see the ecosystem at work

1. Food delivery: live ETAs

Rider GPS pings every few seconds go through Kafka to a stream processor that updates arrival times. The same pings are stored in the lake and used overnight to retrain the ETA model.

GPS pings→Kafka → Flink · lake → Spark→ETA on your phone

2. Banking: regulatory reports

Core banking databases are copied nightly with CDC into the lake, Spark builds risk and compliance tables, and orchestrated jobs produce the reports banks must file with regulators on time.

Core banking DB→CDC → lake → Spark → warehouse→Regulatory report

3. Smart electricity meters

Smart meters send readings every 15 minutes. Utilities ingest them as streams, store years of history for billing disputes, and run batch jobs to forecast demand and find power theft patterns.

Meter readings→Stream ingest → lake → batch models→Bills + forecasts

4. E-commerce search

Every search and click is ingested, stored in the lake, and processed daily to improve search ranking. Analysts query the click tables with SQL to find searches that return nothing useful.

Searches + clicks→Kafka → lake → Spark + Trino→Better results

5. Streaming video: what to watch next

Play, pause and skip events feed both a real-time path (what's trending right now) and a batch path (recommendations recomputed nightly), all scheduled and monitored by an orchestrator.

Viewing events→Stream + batch on one platform→Your home screen
