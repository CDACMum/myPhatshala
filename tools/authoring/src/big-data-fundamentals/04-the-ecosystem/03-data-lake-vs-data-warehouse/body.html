1 The story

Two bosses, two kinds of questions

TiffinGo is growing fast, and Kabir now gets requests from two very different people. The finance head wants one trusted number: last month's revenue by city, matching the bank to the rupee. The data scientist wants everything: raw app clicks, rider GPS trails, customer reviews and kitchen photos, to find out why customers cancel. Kabir tries to keep all of it in one MySQL database. Within a week, it breaks.

K> Sir, the finance report needs perfect tables. But the data scientist's photos and JSON clicks don't fit into tables at all, and every app update adds new fields that break my loads. A> You're trying to put a godown inside a library, Kabir. A data warehouse is the library: only clean, checked data, on fixed shelves, so anyone can find the right answer fast. A data lake is the godown: everything kept exactly as it arrived, cheaply, in any shape. R> Then why not just use the godown for everything? It holds more. A> Because a godown with no catalogue becomes a swamp. Six months later nobody knows which of three copies of rider data is right, and finance can't trust any number from it. K> So I need both? A> Most companies use both, or a lakehouse that puts library rules on top of godown storage. Today you'll build a tiny lake and warehouse yourself and see exactly where each one shines.
2 Definition

What are a data lake and a data warehouse?

Formal definition (write this in exams)

A data warehouse is a central repository of structured, cleaned and integrated data, organised (often as fact and dimension tables) for SQL analysis and reporting. Data must match a defined schema before it is loaded (schema-on-write). A data lake is a repository that stores large volumes of raw data in its native format (structured, semi-structured and unstructured) on cheap, scalable storage; structure is applied when the data is read (schema-on-read). A lakehouse combines lake storage with warehouse features such as ACID transactions, schema enforcement and fast SQL, using open table formats.

In simple words

A warehouse keeps only clean, checked tables so business questions get trusted answers fast. A lake keeps everything as it arrives, so nothing is lost and anyone can explore it later. A lakehouse tries to do both in one place.

Words you'll meet in this lesson

SchemaThe structure of data: which columns exist and their types.
Schema-on-writeCheck and enforce the structure before storing. Bad rows are rejected at load time.
Schema-on-readStore anything; apply structure only when reading it for a question.
ETL / ELTExtract-Transform-Load (clean before loading, classic warehouse) vs Extract-Load-Transform (load raw first, transform inside the platform).
OLTP vs OLAPOLTP databases run the app (many small writes); OLAP systems answer analytical questions over huge history (warehouses).
Fact / dimensionA fact table holds events (orders, amounts); dimension tables describe them (kitchen, city, date).
ParquetA compressed, columnar file format: queries read only the columns they need.
Data swampA lake with no catalogue, owners or quality checks, where data can't be found or trusted.

Lake, warehouse and lakehouse at a glance

Data warehouseStructured · schema-on-write · cleaned, trusted · fast SQL · higher cost per TB · Snowflake, BigQuery, Redshift, Synapse, Teradata
Data lakeAny format · schema-on-read · raw · very cheap storage · needs a catalogue to stay useful · HDFS, S3, ADLS, Google Cloud Storage
LakehouseLake storage + table formats (ACID, schema checks, time travel) · one copy of data for BI and ML · Delta Lake, Apache Iceberg, Apache Hudi; Databricks, Trino, Spark
LEVELS> Lake vs warehouse at three levels L1> Library vs godown

A library (warehouse) accepts only catalogued books and puts each one on the right shelf. Finding a book is quick and you can trust it. A godown (lake) takes every delivery as it is: boxes, sacks, loose items. It holds far more, costs less per square foot, but you need a list to find anything.

  • Warehouse questions: “What was revenue by city last month?” “How many orders were cancelled?” Clean, repeated, business questions.
  • Lake questions: “Do photos with good lighting get more orders?” “What do angry reviews have in common?” New, exploratory questions on raw data.
L2> Schemas, formats, zones and models
  • Schema-on-write vs schema-on-read: the warehouse rejects a row with text in a number column; the lake stores it and the reader decides what to do.
  • ETL vs ELT: classic warehouses cleaned data before loading (ETL). Modern platforms load raw data first and transform inside (ELT), often with SQL tools like dbt.
  • File formats: CSV and JSON are easy but slow; Parquet and ORC are columnar and compressed; Avro is row-based and common for streaming.
  • Partitioning: folders like date=2026-10-19/ let queries skip days they don't need.
  • Medallion zones: bronze (raw), silver (cleaned, de-duplicated), gold (business-ready aggregates).
  • Star schema: one central fact table (orders) joined to dimension tables (kitchen, customer, date). It makes BI queries simple and fast.
L3> Lakehouse internals, governance and cost
  • Open table formats (Iceberg, Delta Lake, Hudi) keep a transaction log next to Parquet files. That gives ACID commits, MERGE/UPDATE/DELETE on lake data, schema evolution and time travel (“query the table as it was yesterday”).
  • Catalog and governance: Hive Metastore, AWS Glue Data Catalog or Unity Catalog record tables, owners, schemas and lineage; access policies and masking protect personal data.
  • Performance: partition pruning, column pruning, file statistics (min/max per file) and avoiding the small-files problem (millions of tiny files slow every query).
  • Cost model: lake storage is cheap and compute is paid per query or per cluster. Modern warehouses also separate storage from compute, so the line between lake and warehouse is blurring.
  • Choosing: many companies keep a lake (or lakehouse) as the single source of raw truth and serve curated gold tables to a warehouse or directly to BI.

The medallion zones

Bronze (raw)

Data exactly as received: duplicates, wrong types, extra fields and all. Never edited, so it can always be reprocessed.

Keep everything

Silver (clean)

De-duplicated, typed, validated and joined where needed. One row per real-world thing. Data scientists usually start here.

Trust the rows

Gold (business)

Aggregated, business-ready tables: daily revenue by city, cancellation rate by kitchen. Dashboards and finance read these.

4 Step by step

One messy order, from bronze to the finance report

  1. Bronze: store it exactly as it arrived

    {"order_id": 2, "kitchen": "K12", "item": "biryani", "amount": "250"}
{"order_id": 2, "kitchen": "K12", "item": "biryani", "amount": "250"}
    The same order arrived twice (an app retry) and the amount is text. The lake stores both lines anyway. Rejecting data at this stage would lose evidence we may need later.

  2. Silver: clean while reading (schema-on-read)

    raw = [{"order_id": 2, "amount": "250"}, {"order_id": 2, "amount": "250"}]
seen, silver = set(), []
for r in raw:
    if r["order_id"] not in seen:
        seen.add(r["order_id"])
        silver.append({"order_id": r["order_id"], "amount": int(r["amount"])})
print(silver)
    [{'order_id': 2, 'amount': 250}]
    The reader decides the structure: one row per order, amount as an integer. The result is written as Parquet in the silver zone.

  3. Gold: load into a warehouse table (schema-on-write)

    CREATE TABLE fact_orders (
  order_id INTEGER PRIMARY KEY,
  kitchen  TEXT REFERENCES dim_kitchen(kitchen),
  amount   INTEGER NOT NULL CHECK (amount > 0)
);
    The warehouse table has rules. A row with amount −90 is rejected at load time. Finance can trust every row that got in.

  4. Model: facts and dimensions

    -- fact_orders(order_id, kitchen, date_key, amount)
-- dim_kitchen(kitchen, kitchen_name, city)
-- dim_date(date_key, day, month, is_weekend)
    A star schema: the fact table in the middle, small descriptive tables around it. Any “by city” or “by month” question is a simple join.

  5. Query: the finance number

    SELECT k.city, SUM(f.amount) AS revenue
FROM fact_orders f JOIN dim_kitchen k ON f.kitchen = k.kitchen
GROUP BY k.city;
    Fast and trusted, because the hard work (de-duplicating, fixing types, rejecting bad rows) happened before. Meanwhile, the data scientist can still go back to bronze for the raw reviews and clicks.

What you see
  1. Four kinds of data arrive every day: order rows, JSON clicks, review text and kitchen photos.

  3. The data scientist wants raw reviews and photos to study cancellations.

Behind the screen
  1. The lake stores all four shapes as files. The warehouse only accepts data that fits its tables.
  2. Loading orders into the warehouse checks every row: duplicates removed, the −90 order rejected. This is schema-on-write.
  3. The data scientist reads raw reviews, photos and orders from the lake and decides the structure in the notebook: schema-on-read.
  4. A new coupon field is stored by the lake without trouble, but breaks the warehouse load until the table and pipeline are changed.
  5. Without owners or documentation, the lake fills with copies and test folders: a data swamp.
  6. The redesign: a lakehouse with bronze, silver and gold tables on lake storage, open table formats and a catalogue.

Real-time scenario 3 · Advanced

Same question, 100× less data read: partitions + columns

The table orders holds one year of data: 1.1 TB, 20 columns. The question: “Revenue in Pune during October?” Watch how file layout changes how much data the engine must read (and how much you pay, on pay-per-scan engines).

Pruning what you don't need 5 steps
Animated example
  1. CSV in one folder: to answer one question, the engine reads all 1.1 TB, every row and every column.
  2. Partitioned by month: data stored in folders like month=10/, so the engine reads only October: about 93 GB.
  3. Parquet (columnar): only the city and amount columns are read, about a tenth of the bytes.
  4. Compression and file statistics: files whose min/max city values exclude Pune are skipped; compressed columns are smaller still.
  5. From 1.1 TB to roughly 3 GB. On engines that charge per byte scanned, this is the difference between a costly and a cheap query. (Sizes are illustrative.)

Who uses what

1. Banks: warehouse for reports, lake for fraud models

Regulatory and finance reports come from a tightly controlled warehouse where every number is audited. Fraud teams train models on years of raw transactions, device logs and call-centre notes kept in the lake.

Transactions→Warehouse (reports) + lake (ML)→Audit + fraud scores

2. Hospitals: images in the lake

X-rays and scans are huge unstructured files that belong in a lake; billing, admissions and pharmacy data live in warehouse tables. Researchers join both, with strict access control over patient data.

Scans + records→Lake (images) + warehouse (billing)→Research, reports

3. E-commerce: lakehouse with medallion zones

Clicks, orders and catalogue changes land in bronze, are cleaned into silver and summarised into gold. Dashboards read gold; recommendation models read silver. One copy of data, two kinds of users.

Events + orders→Bronze → silver → gold→BI + ML

4. Telecom: cheap history, fast summaries

Billions of call and data records per day are kept in the lake as compressed, partitioned files for years. Daily summaries per customer and tower are loaded into the warehouse for billing and network dashboards.

Call records→Partitioned Parquet in the lake→Warehouse summaries

5. Startups: start with a warehouse

A young company with only database tables often starts with a cloud warehouse and adds a lake later, when it needs raw events, images or machine learning. There is no rule that you need both on day one.

App database→Cloud warehouse + dbt→Dashboards
