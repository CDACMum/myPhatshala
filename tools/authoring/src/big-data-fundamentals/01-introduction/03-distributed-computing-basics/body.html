1 The story

One lakh answer sheets, one week

Arjun Sir has been made the head examiner for the university's semester exams: 1,00,000 answer sheets, results due in one week. One teacher checks about 50 sheets a day. Riya does the maths and looks worried: one teacher would need 2,000 days.

R> Sir, with 100 teachers it's 1,000 sheets each: 20 days. Still too long! A> Then 400 teachers: 250 sheets each, five days. But see what else we must organise. Who decides which bundle goes to whom? What if a teacher falls ill on day three? And we don't carry one lakh sheets to one room. Teachers go to the evaluation centres where the sheets already are. R> And at the end, teachers don't send back the sheets, just the marks list. You only merge the lists. A> Exactly. You've just described distributed computing: split the data, process the parts at the same time, move the workers to the data, send back small results, combine them, and plan for someone dropping out. R> So Hadoop and Spark are… a very organised exam department? A> A very fast and very strict one. Let's build a small one in Python. K> Sir, at TiffinGo the orders are split by city. Mumbai alone is bigger than four other cities put together. Does that matter? A> It matters a lot, Kabir. The job finishes only when the slowest piece finishes. Today you'll see that problem, called data skew, and also what a cluster does when it can't tell whether a machine is slow or dead.
2 Definition

What is distributed computing?

Formal definition (write this in exams)

Distributed computing is a model in which a task is divided into smaller parts that are processed in parallel on multiple independent computers (nodes) connected by a network. The nodes coordinate by passing messages, and the system presents the combined result as if one computer had done the work. Key ideas are partitioning of data, parallel processing, data locality, aggregation of partial results, and fault tolerance through replication and re-execution.

In simple words

Cut a huge job into pieces, give each piece to a different computer, let them all work at the same time, then put the answers together. If one computer breaks, give its piece to another.

Words you'll meet in this lesson

Partition / blockOne piece of the data. HDFS splits files into blocks; Spark calls them partitions.
Master (coordinator)The node that plans the work, assigns tasks and tracks progress.
WorkerA node that does the actual processing of one or more partitions.
TaskOne unit of work: “process partition 7”. A job is made of many tasks.
Data localityRunning a task on the node that already stores its data, so data doesn't travel over the network.
AggregationCombining the small partial results from workers into the final answer.
ReplicationKeeping copies of each partition on different nodes so a failure doesn't lose it.
StragglerA slow task that delays the whole job, often because its partition is much bigger (data skew).

The five-step pattern

1. PartitionSplit the data into blocks and spread them across nodes (with copies)
2. ScheduleThe master assigns one task per block, preferably on the node that holds it
3. Process in parallelEach worker processes only its own block, at the same time as all others
4. CombineSmall partial results are sent over the network and merged
5. RecoverIf a worker fails, its task is re-run on another node that has a copy
LEVELS> Distributed computing at three levels L1> Teamwork with rules

Distributed computing is teamwork with strict rules. Think of a wedding kitchen: one head cook (the master) plans the menu and gives each cook (a worker) one dish. Everyone cooks at the same time, and the head cook puts the plates together at the end.

  • You use it daily: a UPI payment touches your app's servers, your bank, NPCI and the receiver's bank. A Google search is answered by thousands of machines, each searching its own slice of the web.
  • The golden rules: split fairly, work in parallel, send back small answers, and have a plan when someone drops out.
L2> How the coordination actually works
  • Heartbeats: every worker tells the master “I'm alive, task 60% done” every few seconds. No heartbeat for a while → the worker is treated as failed and its task is re-run elsewhere.
  • Combiners: each worker first combines its own results (local counts) so that only small summaries travel over the network.
  • Shuffle: when results must be grouped by key across machines (all Mumbai orders together), data is exchanged between workers. This network-heavy step is often the slowest part of a job.
  • Easy vs tricky aggregations: sum, count, min and max combine directly. An average needs (sum, count) pairs; distinct counts need sets (or estimates); a median needs much more care.
  • Speculative execution: if one task runs much slower than the rest, the master starts a backup copy on another node and uses whichever finishes first.
L3> Partial failure, skew and the fallacies of distributed computing
  • Partial failure: in one computer, things work or crash together. In a cluster, some parts fail while others keep going, and a silent node may be dead, slow or just cut off. A timeout can't tell which.
  • Idempotent tasks: because a task may run twice (a retry plus a “dead” worker that comes back), outputs must be written so that running twice gives the same result, for example by committing only one attempt per task.
  • Data skew: one hot key (one city, one celebrity's account) makes one partition huge. Fixes: split the hot key into sub-keys (salting), choose a better partition key, or handle the hot key separately.
  • No global clock: each machine's clock drifts a little, so “which event happened first” across machines is hard. Systems use sequence numbers or logical clocks instead.
  • The fallacies of distributed computing (from engineers at Sun Microsystems): it is wrong to assume the network is reliable, latency is zero, bandwidth is infinite, the network is secure, the topology doesn't change, there is one administrator, transport cost is zero, and the network is the same everywhere. Every big data tool is designed around these.
  • Module 3 goes deeper into partitioning, replication, consistency and the CAP theorem.
/LEVELS EXAM> Learn the pattern as partition → parallel process → aggregate, plus the two supporting ideas data locality (“move computation to data”) and fault tolerance (replication + re-execution). This is the foundation of MapReduce, which you'll study in the Hadoop course.

4 Step by step

Count chai orders on three machines

  1. Partition the data

    orders = ["chai", "samosa", "chai", "poha", "chai", "samosa"]
blocks = [orders[0:2], orders[2:4], orders[4:6]]
print(blocks)
    [['chai', 'samosa'], ['chai', 'poha'], ['chai', 'samosa']]
    In a real cluster, a 30 GB file becomes 240 blocks of 128 MB, and each block is stored on three different nodes.

  2. Each machine counts only its block

    block = ["chai", "poha"]           # machine 2's block
counts = {}
for item in block:
    counts[item] = counts.get(item, 0) + 1
print(counts)
    {'chai': 1, 'poha': 1}
    All three machines run this at the same time, each on the block stored on its own disk. Nothing is sent over the network yet: that's data locality.

  3. Send back small results

    Machine 1 sends {'chai': 1, 'samosa': 1}, machine 2 sends {'chai': 1, 'poha': 1}, machine 3 sends {'chai': 1, 'samosa': 1}.

    Each block may be 128 MB, but its partial result is a few bytes: one number per item. The network carries the small summaries, not the data.

  4. Combine

    partials = [{"chai": 1, "samosa": 1}, {"chai": 1, "poha": 1}, {"chai": 1, "samosa": 1}]
total = {}
for p in partials:
    for item, n in p.items():
        total[item] = total.get(item, 0) + n
print(total)
    {'chai': 3, 'samosa': 2, 'poha': 1}
    The same answer as counting all six orders on one machine. Counts combine by simple addition, which is why counting is the classic first distributed program.

  5. A machine fails

    Machine 2 crashes halfway through its block.

    The master notices that machine 2 stopped reporting (it misses its regular heartbeat). Another node holds a copy of block 2, so the master re-runs just that one task there. Blocks 1 and 3 are not redone.
5 See it happen

A distributed job: what Riya sees, and what the cluster does

Step through the six frames. Left: the job's progress page. Right: the master and four workers.

Split, process, survive, combine 6 steps
What you see
  1. Riya submits a job that counts orders in a 512 MB file. She doesn't choose machines; she just submits.
  2. The page shows four tasks running at the same time.
  3. Task 3 turns red: worker lost. The other three continue.
  4. Task 3 starts again automatically. Three tasks are already finished.
  5. All four tasks finish, and the results are being combined.
  6. The job succeeds. The totals are exactly what one machine would have produced, even with the failure.
Behind the screen
  1. The master splits the work into four tasks and assigns each to the worker that already stores the block: data locality.
  2. All four workers process their own block in parallel. Nothing big moves over the network.
  3. Worker 3 stops sending heartbeats. The master marks task 3 as failed. Tasks 1, 2 and 4 are not affected.
  4. Worker 1 holds a replica of block 3, so the master re-runs only task 3 there.
  5. Each worker sends back a tiny partial result: a few counts, not 128 MB of data.
  6. The master aggregates the partial results into the final answer.

6 Real-world use

Real-time scenarios: a cluster at work

Three live scenarios: whether to move the data or the program, a job held up by one giant partition, and an advanced one about a worker that goes silent and then comes back.

Real-time scenario 1

Move the data, or move the program?

A worker needs to process a 100 GB block stored on another machine. It could copy the data over the network, or the program could be sent to the machine that has the data. Watch the difference.

Data locality 5 steps
Animated example
  1. The choice: node A has the program; node B has the 100 GB block. Copy the data, or send the program?
  2. Copy the data: 100 GB over a 1 Gbps link (about 125 MB/s) …
  3. … takes about 14 minutes, and while it happens the network is busy for everyone else. Multiply by hundreds of blocks and the network becomes the bottleneck.
  4. Send the program: the code is a few kilobytes and arrives almost instantly.
  5. Result: node B processes the data from its own disk and returns a tiny result. This is data locality, a core design idea of Hadoop and Spark.
Real-time scenario 2

Data skew: one giant partition holds up the whole job

TiffinGo's daily report splits orders by city, one city per worker. Mumbai has six times more orders than any other city. Watch the progress bars, then see two standard fixes.

Task progress per worker 5 steps
Animated example
  1. Start: the data is partitioned by city, one city per worker. It looks fair, but Mumbai's partition is 12 GB and the others are 2 GB.
  2. 2 minutes: four workers are done. W5 has finished only a sixth of Mumbai.
  3. 12 minutes: the job ends only when W5 ends. Four machines were idle for 10 minutes. This is data skew, and W5 is a straggler.
  4. Fix 1, salting: Mumbai's orders are split into sub-keys Mumbai-1 to Mumbai-6 and spread over all workers. Each worker gets about 4 GB and the job finishes in about 4 minutes. The six Mumbai results are added at the end.
  5. Fix 2, speculative execution: when the data is fair but one machine is slow (say, a failing disk), the master runs a backup copy of that task on a free worker and keeps the first result. (Times are illustrative.)
Real-time scenario 3 · advanced

Slow or dead? The worker that came back

A cluster has no way to look inside a silent machine. Watch how heartbeats and timeouts handle a worker that goes quiet, and the surprising bug that appears when it comes back.

Heartbeats, timeouts and retries 5 steps
Animated example
  1. Heartbeats: each worker sends a small “I'm alive, here's my progress” message to the master every 3 seconds. W3 is running task 7.
  2. Silence: W3's heartbeats stop. The master cannot know whether W3 crashed, is overloaded, or has lost its network connection.
  3. Timeout: after 30 seconds without a heartbeat, W3 is treated as failed. Task 7 is re-run on W4, which has a replica of the same data block.
  4. The surprise: W3 was only cut off from the network. It reconnects and also finishes task 7. Without care, the same orders would be counted twice.
  5. The fix: task outputs go to a temporary location, and the master commits exactly one attempt per task. Running a task twice now gives the same final result: the task is idempotent. (Timings are illustrative.)

Where distributed computing runs every day

1. Spark and Hadoop jobs

A Spark job is exactly this lesson: the driver (master) splits the data into partitions, executors (workers) process them in parallel, and failed tasks are retried. Hadoop MapReduce does the same with map and reduce tasks.

Big file→Partitions → parallel tasks → combine→Result

2. Distributed databases

Databases like Cassandra and MongoDB split tables across nodes by key (called sharding): customers A–M on some nodes, N–Z on others, each with replicas. A query for one customer goes straight to the right node.

Query by customer id→Route to the shard that owns it→Fast reply

3. Event streams with Kafka

Kafka splits each stream of events into partitions stored on different brokers, with replicas. Many consumers read different partitions in parallel, so millions of events per second can be handled.

Events→Partitions on many brokers→Parallel consumers

4. Content delivery networks (CDNs)

Videos and images are copied to servers in many cities, and your phone fetches from the nearest one. That's replication and locality applied to users instead of processing.

Video→Copies in many cities→Nearest server answers

5. Large-scale testing and builds

Big software companies run thousands of automated tests on every code change. They are split across many machines and run in parallel, so results come back in minutes instead of hours.

10,000 tests→Split across 200 machines→Report in minutes

Examples are simplified to show the pattern. Real systems add many more details.
